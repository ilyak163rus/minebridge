I05: финальная приёмка 0.2.0
---------------------------

Runner полной приёмки 0.2.0 — `tools/smoke_i05.py`. Он проверяет финальный JAR и
**установленный wheel** на настоящем Paper 26.2 build 133, не импортируя
`python/src`. В основном прогоне работают два независимых процесса Python
и два настоящих игровых TCP-клиента Minecraft. Другой свежий мир проверяется
с тем же конфигом Minebridge и выключенным test-control. Фактические результаты,
SHA-256 и границы приёмки — [отчёт I05](../docs/reports/I05.ru.md).

Нужны подготовленные `.tools/t02-toolchain.json`, JDK 25, закреплённый Paper
и bootstrap-кэши существующего проектного стенда. Ранее принятое оператором
EULA копируется из `.work/t02-server/eula.txt`; новое согласие runner не создаёт.
Потребуется память для отдельного Paper и свободные loopback-порты.
Он не устанавливает плагин на сервер занятий и не использует его миры.

Финальные артефакты:

- `dist/v0.2/minebridge-paper-0.2.0.jar`;
- `dist/v0.2/minebridge-0.2.0-py3-none-any.whl`;
- `dist/v0.2/minebridge-0.2.0.tar.gz` — исходный Python-архив для проверки поставки.

Установите wheel в отдельные `.venv-v02-311` и `.venv-v02-314`, затем выполните
проверки из корня репозитория:

```powershell
.\.venv-v02-311\Scripts\python.exe -m pip install --no-deps --force-reinstall dist/v0.2/minebridge-0.2.0-py3-none-any.whl
.\.venv-v02-314\Scripts\python.exe -m pip install --no-deps --force-reinstall dist/v0.2/minebridge-0.2.0-py3-none-any.whl
.\.venv-v02-311\Scripts\python.exe -I -m unittest discover -s python/tests -q
.\.venv-v02-314\Scripts\python.exe -I -m unittest discover -s python/tests -q
.\.venv-v02-314\Scripts\python.exe tools/check_v02_package.py `
    --wheel dist/v0.2/minebridge-0.2.0-py3-none-any.whl `
    --sdist dist/v0.2/minebridge-0.2.0.tar.gz `
    --jar dist/v0.2/minebridge-paper-0.2.0.jar `
    --python .venv-v02-311/Scripts/python.exe `
    --python .venv-v02-314/Scripts/python.exe
```

`check_v02_package.py` проверяет архивы, RECORD и офлайн-импорт из папки вне
репозитория; `--python` можно повторять. Ожидается `passed=true` в
`.work/v02-package-results.json`. Подробные команды создания окружений и
проверки VS Code — [DEVELOPMENT.ru.md](../docs/DEVELOPMENT.ru.md).

Observer — отдельный test-only плагин, который читает мир, игроков,
инвентари, эффекты и сущности непосредственно через Paper API. Он не доверяет
ответам Minebridge как единственному доказательству. Для свежего observer JAR
выполните отдельную сборку, не пересобирая финальный production JAR:

```powershell
$v02Tools = Get-Content .tools/t02-toolchain.json -Raw -Encoding UTF8 | ConvertFrom-Json
$env:JAVA_HOME = $v02Tools.javaHome
$env:GRADLE_USER_HOME = Join-Path (Get-Location) '.tools/gradle-cache'
.\plugin\gradlew.bat -p plugin :observer:build --offline --no-daemon
.\.venv-v02-314\Scripts\python.exe tools/smoke_i05.py `
    --plugin dist/v0.2/minebridge-paper-0.2.0.jar `
    --wheel dist/v0.2/minebridge-0.2.0-py3-none-any.whl `
    --python .venv-v02-314/Scripts/python.exe
```

Это также значения по умолчанию всех трёх параметров CLI. `--help` показывает
только справку и не запускает сервер. Runner ничего не собирает, не устанавливает,
не скачивает и не удаляет. Каждый запуск получает отдельные каталоги
`.work/i05-<runId>/server` и `integration/artifacts/i05-<runId>`; они сохраняются.
Входные JAR/wheel и скрипты фиксируются хешами и не должны изменяться в процессе.

Основной прогон объединяет:

- подключение без обязательного токена и имени мира, два процесса и отдельные сессии;
- блоки, области, состояния, старые ID и современные чтения, дальние чанки;
- игроков, SELF, селекторы, телепортацию и буквальный чат двум игровым клиентам;
- выдачу предметов с учётом остатков, эффекты, обычные и специальные сущности;
- buffered/sync, измерение 100 установок до подтверждённого завершения;
- ошибки отложенных записей, обрыв связи без повтора и остановку с ожидающей операцией.

Тестовые игровые клиенты используют отдельный локальный offline-сервер.
Они проходят реальное сетевое подключение и получают пакеты Minecraft;
два игровых клиента не подменяются двумя соединениями Python.
Публичные вызовы выполняет `integration/tests/i05_worker.py` под `-I` с wheel
из выбранного `site-packages`. Инвентарь, эффекты, типы и урон настоящей молнии
проверяются через observer независимо от возвращённых DTO.

Второй запуск создаёт другой мир с новым UUID и другим именем при **тех же**
байтах конфига Minebridge. Он проверяет обычное подключение по двум параметрам,
автоматический выбор Overworld, запись/чтение и `controlEnabled=false`.
Это отдельная проверка обычного режима, без повторного запуска всей матрицы.

Успех требует кода 0 и `allPassed=true` в `.work/i05-paper-results.json`.
Сводка содержит пути к двум manifest; каждый сохраняет проверки, параметры,
входные хеши и результаты остановки. Сводка записывается также при неудаче.
Тестовые порты и процессы освобождаются; пользовательский сервер не останавливается.
Автозагрузка чанка для создания сущности не обещает постоянную симуляцию:
тест последующих игровых тиков обеспечивает обычные условия мира отдельно.
Эта приёмка не заявляет проверку LAN класса, массовой нагрузки, других сборок
Paper или полной совместимости mcpi.

IDE проверяется без Paper через `python/tests/ide-v02/run.js` в настоящем
VS Code/Pylance. Он использует установленный финальный wheel, `extraPaths=[]`
и отдельные workspace/user-data; результат — `.work/ide-v02-results.json`.
Проверяются подсказки пяти каталогов, определения в `site-packages`, сигнатуры
методов и диагностики неправильных типов ключей. PyCharm в приёмку не входит
по решению пользователя. Команды — в текущем разделе
[DEVELOPMENT.ru.md](../docs/DEVELOPMENT.ru.md).

T08: запуск и проверяемое поведение
----------------------------------

После сборки и установки текущего wheel:

```powershell

```

Для уже установленного архивного wheel T08 предусмотрен путь по умолчанию:

```powershell
.\.venv-tools\Scripts\python.exe tools/smoke_t08.py
```

По умолчанию выбирается `dist/t08/minebridge-0.1.0.dev0-py3-none-any.whl`;
установленный пакет должен соответствовать этому wheel. Harness ничего не
собирает, не устанавливает и не скачивает.

Архивные команды T08/T09 также требуют соответствующих production/observer JAR
в build-каталогах: runner не восстанавливает их из `dist/t08` или `dist/t09`.
Текущие JAR T10 не являются сохранённым набором T08/T09. Для текущей приёмки
используется T10, а при отдельном запуске старого runner на новой сборке путь
wheel задаётся через `--wheel` после его установки в `.venv-t01-314`.

Каждый прогон получает новый runId и новый каталог `.work/t08-<runId>/server`.
Мир `t08-world` создаётся заново с seed `20261021`; его фактический UUID
считывается из Paper, а не задаётся ожидаемым значением. Из прежнего стенда
копируются только bootstrap-каталоги `libraries`, `cache`, `versions` и файл
существующего согласия EULA. Старые миры, плагины и настройки не переносятся.
Уникальные каталоги не переиспользуются и автоматически не удаляются.

Один прогон содержит два последовательных запуска с одним и тем же production
JAR; его SHA-256 проверяется в обоих режимах:

1. `-Dminebridge.testControl=true`: четыре теста. Сначала observer самостоятельно
   очищает две позиции, подготавливает разные STONE/COBBLESTONE, независимо
   читает их, проверяет ошибку неизвестного мира, восстановление исходных данных
   и снятие tickets. Затем подтверждается фактическая выгрузка чанка. После
   проверки oracle выполняются gate/release и отмена закрытого соединения.
2. `-Dminebridge.testControl=false`: один тест. Gate недоступен с
   `CONTROL_DISABLED`, независимое чтение и обычная публичная запись работают.

Локальный test-control по умолчанию выключен. В первом режиме gate удерживает
голову очереди одной сессии перед `APPLY_BEGIN` без ожидания на игровом потоке.
Тест подтверждает исходный AIR и отсутствие ACK, продвижение фактического tick,
успешную запись второго Python-процесса, затем освобождает gate и проверяет мир.
Trace связывает caseId/sessionId/requestId, мир, координаты и поток; для каждой
записи требуется `APPLY_BEGIN < APPLY_DONE < ACK_ENQUEUED` по eventSequence.
Идентификатор потока setter/ACK сравнивается с фактическим потоком observer.

При закрытии клиента с удержанным запросом стенд ждёт серверного
`CANCELLED`/`sessionOpen=false` перед освобождением gate и убеждается, что setter
не начался. Удержанный запрос также проверяется попыткой `cleanup`: ожидается
`CASE_BUSY`, после чего gate, AIR и chunk ticket должны оставаться на месте.
Так cleanup не может восстановить позицию до завершения потенциальной записи.
Этот guard охватывает явно отслеживаемые requestId case. Остальные и будущие
запросы не блокируются им: перед очисткой orchestrator завершает свои вызовы
либо закрывает клиентов и наблюдает отмену.

Ожидания основаны на опубликованных результатах/состояниях с deadline, а не на
предположении, что задержки достаточно. Общий startup deadline — 300 секунд,
результат обычной observer-команды ожидается до 25 секунд; выгрузка в T08
запрашивается на 200 ticks. Ошибка/timeout не заменяются успешным результатом.
Первый отказ теста останавливает соответствующий suite, Paper получает `stop`,
а процессы и pipes закрываются в обработчиках завершения.

Прямой запуск `unittest discover -s integration/tests` без явно переданных fixtures
пропускает реальные серверные suite и ничего не запускает. Для выполнения
приёмки T08 используется `tools/smoke_t08.py`, для T09 — отдельный runner ниже.

Доказательства и ограничения
---------------------------

Свежий результат записывается в `.work/t08-paper-results.json`. Полные данные
каждого прогона сохраняются отдельно в `integration/artifacts/t08-<runId>/`:

- `manifest.json`: версии, URL/SHA артефактов, seed/порты, источник согласия EULA,
  результаты обоих режимов, world UUID, проверки и trace;
- `control-enabled.log`, `control-disabled.log`: UTF-8 логи Paper;
- `*-tests.log`: результаты четырёх и одного реальных серверных тестов;
- `*-observer.json`: коррелированные снимки/ошибки и trace;
- `gate-*.json`, `cancel-*.json`, `control-disabled-client.json`: события,
  stderr и коды завершения отдельных Python-процессов.

Успех требует кода завершения 0, `allPassed=true`, отсутствия пропусков,
неожиданных ERROR/SEVERE/FATAL и чистой остановки Paper. Токен генерируется
на прогон, передаётся клиентам через окружение и не включается в manifest.
Он хранится только в локальном игнорируемом конфиге тестового сервера.
Поток логов редактируется до сохранения; обнаружение токена всё равно считается
ошибкой, а не скрывается редактированием. Observer не возвращает произвольные
тексты исключений или содержимое команд. Конфиги тестового сервера не следует
копировать в публикуемые артефакты.

Observer ограничен 16 активными cases, 16 позициями на case и 4096 командами
за запуск. Чтения не загружают чанки; явная загрузка относится только к setup
и cleanup. Cleanup восстанавливает сохранённые BlockData и снимает только свои
удержания; это не откат генерации мира, block entities или scheduled ticks.
Поэтому мир остаётся одноразовым тестовым миром.

T08 не подтверждает всю матрицу V/D/N/F из
[PAPER_INTEGRATION_TEST_PLAN.ru.md](../docs/PAPER_INTEGRATION_TEST_PLAN.ru.md),
LAN класса, производительность группы, сохранение на диск или полную
совместимость mcpi. T09 проверяет полный успешный путь и две сессии;
T10 — ошибки и управляемые сбои. Исторические результаты T08 собраны отдельно
в [отчёте T08](../docs/reports/T08.ru.md).

T09: полный успешный путь и две сессии
------------------------------------

T09 использует production JAR, observer JAR и wheel T08 без изменения их
содержимого; копии артефактов этапа сохраняются в `dist/t09`. Сборка, установка
wheel, загрузка инструментов и подготовка существующего согласия EULA остаются
отдельными действиями. `tools/smoke_t09.py` ничего из этого не выполняет.

Для архивного wheel T09 сначала устанавливают именно выбранный файл в
интерпретатор клиентских процессов:

```powershell
.\.venv-t01-314\Scripts\python.exe -m pip install --no-deps --force-reinstall dist/t09/minebridge-0.1.0.dev0-py3-none-any.whl
.\.venv-tools\Scripts\python.exe tools/smoke_t09.py
```

Путь по умолчанию — `dist/t09/minebridge-0.1.0.dev0-py3-none-any.whl`. Для текущей
пересборки после сборки и установки из раздела выше задают wheel явно:

```powershell
.\.venv-tools\Scripts\python.exe tools/smoke_t09.py --wheel dist/dev/minebridge-0.1.0.dev0-py3-none-any.whl
```

Runner всегда выполняет два последовательных независимых прогона. Для каждого
создаётся новая папка `.work/t09-<runId>/server` и мир `t09-world` с тем же
фиксированным seed `20261021`, но новым фактическим UUID. Общий `Harness`
по умолчанию сохраняет поведение T08 (`t08-world`); только явно выбранный этап
T09 меняет имя мира и префиксы каталогов. Оба прогона T09 запускают один и тот же
production JAR с `-Dminebridge.testControl=true`. Проверка этого JAR без флага
остаётся отдельным сценарием T08.

Каждый прогон содержит 12 тестов, выполняемых в следующем порядке:

1. Самопроверка oracle из T08: независимое чтение двух значений, проверка
   неизвестного мира, восстановления блоков и снятия chunk tickets.
2. V01–V07: hello до возврата `create`, четыре допустимые формы блока через
   корневой и `blocks` API, повторная запись, floor и границы высоты, gate/ACK,
   последовательные записи, идемпотентный `close` и новое соединение.
3. D01–D04: одновременно READY два отдельных Python-процесса, независимые
   ответы при одинаковом `id=2`, запись в общую позицию с итогом по фактическому
   `applySequence`, закрытие удержанной сессии A с продолжающей работать B.

Клиенты по-прежнему импортируют установленный wheel в изолированных процессах
`python -I`. Независимый observer подтверждает содержимое мира; production trace
подтверждает поток setter и порядок `APPLY_DONE → ACK_ENQUEUED`. Gate и наблюдаемые
состояния обеспечивают барьеры с конечным deadline. Дополнительный pending-probe
проверяет состояние вызова внутри worker и возвращается по той же упорядоченной
stdout pipe, что результаты: задержка reader orchestrator не скрывает уже
завершённый вызов. В D04 используется разрешённый
планом вариант с публичным `close` ожидающего клиента: его результат `unknown`
сопоставляется с наблюдаемой серверной отменой до setter, после которой B снова
записывает блок по своему соединению.

Дополнительный `integration/tests/wire_tap.py` слушает только `127.0.0.1` на
выбранном ОС временном порту и пересылает соединения на production `4711`.
Он захватывает полные JSON/LF кадры, затем пересылает их исходные байты без
изменения. Поле `token` удаляется из сохранённого hello до создания события;
прочие вхождения секрета редактируются до сохранения. Событие связывает
`connectionId`, направление, последовательность и декодированный кадр.
Это позволяет сравнивать реальные wire-параметры двух вариантов API,
обнаруживать лишние запросы и сопоставлять ответы с сессией и requestId.
Capture ограничен 32 соединениями, 256 кадрами и размером кадра 65536 байт
без LF. Полный кадр буферизуется до пересылки, поэтому этот стенд не доказывает
поведение при фрагментации, задержках сети или backpressure; эти сценарии
относятся к N/F в T10.

Доказательства T09 и критерии успеха
----------------------------------

`.work/t09-paper-results.json` содержит последний сводный результат двух
прогонов. Каждый прогон сохраняется отдельно в
`integration/artifacts/t09-<runId>/`:

- `manifest.json`: артефакты и SHA-256, хеши исходников тестов, миры/порты,

- JSON-файлы отдельных клиентских процессов: события, stderr и код завершения.

Приёмка требует успешного завершения обоих прогонов: по 12 тестов без ошибок,

trace должен иметь droppedEvents=evictedEvents=0. Эти состояния входят в manifest.
Доказательства сохраняются и при неудаче; прошлые папки не переиспользуются.

Эти команды описывают воспроизводимую процедуру. Итоговые результаты и ссылки
на конкретные прогоны фиксируются отдельно в отчёте этапа. Даже успешная
матрица V/D не закрывает N01–N10, F01–F05, LAN класса или проверку нагрузки.

Runner сверяет все файлы `minebridge/` в `.venv-t10-314` с выбранным wheel,
SHA-256 закреплённого Paper и свободный `127.0.0.1:4711`. Он создаёт два разных
runId и два мира `t10-world` с seed `20261021` и разными фактическими UUID.
Первый мир повторно открывается только внутри F04; второй — для default-off.
В manifest фиксируются production/observer/wheel/Paper SHA и исходники runner,
всех `integration/tests/*.py`, Java production/observer и `server.properties`.
Их изменение во время приёмки или различие между двумя прогонами — ошибка.

Один вызов всегда выполняет следующие группы:

| Запуск и группа | Число тестов | Проверяемая часть |
| --- | ---: | --- |
| primary / vertical | 12 | oracle, V01–V07, D01–D04 |
| primary / validation | 6 | N01–N06 |
| primary / protocol | 8 | N07–N09, четыре ограниченных N10 subcases |
| primary / slow-reader | 1 | N10, реальный kernel backpressure |
| primary / faults | 4 | F01, F02, F03, F05 |
| primary / shutdown | 1 | F04, stop и restart сохранённого мира |
| repeat / vertical | 12 | oracle и все V/D на свежем мире |
| default-off | 1 | обычная запись и недоступность test-control |

Таким образом, основной suite содержит 32 теста; следующий — 12 и 1.
Всего стартуют четыре процесса Paper: primary, restart в F04, repeat и
default-off. F04 завершает primary внутри теста; последующий `finish()`
проверяет уже завершённый процесс. Оба мира работают с теми же артефактами.
N07 должен иметь ровно два результата, N10 — пять, остальные V/D/N/F — по
одному; runner проверяет именно эту полноту, а не только число успешных тестов.

Границы fault и transport проверок
----------------------------------

У каждой группы свой `WireTap`: он слушает временный loopback-порт и пересылает
реальные полные кадры на production `127.0.0.1:4711`. Это позволяет проверить
отсутствие ACK, лишних запросов и retry в публичных клиентах; token удаляется
до сохранения. Raw peers для фрагментации, повреждённых кадров и kernel
slow-reader идут напрямую на bridge: буферизация целого кадра в WireTap
не должна скрывать framing и backpressure реального reactor.

`FaultProxy` в F01/F03 принимает и удерживает настоящий ACK после записи в
Paper. Независимый observer и trace подтверждают применение, пока клиент
получает timeout или обрыв с `outcome=unknown`; последующая новая операция
проверяется отдельно, автоматического повтора нет. В F02 закрывается gated
сессия A и проверяется работа B. `ControlledPeer` в F05 намеренно выдаёт
синтетические ответы установленному клиенту; этот тест проверяет ошибки
клиента и отсутствие второго запроса, не доказывая изменение состояния Paper.

Kernel slow-reader уменьшает receive buffer до подключения и после hello
не читает socket, пока observer не подтвердит закрытие со стороны сервера.
Обычные небольшие ответы заполняют реальные TCP-буферы, без `writerPause`.
Нужно наблюдать pending output несколько Paper ticks, успешную операцию B
при ещё открытой медленной сессии, ограниченные очереди и последующее закрытие
с восстановлением capacity. Число запросов, observer-команд, объём чтения и
время ограничены. Отдельные управляемые output-тесты с `writerPause` проверяют
ровно восемь кадров до high-water, закрытие при девятом и writer deadline;
они дополняют, а не заменяют реальный socket-сценарий.

Trace имеет конечную историю. В T10 каждый case или проверяемая операция
начинается с checkpoint; текущий интервал обязан сохраняться полностью,
`droppedEvents` должен оставаться 0. Совокупный `evictedEvents` может расти,
когда вытесняются завершённые старые cases, особенно в kernel slow-reader.
Это не критерий провала, если сохранены доказательства ранних операций и
полный интервал текущей операции. Правило исторического T09
`droppedEvents=evictedEvents=0` не переносится на весь объём T10.

F04 останавливает Paper с двумя отдельными READY-клиентами и удержанными
запросами; оба вызова должны завершиться с `unknown`, без ACK и retry.
После restart на том же порту и мире сравниваются сохранённые исходные
BlockData всех позиций. Одна из них до setup заведомо не AIR, а перед stop
очищена: её восстановление подтверждает cleanup observer в `onDisable`.
Новая публичная сессия затем выполняет запись с независимым чтением результата.
На втором мире default-off проверяет тот же production JAR без включённого
test-control: обычная запись работает, gate и writer control отвечают
`CONTROL_DISABLED`.

Доказательства T10 и критерии приёмки
------------------------------------

Последняя сводка записывается в `.work/t10-paper-results.json`, а каждый run
сохраняется отдельно в `integration/artifacts/t10-<runId>/`:

- `manifest.json`: артефакты и исходники с SHA-256, миры, источник согласия
  EULA, группы, точное покрытие V/D/N/F, остановки и restart;
- `primary.log`, `restart.log`, `repeat.log`, `default-off.log`: логи
  соответствующих запусков Paper в каталоге своего run;
- `<group>-tests.log`, `<group>-wire.json`: результаты suite и отдельный
  capture каждой группы; у свежего повторения также группа `vertical`;
- `*-observer.json`, клиентские и fault JSON: снимки, checkpoints, trace,
  реальные/синтетические кадры с обозначением источника, stderr и exit code.

Успех требует `allPassed=true` в общей сводке и обоих manifest, полного
покрытия, ожидаемых 32/12/1 тестов без failures/errors/skipped, кодов завершения
Paper 0 и чистого освобождения сессий/capture-соединений. Хеши артефактов и
исходников должны совпадать, а runId и UUID свежих миров — различаться.
Сводка сохраняется и при неудаче; первые ошибки не превращаются в пропуски.
Фактические результаты конкретного запуска и SHA приведены
в [отчёте T10](../docs/reports/T10.ru.md).

IDE проверяется отдельно существующим `python/tests/ide/run.js` в настоящем
VS Code с Python/Pylance и `.venv-t10-314`, без старта Paper. Пользователь
исключил PyCharm из приёмки 22 октября 2026 года. Команды запуска и происхождение
portable VS Code 1.142.0 с проверкой опубликованного Microsoft SHA-256 приведены
в [DEVELOPMENT.ru.md](../docs/DEVELOPMENT.ru.md); профиль глобального IDE не меняется.
Полная локальная матрица не утверждает проверку LAN класса, массовой нагрузки,
общего сохранения мира на диск или полной совместимости mcpi.
