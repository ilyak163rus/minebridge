# Testing on a real Paper server

The integration fixtures check the installed Python library against a disposable
**Paper 26.2 build 133 / Java 25** server. They supplement the portable unit and
package tests in [CONTRIBUTING](../CONTRIBUTING.md).

Normal users need only the Minebridge plugin and Python package. Everything in
this directory is test infrastructure.

## Manual acceptance on a fresh server

Use a separate test server and world, with the same Minebridge JAR and wheel you
intend to distribute. Install them using the
[getting-started guide](../docs/en/GETTING_STARTED.md). The server operator must
review and accept the [Minecraft EULA](https://www.minecraft.net/en-us/eula).

For gameplay changes, verify:

1. Connect from Python, place a block, call `flush()`, and independently inspect
   the world in Minecraft. Check block properties as well as material.
2. Build a region across chunk boundaries, including unloaded chunks. Confirm
   the final coordinates, block count and states after acknowledgement.
3. Run two independent Python programs against that server at the same time.
   Bind each with `player="OnlineNick"` when testing `selector.SELF`. Give each
   player different items and positions, and check that results stay separate.
4. Keep one session active while the other builds a large region. Verify that
   both sessions can complete requests and receive their own results/errors.
5. Check the affected gameplay feature directly: real chat for event handlers,
   actual inventory slots, native effects, entity presence and world settings.
6. Test a rejected operation, then send a valid request over the same connection.
   For Peaceful spawning, a blocked hostile entity should raise
   `PeacefulSpawnError` without appearing in the world.
7. Close both Python sessions, then stop Paper normally. Check its log for
   unexpected exceptions, leaked connections or failed shutdown.

Measure completed operations with `flush()` or a result-returning call. Timing
only the buffered Python loop measures enqueueing rather than construction.
Report cold chunk generation separately from work in already loaded chunks.

## Independent observer

The separate [observer plugin](observer-plugin/README.md) reads Paper state
directly and writes immutable JSON snapshots requested through the server console.
It does not obtain expected results through Minebridge RPC. It also supplies
fixture setup and local test-control operations for deterministic failure tests.

Build it with the same Gradle wrapper:

```console
bash plugin/gradlew -p plugin :observer:jar --no-daemon --console=plain
```

On Windows use `plugin\gradlew.bat` instead. The output is
`integration/observer-plugin/build/libs/minebridge-observer-0.1.0-dev.jar`.
This JAR must never be bundled into the production plugin or installed on a
normal classroom/public server. Fixture clients use loopback and disposable
offline-mode player names; they are not an authentication example.

## Automated regression runner

`tools/smoke_v031.py` covers acknowledged region filling, modern block states,
physics, two independent installed SDK processes, two actual Minecraft protocol
connections, named player selection and Peaceful spawn errors. It also compares
region construction with the archived 0.3.0 release.

This runner currently retains **Windows-specific paths and historical fixture
requirements**. It is not a one-command setup for a fresh clone. It expects:

- `.tools/t02-toolchain.json`, generated by `tools/bootstrap_t02.py`; this helper
  downloads checksum-pinned Paper build 133, a Windows x64 JDK 25 and Gradle;
- an operator-created `.work/t02-server/eula.txt` containing `eula=true`, plus
  optional Paper bootstrap caches in that directory;
- a prebuilt observer JAR at the output path above;
- the 0.3.1 JAR/wheel in `dist/v0.3.1/` and archived 0.3.0 JAR/wheel in
  `dist/v0.3/`;
- matching installed wheels in `.venv-v031-314/Scripts/python.exe` and
  `.venv-v03-314/Scripts/python.exe`, respectively.

After those prerequisites are deliberately prepared, run from the repository
root:

```powershell
python -I tools/smoke_v031.py
```

The runner checks artifact bytes against the installed packages and starts only
its own new fixtures. It does not build/download/install artifacts or accept the
EULA. It writes logs/manifests under ignored `.work/` and
`integration/artifacts/`, shuts down its child processes and leaves the worlds
available for inspection. Do not point it at an existing server.

Other versioned runners are retained as regression infrastructure. Their setup
may depend on older local release artifacts; ordinary contributors can use the
manual matrix above and the portable unit/package checks without reconstructing
that history.

## Scope of evidence

An SDK acknowledgement confirms the server operation, not a disk save. Independent
observer readback and real connected players are needed for gameplay assertions.
The test clients have no rendering or movement simulation. A successful local
fixture does not establish performance on every machine, LAN, plugin combination
or server version. CI runs unit/package tests; native Paper acceptance remains a
separate check.
