События Minebridge 0.3 — обработчики, новые записи и история
==========================================================

Дополнение к [плану 0.3](IMPLEMENTATION_PLAN_V0_3.ru.md) от 26 октября 2026 года.
Это проект API; в поставке 0.2.1 этих методов ещё нет. Добавление запрошено
пользователем: чтение сообщений, ударов и выстрелов по образцу mcpi.

1. Три способа работы с одними игровыми фактами
---------------------------------------------

| Вход | Назначение | Что изменяет чтение |
|---|---|---|
| subscribe + run | Выполнить функцию при новом событии | Очередь соответствующей live-подписки |
| pollEvents / pollChatPosts и другие короткие методы | Забрать новые записи после прошлого запроса | Только pull-курсор этого типа в этом TCP-соединении |
| getRecent | Посмотреть последние записи доступной истории | Ничего: ни pull-курсоры, ни callbacks |

Обработчики и прямое чтение используют один источник снимков, но независимые
пути доставки. Запрос чата не забирает удары/выстрелы, не лишает событий
обработчик и не очищает данные другой программы.

Имена `pollChatPosts`, `pollBlockHits`, `pollProjectileHits` и `clearAll`
знакомы по mcpi. Сохраняем удобство цикла `for event in ...`, но не заявляем
полную бинарную/структурную совместимость со старой библиотекой.

2. Предлагаемый API
------------------

```python
from minebridge import Minecraft, events

mc = Minecraft.create("192.168.0.200", 4712)
try:
    for event in mc.events.pollChatPosts():
        print(event.player.name, event.message)

    for hit in mc.events.pollBlockHits():
        print(hit.player.name, hit.position, hit.action, hit.hand)

    for shot in mc.events.pollProjectileShots():
        print(shot.projectile, shot.shooter, shot.position)

    for hit in mc.events.pollProjectileHits():
        print(hit.projectile, hit.hitEntity, hit.hitBlock)

    for damage in mc.events.pollDamageEvents():
        print(damage.victim, damage.causingEntity, damage.finalDamage)

    # Повторный просмотр последних десяти сообщений, без сдвига poll-курсора.
    recent = mc.events.getRecent(events.CHAT_MESSAGE, limit=10)
finally:
    mc.close()
```

Для накопления событий отдельный run/subscribe не нужен: программа может
выполнять другую работу и периодически вызывать poll-методы. Такой скрипт
не начинает получать события до открытия соединения и не удерживается
бесконечно после окончания тела программы.

```text
mc.events.pollEvents(eventType, *, limit=100) -> EventBatch[TEvent]
mc.events.pollChatPosts(*, limit=100) -> EventBatch[ChatEvent]
mc.events.pollBlockHits(*, limit=100) -> EventBatch[BlockInteractEvent]
mc.events.pollEntityAttacks(*, limit=100) -> EventBatch[EntityAttackEvent]
mc.events.pollDamageEvents(*, limit=100) -> EventBatch[EntityDamageEvent]
mc.events.pollProjectileShots(*, limit=100) -> EventBatch[ProjectileShotEvent]
mc.events.pollProjectileHits(*, limit=100) -> EventBatch[ProjectileHitEvent]
mc.events.getRecent(eventType, *, limit=20) -> RecentEvents[TEvent]
mc.events.clearPending(eventType=None) -> None
mc.events.clearAll() -> None
```

Короткие poll-методы — обёртки над одним generic pollEvents. Новые блоки,
смерти и прочие типы читаются, например, `pollEvents(events.BLOCK_BREAK)`;
отдельный метод на каждую константу не обязателен.

EventBatch — неизменяемая Sequence: поддерживает for/len/индексирование.
Также содержит hasMore, nextCursor и границы прочитанного интервала.
limit — максимум записей, не обещание одного полного кадра: из-за byte-budget
batch может быть короче limit и иметь hasMore=True. Следующий poll продолжает
с подтверждённой позиции, без пропуска остатка.
Каждый запрос фиксирует верхнюю границу журнала при старте: новые записи
остаются следующему poll. Поиск редкого типа не догоняет бесконечно растущий tail.

RecentEvents тоже поддерживает for/len/индексирование, содержит границы
доступной истории и признак ограниченного окна. Возвращает до limit последних
подходящих записей, упорядоченных от старых к новым. Для большого ответа SDK
читает внутренние страницы с зафиксированной верхней границей, не меняя
основной poll-курсор. Если нужные страницы уже вытеснены, частичный результат
не выдаётся за полный успешный ответ.

Во всех методах limit — целое 1..1000, не bool. Точные byte-budgets и верхний
предел после измерений фиксируются в контракте I02. Сокращение длинного текста
снимка обозначается truncated; переносы и Unicode не меняют NDJSON framing.

3. Когда начинается сбор и что означает «последние»
-------------------------------------------------

Начальная позиция pull-чтения — конец журнала при успешном hello. Поэтому
первый poll возвращает накопленное **после create**, а не только произошедшее
после первого poll. При очень долгой паузе доступность ограничена retention.
Это порядок фиксации снимков в журнале, не точная граница времени получения
асинхронного сетевого пакета чата; этот нюанс также относится к serverTick.

getRecent тоже ограничен началом данной TCP-сессии: не читает сообщения до
подключения, серверный logs/latest.log и события предыдущего запуска Python.
Это небольшой журнал в RAM, не долговременный аудит и не автоматический replay
обработчиков. Повторный getRecent видит те же записи, пока они ещё хранятся.

Чтобы первый poll ничего не пропустил, плагин записывает поддерживаемые native
события, пока в соответствующем мире есть хотя бы одна ready bridge-сессия
или активная live-подписка этого мира. Monitor лавы активен по той же причине,
а не только после subscribe. Это необходимое дополнение прежнего ленивого
монитора: одних обработчиков уже недостаточно для истории до первого poll.

Нынешний hello не сообщает серверу, какую версию Python использует клиент.
Поэтому не вводим обязательное поле «event-capable клиент» и не полагаемся
на такую классификацию. Дополнительные metadata в ответе hello сообщают
serverEpoch, начальную границу и лимиты журнала; старые request-поля сохранены.

Ориентир для проверки: отдельный журнал каждого активного мира, ограниченный
одновременно 4096 записями, 4 МиБ и 120 игровыми секундами (2400 тиков).
Первый сработавший лимит вытесняет старые записи. Это **предлагаемые пределы**,
не обещание сохранить все две минуты при любой нагрузке. Финальные значения
и предел размера одного снимка определяются в I02 на закреплённом Paper.

4. Курсоры, потеря истории и совместное использование
---------------------------------------------------

- Один внутренний pull-курсор на тип события и TCP-соединение. pollChatPosts
  и pollEvents(CHAT_MESSAGE) используют один курсор. withContext разделяет
  его с исходным фасадом, как общий транспорт. Другое подключение независимо.
- Pull-вызовы одного типа сериализуются вокруг запроса и обновления курсора;
  два потока не должны прочитать один старый cursor одновременно. Сам журнал
  чтением не удаляется.
- Курсор хранится на клиенте и обновляется только после успешного разбора
  ответа. Серверное чтение не выполняет скрытый destructive pop. Автоматического
  retry после обрыва нет; nextCursor в ответе описывает прочитанный диапазон.
- При обычной ротации ring-buffer видимая потеря соответствующего типа даёт
  EventHistoryLostError с границами/доступной позицией. Типизированные watermarks
  нужны, чтобы большой поток других типов не выдавался за потерю чата.
  Курсор сам не перескакивает вперёд.
- clearPending(type) явно переводит только этот pull-курсор на текущий tail;
  clearPending() — все pull-курсоры соединения. clearAll — совместимый по имени
  alias clearPending(), а не удаление общего журнала. Эти операции не трогают
  live callbacks, getRecent и другие программы.
  Сбрасываются также типы, которые ещё ни разу не читались: они не возвращаются
  к старому hello-tail при первом запросе после clearAll.
- EventHistoryLostError не делает live-подписки BROKEN. Ранее описанный
  EventOverflowError относится к потерям live-очереди; это разные ситуации.
- Старый запрет двух consumers относится только к live events.run/events.poll.
  pollEvents/pollChatPosts/getRecent допустимы в обработчике и одновременно
  с run: они не читают его очередь. Но если обработчик сам читает историю,
  он может намеренно повторно увидеть свой eventId — автоматической дедупликации
  между независимыми путями нет.

В первой версии прямые poll-методы читают выбранный тип в мире сессии;
не вводим меняющиеся selector-фильтры одного общего курсора. В Python можно
отфильтровать полученные snapshots. Отдельные EventReader с независимыми
курсорами/фильтрами — дальнейшее дополнение, если понадобится несколько
независимых readers внутри одного подключения.

Потеря возможна ещё до записи в ring, например при переполнении async chat
ingress. Одного sequence для этого недостаточно: нужен отдельный capture-loss
watermark/маркер по затронутым типам и интервалам. Poll через такой интервал
даёт `EventHistoryLostError`, даже если сохранённые
sequence идут без разрыва. getRecent также сообщает ошибку при потерях внутри
его окна; нельзя выдавать неполный ответ как полный. Отдельно проверяется
ingress overflow без единой live-подписки, когда работают только pull-читатели.
Причина `capture-overflow` передаётся в необязательных данных wire-ошибки;
публичный Python-класс не предоставляет атрибут `reason`. В программе
перехватывайте `EventHistoryLostError`; его `code` идентифицирует ошибку.

5. Какие события действительно полезны
-------------------------------------

В основной набор 0.3 включаем:

| Тип | Что можно узнать | Задачи |
|---|---|---|
| CHAT_MESSAGE | Кто, что написал, тик/мир | Чат-команды, викторины, ответы учеников |
| BLOCK_INTERACT, alias BLOCK_HIT | Кто кликнул блок, позиция/тип/грань, левая/правая кнопка, рука, тип предмета | Выбор точек, инструменты строительства, кнопки/рычаги |
| ENTITY_ATTACK | Игрок, цель, willAttack, cancelled | Попытки атаки/выбор тренировочной цели до расчёта урона |
| ENTITY_DAMAGE | Жертва, прямой источник, вызывающая сущность, причина, raw/finalDamage | PvP/PvE, очки за урон, опасные зоны |
| PLAYER_DAMAGE | Типизированное представление ENTITY_DAMAGE с жертвой-игроком | Лава/падение/удар по игроку |
| PROJECTILE_SHOT | UUID/тип снаряда, стрелок/блок-источник, позиция/скорость | Количество выпущенных стрел/снежков, начало траектории |
| PROJECTILE_HIT | Тот же UUID снаряда, цель-сущность/блок, грань, положение снаряда | Тир, попадания по мишеням |
| BLOCK_BREAK / BLOCK_PLACE | Кто и какой блок сломал/поставил, позиция и снимки | Стройка, задания, сбор ресурсов |
| PLAYER_ENTER_LAVA | Кто и где впервые оказался в контакте | Спасение, штраф, испытания |
| PLAYER_JOIN / PLAYER_QUIT | UUID и имя игрока | Подготовка/очистка раунда |
| PLAYER_DEATH / PLAYER_RESPAWN | Игрок, reason/respawnLocation и данные жизненного цикла | Число жизней, возрождение/переход с причиной |

Для нескольких следующих адаптеров есть высокая практическая ценность,
но они не становятся обязательной частью 0.3 этим списком:

| Следующие типы | Пример |
|---|---|
| ITEM_PICKUP / ITEM_DROP | Собрать десять алмазов, сдать предмет |
| PLAYER_INTERACT_ENTITY / ITEM_CONSUME | Диалог с NPC, применение/съедание предмета |
| INVENTORY_OPEN / INVENTORY_CLOSE | Открыть сундук с загадкой |
| PLAYER_CHANGE_WORLD / PLAYER_TELEPORT | Порталы и точки маршрута |
| PLAYER_ENTER_REGION / PLAYER_LEAVE_REGION | Контрольные точки, арены |
| ENTITY_DEATH | Награды за мобов |
| REDSTONE_CHANGE | Датчики и логические схемы |

GUI clicks/сложные inventory transactions, все перемещения каждый тик,
произвольные plugin-события и долговременная история остаются отдельными задачами.

6. Удары, выстрелы и попадания: обязательные различия
--------------------------------------------------

Клик по блоку не означает разрушение, попытка атаки не доказывает урон,
запуск снаряда не означает попадание. ProjectileHit не доказывает потерю HP.
Эти факты имеют разные типы; не добавляем общий неопределённый pollHits().

**Block hits.** Канонический BLOCK_INTERACT охватывает LEFT_CLICK_BLOCK и
RIGHT_CLICK_BLOCK. BLOCK_HIT и pollBlockHits — удобные имена для этого же типа,
без нового источника/очереди. В Minebridge это расширенный аналог: не только
мечи и не только правая кнопка. В RaspberryJuice старый listener фильтровал
мечи и hitclick LEFT/RIGHT/BOTH. Для прежнего поведения пользователь проверяет
action/тип предмета в снимке. Воздух/PHYSICAL не входят в этот тип.

У PlayerInteractEvent возможны отдельные уведомления двух рук и два результата
использования — useInteractedBlock/useItemInHand. Vanilla no-op тоже может
иметь cancelled-состояние. Поэтому block-interaction фиксируется как попытка
взаимодействия вместе со статусами; blanket ignoreCancelled не применяется.
Не удаляем «дубликаты» по эвристике «один игрок/блок/тик».

**Attack/damage.** ENTITY_ATTACK отражает намерение игрока; willAttack=true
не гарантирует итог. Для урона сохраняем victim, directSource и causingEntity:
при попадании стрелой это разные ссылки. finalDamage — вычисленное значение
в фазе наблюдения, а не обещание точного уменьшения HP после всех последствий.
PLAYER_DAMAGE — проекция того же canonical damage fact с тем же eventId.
Если подписаться на обе проекции, две доставки ожидаемы, не два физических удара.

**Shots.** PROJECTILE_SHOT — один принятый запуск конкретного UUID снаряда.
Для bow/crossbow событие EntityShootBowEvent может дать weapon/hand/force,
но не создаёт второй выстрел поверх ProjectileLaunchEvent. Multishot может
создать несколько снарядов: не обещаем один факт на нажатие кнопки.
Correlation и порядок событий отдельно проверяем на Paper. Для других типов
не выдумываем weapon/force, если этих данных нет.

Стрелок бывает игроком, мобом, блоком-раздатчиком или неизвестным. Снимок
допускает shooter=None и sourceBlock; неизвестный стрелок никогда не равен SELF.
PROJECTILE_HIT сохраняет nullable hitEntity/hitBlock/hitFace. position означает
положение снаряда при наблюдении, не обещанную точную точку геометрического
пересечения. Пронизывающая стрела может иметь несколько попаданий с одним UUID;
запуск и повреждения тоже связываются UUID/ссылками, а не ближайшим игроком.

Попытки ENTITY_ATTACK, BLOCK_INTERACT и контакт PROJECTILE_HIT сохраняют
наблюдаемые признаки отмены. Для результативных chat/break/place/damage/launch
в 0.3 по умолчанию доставляются неотменённые действия. Политика одинакова
для журнала и live-доставки данного типа, без общего неверного ignoreCancelled.

Для новых типов live subscribe допускает players=None — без player-фильтра,
например, для выстрелов раздатчика/моба. При players=... блок/attack/chat
сопоставляются с актором, damage — с жертвой-игроком, projectile — со стрелком-
игроком. Это задаётся по типу; неизвестный актор не угадывается. Для более
сложного сопоставления можно использовать players=None и поля snapshot в Python.
Например, `subscribe(events.ENTITY_DAMAGE, on_damage, players=None)` включает
жертв-мобов. Default ALL_PLAYERS у этой подписки ограничен жертвами-игроками,
тогда как прямой pollDamageEvents читает все доступные damage facts мира.
PLAYER_RESPAWN не ограничен смертью: API133 содержит причины DEATH/END_PORTAL/PLUGIN;
respawnLocation — место, выбранное в наблюдаемом событии, а не доказательство,
что игрок уже завершил перемещение.

7. Общая запись и транспорт
-------------------------

В журнале хранится canonical EventRecord: serverEpoch, уникальный eventId (UUID),
монотонный sequence данного мира, eventType, serverTick, UUID мира и неизменяемые данные типа.
subscriptionId не является частью игрового факта. Live-доставка оборачивает
его в subscriptionId + deliverySequence. Journal reads возвращают те же eventId.
Алиасы/projections не должны создавать второй физический факт.
В публичном снимке sequence всегда означает позицию в журнале, независимо
от способа чтения. subscriptionId/deliverySequence — отдельные необязательные
metadata live-доставки, не перегружающие смысл sequence у poll-события.

Журнал общий для мира, но читательские позиции принадлежат подключениям.
Snapshots формируются на игровом потоке; async chat сначала проходит bounded
ingress. Журнал и очередь live-подписки независимы и ограничены. Новые RPC
events.pollEvents/getRecent/clearPending не требуют второго сокета или reader.
Idle reader без pending RPC не получает journal frames самопроизвольно.
Чтения имеют byte-budget и ограниченный объём работы за тик; большой scan/
сбор нескольких страниц не выполняется одним неограниченным проходом на
главном потоке. Синхронный Python-вызов может ждать внутренних job/progress,
как уже существующие операции с блоками.

Capabilities: отдельно для live subscribe и для pull/history; старый клиент
не получает неизвестных уведомлений. Новый Python на старом плагине выдаёт
UnsupportedFeatureError до запроса неподдержанного метода.

I03: добавить block interaction/attack/damage/projectile/respawn adapters,

Проверить реальные левый/правый клики двумя руками, атаку без урона,

неизвестного/неигрового стрелка и отменённые контакты. Наличие API подтверждено,
всё перечисленное runtime-поведение пока предмет приёмки, а не установленный факт.

I05: два игровых клиента и два Python-процесса читают один факт независимо;
poll чата не съедает выстрелы; getRecent не очищает unread; clearAll одной
программы не влияет на другую/обработчики. Вытеснение ring и live overflow
проверяются отдельно; ни один поток не вытесняет ACK обычных мутаций.
Высокочастотные записи не увеличивают RAM без предела и не дают регрессии
обычной буферизированной установки блоков без активных callbacks.

Пять итераций и одна итоговая поставка сохраняются. Код реализации этим
дополнением не добавляется.

Источники и проверенные основания
--------------------------------

Локальный API133 через javap подтверждает PlayerInteractEvent, PrePlayerAttackEntityEvent,
EntityShootBowEvent, ProjectileLaunch/Hit, DamageSource direct/causing entity,
getFinalDamage и player lifecycle. Веб-Javadoc `/26.2` сейчас build134;
он не подменяет локальную проверку133 и будущие игровые тесты.

- Попытка атаки: [PrePlayerAttackEntityEvent](https://jd.papermc.io/paper/26.2/io/papermc/paper/event/player/PrePlayerAttackEntityEvent.html).
- Выстрел/контакт: [EntityShootBowEvent](https://jd.papermc.io/paper/26.2/org/bukkit/event/entity/EntityShootBowEvent.html), [ProjectileHitEvent](https://jd.papermc.io/paper/26.2/org/bukkit/event/entity/ProjectileHitEvent.html).
