цели и порядок реализации. На момент подготовки плана его методы ещё

проверенная 0.2.1, [контракт 0.2](contracts/V0_2_CONTRACT.ru.md),
[отчёт исправления](reports/V0_2_1.ru.md) и

проверена на Paper с двумя Python-процессами и двумя игровыми подключениями,
новым миром и старым клиентом. [Отчёт I05](reports/V0_3_I05.ru.md),
[поставка](../dist/v0.3/README.ru.md), [доступный API](API_V0_3.ru.md).

в их результатах — история. Файлы 0.2/0.2.1 сохранены отдельно.

Сохраняем Paper 26.2 build 133 / Java 25 / Python 3.11+, два позиционных
параметра create, отсутствие обязательных token/world, buffered по умолчанию,
нормальный выход Python с ожиданием записей, logging=False и существующий API.
Новые возможности требуют расширения **и библиотеки, и плагина**; исключение —
тонкие Python-алиасы и удобная позиционная форма уже существующих методов.

1. Границы версии
-----------------

Обязательный набор по запросу:

- прикрепить Python-функцию к чату, ломанию блока и входу игрока в лаву;
- читать накопленные сообщения, удары, выстрелы и попадания знакомыми poll-методами;
- читать/записывать конкретные слоты сундука и инвентаря онлайн-игрока;
- менять игровой режим игроков по селектору;
- `mc.setPos(targets, x, y, z)` по селектору;
- разрешить позиционные числовые аргументы `effects.add`.

Дополнения, которые предлагается включить в ту же версию:

- события установки блока, входа/выхода игрока, смерти и урона;
- чтение содержимого и очистка выбранного слота/инвентаря;
- время, погода и типизированные gamerules выбранного мира;
- снятие эффектов, здоровье и сытость игроков для завершения/перезапуска игр;
- публичная информация о подключении/возможностях и `with Minecraft.create(...)`.

Пока не включаем: синхронную отмену игрового события из Python, декларативные
серверные правила, непрерывный поток PLAYER_MOVE, фоновые/asyncio callbacks,
декораторы как второй обязательный способ подписки, долговременный replay событий,
GUI-меню, печи/варку, офлайн-инвентари, произвольные NBT/компоненты, lossless
копирование/перенос предметов, scoreboard, title/actionbar и новые платформы.
Scoreboard и экранный UI остаются подходящими следующими отдельными областями.

2. Удобные изменения существующего API
------------------------------------

Позиционные эффекты
~~~~~~~~~~~~~~~~~~

Согласованная сигнатура сохраняет текущий порядок duration → level:

```text
mc.effects.add(targets, effect, duration, level=1, *, particles=True)
```

```python
# Согласовано: 100 игровых секунд, уровень 200.
mc.effects.add(selector.SELF, effects.SPEED, 100, 200)

# Старые программы продолжают работать.
mc.effects.add(selector.SELF, effects.SPEED, duration=30, level=100)
```

Пользователь подтвердил порядок 26 октября 2026 года: **сначала длительность
в секундах, затем уровень**. Имена duration/level и старые вызовы с именованными
аргументами сохраняются. Угадывание порядка по величине числа не вводится.
Длительность остаётся в игровых секундах, level=1 — первый уровень; существующий
диапазон 1..256 не меняется. Пример не означает level=amplifier.

Позиция и игровой режим
~~~~~~~~~~~~~~~~~~~~~~

```python
from minebridge import Minecraft, selector, gamemode

mc = Minecraft.create("192.168.0.200", 4712, player="CurrentNick")
mc.setPos(selector.SELF, 10, 80, 10)
mc.setPos(selector.ALL_PLAYERS, 0.5, 90, 0.5)
mc.players.setGameMode(selector.ALL_PLAYERS, gamemode.ADVENTURE)
```

`mc.setPos(targets,x,y,z,*,world=None)` и `mc.players.setPos(...)` — алиасы
существующего `mc.players.teleport`, без второго движка телепортации.
Старый teleport остаётся. Селектор первый; перегрузку с неявным SELF по трём
числам не добавляем. Дроби, загрузка чанков, TargetResult и явный контекст SELF
сохраняются. Координаты никого не привязывают к прошлому компьютеру/нику.

`mc.players.setGameMode(targets, mode) -> TargetResult` принимает типизированные
`gamemode.SURVIVAL/CREATIVE/ADVENTURE/SPECTATOR`. `getGameMode(target)` читает
ровно одного игрока. Весь набор целей проверяется до изменений. После setter
проверяется фактический режим: void-метод Paper сам по себе не доказывает успех
при вмешательстве другого плагина.

3. Слоты и контейнеры
--------------------

Сохраняем уже предусмотренную службу `mc.inventories`, не добавляя параллельные
`mc.inventory`/`mc.containers` с другими правилами.

```python
from minebridge import items, selector, slots

chest = mc.inventories.ofBlock(10, 64, 10)
chest.setItem(0, items.DIAMOND, 16)
print(chest.getItem(0))
print(chest.getContents())
chest.clear(0)

inventory = mc.inventories.ofPlayer(selector.SELF)
inventory.setItem(0, items.IRON_SWORD, 1)
inventory.setItem(slots.OFF_HAND, items.SHIELD, 1)

# Массовый удобный вход: тот же серверный сервис точного слота.
mc.players.setItem(selector.ALL_PLAYERS, 0, items.COMPASS, 1)
```

Предлагаемые входы:

```text
mc.inventories.ofBlock(x,y,z,*,world=None,combined=False) -> InventoryRef
mc.inventories.ofPlayer(target) -> InventoryRef
inventory.getItem(slot) -> ItemView | None
inventory.getContents() -> dict[Slot, ItemView | None]
inventory.setItem(slot,item,amount=None) -> SlotWriteResult
inventory.clear(slot=None) -> InventoryUpdateResult
mc.players.setItem(targets,slot,item,amount=None) -> TargetResult
```

Классы возвращаемых результатов закрепляются до I04: SlotWriteResult описывает
применение, слот и read-only вид прежнего/нового содержимого;
InventoryUpdateResult — применение и затронутые слоты. Bulk-метод возвращает
компактный результат по UUID, без огромных копий всех инвентарей.
Свойства InventoryRef — локальные метаданные, а не скрытые сетевые чтения.

Семь правил, обязательных до реализации:

1. **Точный слот — замена.** setItem заменяет прежний стек; не складывает,
   не ищет свободное место, не выбрасывает остатки. amount положительное,
   не больше настоящего максимума предмета и выбранного inventory. Например,
   64 меча в одном слоте — ошибка до изменения. `giveItem` сохраняет прежнюю
   семантику распределения/остатков; amount=0 не используется для очистки.
2. **Пустой слот — None.** Очистка имеет отдельный clear. getContents возвращает
   также пустые слоты, чтобы номера не сдвигались. У игрока clear() очищает
   только публичные слоты 0..35 и armor/offhand; скрытые BODY/SADDLE не затрагивает.
3. **Игрок — только онлайн.** ofPlayer разрешает ровно одного: ноль или несколько
   — ошибка. Ссылка закреплена за UUID, а не за runtime ID/номером компьютера.
   Для группы предназначен players.setItem; исходный селектор разрешается один
   раз, цели предвалидируются, дальнейший частичный результат не обещает rollback.
4. **Нумерация игрока.** В 0.3 поддерживаем storage 0..35, из них хотбар 0..8.
   Броня и вторая рука — `slots.HEAD/CHEST/LEGS/FEET/OFF_HAND`.
   getContents включает эти публичные ключи. Точный состав/порядок публичных
   ключей возвращается в метаданных ссылки; не приравниваем его к полному
   внутреннему PlayerInventory Paper. BODY/SADDLE и сетевые window slot IDs
   не входят в 0.3. Все константы доступны IDE без подключения.
5. **Сундук.** Поддерживаем обычный и trapped chest. По умолчанию адресуем
   физическую половину на 27 слотов, даже если рядом есть вторая.
   `combined=True` разрешает общий сундук на 54 слота и возвращает size и
   отображение диапазонов на координаты половин. Порядок задаётся контрактом
   по серверным половинам, а не направлением взгляда ученика. У одиночного
   сундука combined=True по-прежнему даёт 27 слотов.
6. **Актуальность.** Каждый RPC загружает нужные чанки через ChunkService и
   заново проверяет тип/схему inventory. Если объединённый сундук разделён или
   перестроен с другим layout, старая ссылка получает InventoryChangedError.
   Ссылка на блок адресует текущий подходящий контейнер по UUID мира/координатам;
   вечную идентичность удалённого и повторно поставленного сундука не обещаем.
7. **Чтение сложных предметов.** Текущий ItemStack описывает только material,
   amount, name, lore. Для произвольного существующего предмета возвращаем
   отдельный неизменяемый ItemView с известными полями и hasAdditionalData;
   при сокращении текста это также явно обозначено. ItemView не принимается
   setter как полный предмет. Поэтому get→set не обещает сохранения зачарований,
   содержимого шалкера и прочих компонентов. Lossless copy/move проектируется
   отдельно; на 0.3 не добавляем неограниченный opaque NBT в транспорт.

Все инвентарные операции ждут результата в обоих writeMode и являются барьером
предыдущих записей. Изменение занятого слота/clear — прямое действие указанного
метода, без дополнительных подтверждений в пользовательском API.

getContents может не поместиться в один кадр 64 КиБ даже для 54 слотов:
внутри читаем страницами с ограничением по байтам, оставляя пользователю один
словарь. Каждый ItemView имеет ограниченный размер и явный truncated при
сокращении; то же правило действует для previous/current в SlotWriteResult.
Это не атомарный снимок против действий игроков/воронок между страницами.
При обнаруженной смене layout не возвращаем частичный словарь как полный успех.

4. События: обработчики и чтение
------------------------------

Дополнение пользователя: нужны также запросы последних сообщений, ударов и
выстрелов. Подробный [дизайн событий и истории](EVENTS_V0_3.ru.md) фиксирует
каталог, курсоры, ограничения RAM и различия попытки атаки/урона/попадания.

```python
for message in mc.events.pollChatPosts():
    print(message.player.name, message.message)

shots = mc.events.pollProjectileShots()
hits = mc.events.pollProjectileHits()
recent = mc.events.getRecent(events.CHAT_MESSAGE, limit=10)
```

poll-обёртки читают новые записи по отдельному курсору типа/соединения;
getRecent повторно смотрит историю, не сдвигая его. История начинается при
успешном create и ограничена RAM-окном. Эти чтения не отнимают события у
callbacks/другого ученика; подписка для них не нужна. История до подключения
и чтение старых server logs в 0.3 не входят.

Основной учебный синтаксис
~~~~~~~~~~~~~~~~~~~~~~~~~

```python
from minebridge import Minecraft, events, items

mc = Minecraft.create("192.168.0.200", 4712)

def on_chat(event):
    if event.message == "награда":
        mc.players.giveItem(event.player, items.EMERALD, 1)

def on_lava(event):
    mc.setPos(event.player, 0, 90, 0)

def on_break(event):
    mc.postToChat(f"{event.player.name} сломал {event.block.key}")

mc.events.subscribe(events.CHAT_MESSAGE, on_chat)
mc.events.subscribe(events.PLAYER_ENTER_LAVA, on_lava)
mc.events.subscribe(events.BLOCK_BREAK, on_break)

try:
    mc.events.run()
finally:
    mc.close()
```

`subscribe` прикрепляет функцию к событию. Функция остаётся в Python, её код
не отправляется в Java. `run()` явно удерживает программу и вызывает функции;
одна подписка без run не превращает скрипт в бессрочный процесс. `close()`
и автоматический нормальный выход 0.2.1 не запускают callbacks сами.

API и модель исполнения
~~~~~~~~~~~~~~~~~~~~~~

```text
mc.events.subscribe(eventType,handler=None,*,players=selector.ALL_PLAYERS,
                    world=None,region=None,blocks=None) -> Subscription
subscription.unsubscribe() -> None
mc.events.run() -> None
mc.events.poll(timeout=0.0) -> Event | None
mc.events.stop() -> None
```

- run вызывает обработчики последовательно в вызывающем потоке. Сетевой reader
  только декодирует ответы/уведомления и кладёт снимки в очередь. Поэтому
  синхронные giveItem/getBlock/setPos внутри обработчика не создают deadlock.
- Один consumer live-очереди на соединение: run и poll нельзя выполнять одновременно.
  poll возвращает один снимок, не вызывает handler; timeout=0 — без ожидания,
  None — ждать до события/stop/disconnect. Для ручного poll допустим handler=None;
  run требует обработчиков у активных подписок и сообщает об их отсутствии.
  Это ограничение не относится к pollEvents/pollChatPosts/getRecent: они читают
  журнал отдельным курсором и допустимы одновременно с run/внутри callback.
- Исключение обработчика выходит из run обычным исключением. Оно не скрывается
  в daemon-потоке и не останавливает Paper или чужие сессии. Пользователь
  выбирает try/except/finally; автоматический бесконечный перезапуск не вводится.
- stop будит ожидающий run/poll и останавливает dispatch после текущего вызова,
  сохраняя соединение и подписки. Зависшую пользовательскую функцию stop
  принудительно прервать не может. close останавливает dispatch, освобождает
  подписки и ожидает принятые записи. flush ожидает RPC, а не весь будущий поток
  событий/обработчиков. При разрыве run/poll просыпаются с ConnectionError.
- Обработчик получает типизированный неизменяемый snapshot: subscriptionId,
  deliverySequence, общий eventId/sequence, serverTick, мир и данные типа события.
  sequence — позиция в журнале; deliverySequence — отдельный счётчик подписки.
  Это не живая Java-ссылка.
  События могут устареть до обработки. `event.player` — актор события;
  selector.SELF автоматически не переключается на него.
- `.withContext(...)` сохраняет одну общую очередь/dispatcher соединения;
  контекст конкретной подписки фиксируется при её создании. Закрытие любого
  фасада закрывает всё общее соединение, как в 0.2.
  run/poll/stop на любом фасаде обслуживают/останавливают все подписки этого
  соединения; контекст подписки задаёт фильтры, не создаёт отдельный consumer.

События 0.3
~~~~~~~~~~~

| Константа | Минимальные данные | Уточнение |
|---|---|---|
| CHAT_MESSAGE | player, message, cancelled | Сообщение игрока; plain text, без Promise финального вида для каждого зрителя |
| BLOCK_BREAK | player, position, block, cancelled | BlockSpec до ломания, наблюдаемое действие игрока |
| PLAYER_ENTER_LAVA | player, position | Один наблюдаемый вход в контакт с лавой |
| BLOCK_PLACE | player, position, block, replacedBlock, cancelled | Поставленный блок и прежний снимок |
| PLAYER_JOIN | player | Вход онлайн-игрока после регистрации подписки |
| PLAYER_QUIT | player | Выход; актор уже может быть недоступен для команды |
| PLAYER_DEATH | player, position | Смерть игрока, без изменения drops через Python |
| PLAYER_DAMAGE | player, cause, rawDamage, finalDamage, cancelled | Проекция урона с жертвой-игроком |
| BLOCK_INTERACT / BLOCK_HIT | player, position, block, face, action, hand, use-results | Клик по блоку; BLOCK_HIT — alias расширенного аналога mcpi |
| ENTITY_ATTACK | player, target, willAttack, cancelled | Попытка атаки, без обещания урона |
| ENTITY_DAMAGE | victim, directSource, causingEntity, raw/finalDamage | Канонический факт урона; PLAYER_DAMAGE — проекция с тем же eventId |
| PROJECTILE_SHOT | projectile, shooter/sourceBlock, position, velocity | Один запуск снаряда, не одно нажатие кнопки |
| PROJECTILE_HIT | projectile, shooter, hitBlock/hitEntity, hitFace | Контакт снаряда, отдельно от damage |
| PLAYER_RESPAWN | player, reason, respawnLocation | Возрождение/переход с причиной, не только смерть |

Статические `EventType[TEvent]` и классы ChatEvent/BlockBreakEvent/LavaEnterEvent
и других снимков дают подсказки handler-параметрам. Причины урона — отдельный
типизированный каталог damageCause, экспортированный из закреплённого Paper.
Не обещаем свойства .block/.message/.player для всех событий одного нетипизированного
dict: у снаряда стрелок может быть мобом, раздатчиком или неизвестным.

Фильтры
~~~~~~~

Фильтруем в плагине до передачи. world=None означает UUID мира сессии;
остальные фильтры пересекаются с выбранным миром. Это не меняет глобальный
смысл @a в существующих командах игроков.

В первой версии players принимает ALL_PLAYERS (динамически, включая новых
игроков), SELF (UUID явно связанного игрока) либо явный ник/UUID/PlayerRef/список
ссылок. Ник разрешается при подписке; после этого сравнивается UUID.
Произвольные @r/@p/сложные селекторы в подписках пока отклоняются: их динамическая
семантика отличается от однократного разрешения цели обычной команды.
Такое ограничение не касается существующих setPos/giveItem/эффектов и прочих RPC.

region — типизированный Region с UUID мира и включёнными границами,
blocks — BlockSpec/константы или список типов, только для block-событий.
Сравнение блока по key; состояния фильтруются отдельно после снимка в Python.
Неприменимый фильтр — ошибка подписки, а не игнорируемая опция.
Для результативных действий отменённые события по умолчанию не доставляются.
Для попыток/контактов BLOCK_INTERACT, ENTITY_ATTACK, PROJECTILE_HIT сохраняются
наблюдаемые статусы: blanket ignoreCancelled здесь неверен, vanilla no-op
взаимодействие тоже может иметь cancelled. Данные/правила заданы по типу в
[дополнении](EVENTS_V0_3.ru.md). Новые типы поддерживают players=None для
наблюдения неигровых источников без player-фильтра.

Важные игровые различия
~~~~~~~~~~~~~~~~~~~~~~

**Лава.** Рекомендуется общий монитор `Entity.isInLava()` один раз за игровой
тик для нужных игроков, пока есть ready-сессия/подписка соответствующего мира:
историю нужно начать до первого poll, а не только после subscribe.
Событие создаётся на переходе
false→true, без повтора за каждый тик пребывания. Это отдельно от LAVA damage:
creative/fire resistance не должны отключать обнаружение входа. Проверяется
контакт сущности, не только блок под ногами. При новой подписке уже стоящий
в лаве игрок становится исходным состоянием без искусственного входа.
Уход/возврат даёт новый вход; новая мировая область после телепорта/respawn —
новый контакт, если текущий контакт подтверждён монитором. Join/quit/death
очищают соответствующее состояние; после смерти игрок исключён из sampling
до respawn. Новая подписка имеет собственный baseline/момент активации и
не сбрасывает историю контактов существующих подписок. Состояние, возникшее и исчезнувшее целиком
между двумя наблюдениями, sampling обнаружить не обещает. Это проект алгоритма,
ещё не проверенное поведение будущего адаптера.

**Чат.** AsyncChatEvent может приходить вне игрового потока. Listener копирует
текст/статус и безопасную идентичность в ограниченный ingress; Paper-мир,
позиции и цели разрешаются на игровом потоке. Не переносим живой Event в Python
и не читаем произвольное игровое состояние из async listener. Для чата
serverTick/мир относятся к нормализации на игровом потоке; точную позицию
игрока в момент исходного async пакета не обещаем. Собственный postToChat
рассылает текст и не создаёт CHAT_MESSAGE: обработчик не зацикливается на ответе.

**Ломание/отмена.** BLOCK_BREAK наблюдает действие игрока. `mc.setBlock(...,AIR)`
не выдаётся за такое действие. Отменяемые события наблюдаем на MONITOR с учётом
отмены; это известный статус в фазе наблюдения, а не атомарная гарантия всех
последующих изменений мира. Сетевая Python-функция не может вызвать event.cancel()
и успеть синхронно предотвратить действие. Для этого впоследствии нужны
отдельные заранее зарегистрированные серверные правила.

5. Мировые настройки и небольшие удобства
---------------------------------------

Следуем существующему имени `mc.worlds`; без обязательного имени мира в вызовах.
world=None в новых методах выбирает мир сессии. GameMode относится к игрокам,
время/погода/gamerules — к миру, поэтому эти операции не смешиваются.

```python
from minebridge import weather, gamerule

mc.worlds.setTime(6000)
mc.worlds.setWeather(weather.CLEAR)
mc.worlds.setGameRule(gamerule.KEEP_INVENTORY, True)
mc.worlds.setGameRule(gamerule.DO_DAYLIGHT_CYCLE, False)
```

Пары чтения/записи: getTime/setTime, getWeather/setWeather,
getGameRule/setGameRule. Время — игровые тики суток 0..23999, не секунды;
отдельный setFullTime не вводим, setTime следует семантике Paper. По документации
установка более раннего времени суток может продвинуть полный счётчик на день;
это нужно подтвердить на pinned133 при реализации. Погода —
weather.CLEAR/RAIN/THUNDER; обычный игровой цикл может поменять её позднее.
Для фиксации используется DO_WEATHER_CYCLE, а не скрытый бессрочный scheduler.

GameRuleKey[bool] и GameRuleKey[int] дают IDE тип нужного значения. Каталог
экспортируется из API133. Проверяем bool/int без приёма bool за числовое правило;
не выдумываем универсальный диапазон для всех int-правил: API даёт тип/default,
но не общий min/max. Конкретные правила, поведение setter и чтение результата
нужно сверить в I01; неподдержанное значение должно дать понятную ошибку.

Полезные небольшие методы той же версии:

| API | Зачем |
|---|---|
| effects.remove(targets,effect), effects.clear(targets) | Снять награду/временные эффекты после раунда |
| players.getHealth(target), setHealth(targets,value) | Восстановить игрока, читать результат; максимум фактический, не всегда 20 |
| players.getFoodLevel(target), setFoodLevel(targets,value) | Перезапуск мини-игры, диапазон сытости 0..20 |
| server.getInfo(), server.getCapabilities() | Читать согласованные версии/мир/session ID/capabilities из hello без доступа к _transport и без обещания текущих TPS |
| with Minecraft.create(...) as mc | Явно закрывать сессию и подписки при выходе из блока/ошибке |

Новые перечисления — модули статических типизированных констант, а не отдельные
подклассы для каждого предмета/события. Экспорт/генерация — локальные файлы;
подсказки не требуют подключения к серверу.

6. Изменения плагина и транспорта
--------------------------------

Версия пакета/плагина 0.3 не означает автоматическую смену major протокола.
Рекомендуется сохранить protocol 2.0 и добавить capabilities по областям.
Существующий decoder строго ждёт minor=0: незаметный ответ minor=1 сломает
0.2-клиент. Самопроизвольные event-уведомления отправляются только явно
подписавшейся сессии; pull/history приходят обычными ответами на запросы.
Новый Python проверяет нужную capability до нового вызова, старый Python
продолжает получать только обычные ACK/ошибки/известный progress.

Сейчас receiver отвергает входящие frames при pending=0 как unsolicited.
Нужно выделить три независимые ветки: ответ RPC, system.progress и событие.
Event frame обрабатывается **до** проверки списка ожидающих RPC и никогда
не сдвигает request ID/last_completed. Снимок добавляется в очередь;
пользовательская функция не выполняется сетевым reader.

Общий EventJournal хранит canonical eventId/serverEpoch/type/tick/world и данные,
без subscriptionId. Подробные курсоры/retention/страницы заданы в
[дизайне истории](EVENTS_V0_3.ru.md). Hello возвращает начальный tail и параметры
журнала дополнительными полями, сохраняя старый запрос и minor=0.

Live-уведомление содержит subscriptionId, delivery sequence, eventId, eventType и snapshot. Для
подписки клиент заранее создаёт UUID/локальную запись, затем отправляет RPC.
Сервер активирует выдачу после публикации ACK. ACK и первое событие в одном
TCP chunk должны корректно разбираться. Ошибка subscribe удаляет локальную запись.

После unsubscribe ACK сервер не создаёт новые события этой подписки. Уже
отправленные могут прийти позднее: клиент их безопасно отбрасывает и не запускает
новые callbacks; уже выполняющийся callback не прерывается принудительно.
Закрытие сессии освобождает registry, накопленные frames и монитор лавы.

Не помещаем поток событий прямо в нынешнюю output-очередь, где переполнение
закрывает соединение: это вытеснило бы ACK мутаций. Нужны отдельная bounded
event-очередь, приоритет control/RPC, и сохранение целостности начатого frame.
Ориентиры лимитов для первой проверки — до 32 подписок/сессию и 512 событий
в server/Python очереди; итоговые значения фиксируются по стенду в I02.
Это очереди live-доставки; bounded журнал истории имеет отдельные лимиты.

Предлагаемая политика переполнения: drop-newest, явный счётчик/уведомление
с источником server/python и sequence, остановка dispatch с EventOverflowError.
RPC/другие сессии продолжают работать. Уведомление о потере нельзя терять
в той же переполненной очереди; для него нужен отдельный coalesced статус.
Затронутые подписки помечаются BROKEN: их накопленные события удаляются,
новые callbacks не запускаются. Повторный run/poll сообщает EventOverflowError,
пока такие подписки не удалены. Восстановление явное: unsubscribe повреждённых
подписок, чтение актуального состояния игры, новая подписка с новым UUID.
При потере общего chat ingress повреждёнными считаются заинтересованные
chat-подписки; они также получают видимую ошибку, а не ложную непрерывность.
Автоматического повтора команд/обработчиков, exactly-once и долговременного
replay нет. Ограниченное повторное чтение истории через getRecent входит.
Потеря истории при ротации ring вызывает отдельный EventHistoryLostError,
не помечает live-подписки BROKEN и не сдвигает pull-курсор молча.
Потеря async ingress до записи в журнал тоже имеет отдельный capture-loss
watermark: непрерывные сохранённые sequence не должны скрывать такую потерю.
Очередь async chat ingress тоже ограничена и имеет видимую потерю.

Все новые игровые операции используют главный поток, существующие ChunkService,
FIFO/бюджеты, учёт частичных результатов и SessionActivityLog. logging=True
логирует подписку/отписку, отправку/потери событий и RPC. Сервер не может
утверждать, что локальная Python-функция уже выполнилась, только по факту
постановки event frame в очередь.

Двадцать игроков/LAN не считаются проверенными по одному локальному стенду.
**Риски:** проверка из исходников вместо поставки, незаметный event-thread leak,
смешение подписок, инвентарь не того игрока, необоснованное обещание скорости.

8. Что зафиксировать перед программированием
--------------------------------------------

До I01: перенос согласованного порядка эффекта в контракт, aliases setPos,
возвращаемые типы/единицы, неизменность
старых вызовов и capability-политика.

До I02: event envelope, очередь/consumer, subscribe ACK fence и unsubscribe,
sequence/overflow/error/disconnect, фильтры и отсутствие синхронной отмены.
Также canonical eventId, hello baseline, pull-курсоры и их общность с aliases,
getRecent/retention/history gaps/clearPending и byte-budget ответов.
Смена major протокола, новый тип подключения или отправка Python-кода в Java
для этих требований не нужны.

До I03: payload каждого события, наблюдаемая фаза/отмена, lava baseline,
телепортация/respawn и момент мирового снимка async chat.

До I04: номера/типы слотов, replacement/stack limits, идентичность inventory,
double-chest layout, результаты, byte-budget страниц и read-only ItemView
вместо ложного round trip.

Позднее можно решать: декораторы, asyncio, произвольные selector-фильтры
подписки, новые контейнеры, lossless transfer, GUI, scoreboard, durable replay и
серверные правила. Они не блокируют указанные срезы.

Выполненная первая самостоятельная задача — I01(a): реализовать согласованную
позиционную форму effects.add и два алиаса setPos без изменения wire-формы.
Готово, когда прежний keyword-вызов и новый позиционный эквивалентны, алиасы
делегируют teleport, все три входа поддерживают тот же selector/дроби/TargetResult,
есть один короткий пример и проходят существующие плюс точечные проверки.
Промежуточной установочной поставки для этой задачи не требуется.
Затем выполнены I02–I05, включая callbacks, независимую историю, игровые события,
слоты и общую приёмку. Обязательных задач этого плана не осталось.

9. Проверенные основания и ещё не проверенное поведение
-----------------------------------------------------

Этот раздел отражает основания **на дату первоначального плана**.
Итоговые результаты реализации приведены в отчётах I01–I05 выше.

Существующий репозиторий подтверждает: callbacks/run/poll уже согласованы;
receiver пока допускает только ответы/progress при ожидающих RPC; postToChat
использует sendMessage, а setBlock — setter BlockData. Это объясняет нужные
изменения транспорта и разделение событий, не является тестом будущей 0.3.

Локально по закреплённым Paper API/server build 133 через javap подтверждены:
AsyncChatEvent, Entity.isInLava, PlayerMoveEvent/damage API; Chest физический/
общий inventory, DoubleChestInventory; PlayerInventory с внутренними слотами
0..42 и BODY/SADDLE; ItemStack.getMaxStackSize и byte serialization;
GameRule тип/default, World time/weather/rule и GameMode API.
Наличие метода/bytecode не заменяет игровую приёмку алгоритма, slot mapping,
снятия отмены или поведения рядом с другим плагином.

используются как справка и не выданы за проверку pinned133:
