Контракт минимального среза v0.1, протокол 1.0
===========================================

Статус: рабочая ревизия r1 протокола 1.0 зафиксирована для реализации
20 октября 2026 года (T00). Здесь перечислены решения, а не результаты испытаний.
Офлайн-модели T01, codec T03, транспорт T04, handshake T05, blocks.set T06 и
публичный Python-фасад T07 и observer/gate T08 реализованы и проверены;
V01–V07/D01–D04 пройдены в T09, N01–N10/F01–F05 — в T10 вместе с повтором V/D.
Минимальный технический subset принят 22 октября; результаты — в отчётах этапов.
При конфликте с широким roadmap этот документ задаёт только
объём v0.1; согласованные будущие возможности не отменяются.

1. Публичный Python subset
-------------------------

Рабочий импорт: from minebridge.minecraft import Minecraft;
from minebridge import block. Имя пакета пока не публикуется в PyPI.

Поддерживаемые сигнатуры:

```text
Minecraft.create(ip="localhost", port=4711, *, token=None,
                 world=None, timeout=5.0, coordinates=None) -> Minecraft
mc.setBlock(x, y, z, block, data=0) -> None
mc.blocks.setBlock(x, y, z, block, data=0) -> None
mc.close() -> None
```

Оба setBlock используют один normalizer и один blocks.set. create возвращает
готовый объект только после успешного hello. close идемпотентен, закрывает TCP,
не требует отдельного RPC и не откатывает выполненную запись.
timeout — конечное положительное число секунд; отдельный предел подключения
и ожидания каждого ответа. Это не обещание задержки обработки на Paper.

coordinates=None означает согласованный absolute; строка "absolute" разрешена.
Другой профиль даёт UnsupportedFeatureError до игрового запроса.
player, pairingCode, project и withContext не входят в данный subset;
неподдержанные kwargs дают TypeError, не игнорируются. getPlayerEntityId,
setBlocks/getBlock и другие области пока отсутствуют, это не полный mcpi.

Клиент сериализует RPC одним lock, имеет не более одного ожидаемого ответа
и одного владельца чтения сокета на соединение. Фонового event-reader пока нет.
Между отдельными процессами/экземплярами состояние не разделяется.

Уточнения публичного фасада T07: канонический импорт остаётся
from minebridge.minecraft import Minecraft; from minebridge import Minecraft
экспортирует тот же класс. Minecraft.create вызывает внутренний connect_and_handshake
и возвращает объект после проверки hello. mc.blocks — read-only свойство одного
экземпляра Blocks; root setBlock делегирует ему без отдельного соединения,
нормализатора или таблицы блоков. Оба пути отправляют blocks.set с mutation=True,
выбранным именем мира и возвращают None после проверенного ACK. Публичные
context manager, session metadata, reconnect и дополнительные kwargs не добавлены.

2. Входные блоки и координаты
----------------------------

BlockInput = int | LegacyBlock | str | BlockSpec. Типы значений неизменяемы.
Поддержанные legacy-пары и статические константы:

| (id,data) | Константа | Канонический ключ |
|---|---|---|
| (0,0) | block.AIR | minecraft:air |
| (1,0) | block.STONE | minecraft:stone |
| (4,0) | block.COBBLESTONE | minecraft:cobblestone |

LegacyBlock хранит .id/.data. При объекте LegacyBlock ненулевой отдельный data
не допускается; эффективная пара берётся из объекта. Для числового ID data
берётся из аргумента. Иные пары дают UnsupportedLegacyBlockError до отправки.
Для str/BlockSpec data обязан быть 0. BlockSpec имеет key и states, в v0.1
допустим только пустой states. Непустой states и строка со свойствами [..]
дают UnsupportedFeatureError; их нельзя молча обрезать.
Современная строка должна быть полным ключом namespace:path, без автоподстановки
namespace. Поддержку реального типа блока проверяет сервер; ключ предмета
вместо блока, отсутствующий материал и air-подмена неизвестного не допускаются.

В первой задаче compat-файл содержит только эти три пары и ссылку на их
происхождение/проверку. Не рекламируем поддержку всех старых ID.

Уточнение упаковки T01: единственный JSON находится в
python/src/minebridge/_data/legacy-blocks-v0.1.json и поставляется как package data.
compat/README.md указывает на него. Так wheel и самостоятельный sdist не зависят
от внешнего каталога и не содержат расходящихся копий таблицы.
Локальные машинные коды: UnsupportedLegacyBlockError=UNSUPPORTED_LEGACY_BLOCK,
InvalidBlockError=INVALID_BLOCK, UnsupportedFeatureError=UNSUPPORTED_FEATURE;
у них outcome=not-applied.

Координаты Python: конечные int/float, исключая bool, NaN и бесконечность.
Для каждого значения применяем floor. Результат должен помещаться в int32.
Другие типы дают TypeError, недопустимые числа/диапазоны — ValueError до RPC.
data и legacy ID также не принимают bool. На проводе координаты — целые JSON
числа без дробной/экспоненциальной записи; сервер не округляет raw-ввод.
Форма position — массив ровно из трёх таких чисел.

Сервер проверяет y по фактическим minHeight <= y < maxHeight. В данном
кандидате сервер также проверяет действующую WorldBorder для центра блока x+0.5/z+0.5;
это явная политика API данного среза, а не утверждение о запрете Paper setter.
Проверки мира, его границ, loaded-состояния и setter выполняются в одной
серверной задаче. Вычисление chunkX/chunkZ использует floorDiv(x,16),
включая отрицательные координаты.

3. Транспорт и ограниченный профиль JSON-RPC
-----------------------------------------

TCP, UTF-8 без BOM, один JSON-объект и LF. CR перед LF допустим и удаляется.
Переводы строк внутри JSON-строк экранируются. Один read не равен одному кадру.
Размер считается в байтах payload до LF, включая возможный CR. JSON-парсер
строгий: повторные ключи, NaN/Infinity и превышение глубины отвергаются.

Запрос имеет jsonrpc="2.0", id, method и params-объект. ID — целое
1..9007199254740991 без дроби, экспоненты, bool и null. ID возрастают в пределах
соединения; повторы/уменьшение — INVALID_REQUEST и закрытие. Одинаковые ID
в разных соединениях допустимы. Корреляция всегда (session/connection, id).

Ответ содержит тот же id и ровно одно из result/error. Для ошибок повреждённой
структуры, когда ID определить нельзя, используется id=null.
Порядок полей объекта и пробелы не имеют значения. Дополнительные поля
result от будущего совместимого сервера клиент игнорирует; неизвестные поля
параметров запросов v0.1 отвергаются как INVALID_PARAMS, чтобы замечать опечатки.

Поддерживается ограниченный профиль JSON-RPC, не полная универсальная реализация:
нет batch, positional params и client notifications. Массив batch получает
INVALID_REQUEST/id=null, ни один его элемент не выполняется. Валидное сообщение
без id трактуется как notification: не выполняется, ответа нет, соединение
закрывается. Ошибочный объект, не являющийся notification, получает ошибку.
Это ограничение профиля должно быть явно описано для сторонних клиентов.
Нельзя случайно выполнить blocks.set без подтверждения.

Dev-лимиты (проектные значения, не результаты измерений; транспортные лимиты
реализованы в T04, игровые бюджеты — в executor T05/T06):

| Имя | Значение / смысл |
|---|---|
| maxFrameBytes | 65536 байт |
| maxJsonDepth | 16 уровней вложенных объектов/массивов; корневой объект — уровень 1 |
| maxSessions | 8 активных соединений, включая незавершившие hello |
| maxQueuedRequests | 8 ещё не начатых запросов на соединение |
| maxOutputFrames | 8 кадров на соединение |
| handshakeTimeoutSeconds | 5 секунд от accept до завершения hello |
| frameAssemblyTimeoutSeconds | 5 секунд от первого байта кадра; пустой idle READY разрешён |
| writeTimeoutSeconds | 5 секунд на передачу кадра; ожидание только вне игрового потока |
| maxOperationsPerTick | 32 короткие записи суммарно |
| maxOperationsPerSessionPerTick | 4, round-robin между готовыми сессиями |
| executorBudgetMillis | 2 мс, проверка между операциями, не прерывает отдельный setter |

Возможность одного setter с физикой выйти за бюджет не скрывается. Это не
готовность полного класса по производительности. Устойчивый журнал повторов,
персональная справедливость и большие задания остаются следующими срезами.

При превышении размера/depth/невалидном UTF-8 — закрытие без обязательного
ответа, без исполнения повреждённого запроса. При превышении входной очереди
валидный запрос получает LIMIT_EXCEEDED/not-applied, если ответ можно поставить
в ограниченную выходную очередь. Выходная очередь переполнена/читатель завис —
закрытие соединения, игровой поток не ожидает сеть. 9-е соединение закрывается
без создания сессии. Незавершённый кадр при EOF не исполняется.

Уточнения codec для T03 (20 октября 2026 года; wire-версия остаётся 1.0):

- Проверки выполняются по этапам: размер payload, строгий UTF-8, запрет BOM,
  предварительный подсчёт глубины вне строк, затем JSON и форма сообщения.
  Поэтому даже синтаксически повреждённый текст, превышающий глубину,
  отвергается как JSON_TOO_DEEP до разбора JSON. Скобки внутри строк не считаются.
- Экранированные непарные UTF-16 surrogate отвергаются как PARSE_ERROR;
  корректная surrogate-пара допустима. Дубликаты имён ищутся после декодирования
  escape-последовательностей. BOM и синтаксические ошибки — PARSE_ERROR.
- Неизвестные поля оболочки допускаются. Для известных методов точный набор
  полей обязателен в params и вложенных protocol/block. Неизвестный метод с
  корректной оболочкой передаётся будущему router без проверки его params.
- Notification — корректная оболочка с jsonrpc/method/params без id. Параметры
  метода у неё не проверяются: исполнения и ответа не будет, соединение позже
  закрывает транспорт/router. Отсутствие id у повреждённой оболочки не делает
  её notification. Корректный ID повреждённой оболочки сохраняется в ошибке.
- Все поля, объявленные целыми, требуют целой лексической записи: в том числе
  major/minor, error.code и счётчики limits. Неотрицательный -0 равен 0;
  для положительного ID и положительных счётчиков 0/-0 недопустимы.
  Верхний предел major/minor, error.code и счётчиков сверх размера кадра
  не вводится. Числа сохраняют исходную запись до проверки поля.
- В hello-result счётчики limits положительные целые; *TimeoutSeconds и
  executorBudgetMillis — положительные JSON-числа, допускающие дробь/экспоненту.
  Это проверка формы, а не автоматическое принятие клиентом удалённых лимитов.
  Ответ v0.1 содержит protocol=1.0, UUID в форме 8-4-4-4-12 и int32-границы
  minY < maxYExclusive. Дополнительные поля результата, включая вложенные,
  не мешают проверке обязательных полей.
- Известный error.code должен совпадать с data.code по таблице раздела 6;
  противоречие — повреждённый ответ. Для неизвестного числового кода сохраняются
  data.code/outcome и используется базовый MinecraftError, даже если имя
  совпало с известным. У сообщения ошибки нет роли в классификации.

Codec не хранит состояние соединения: монотонность ID, handshake, авторизация,
таймеры и применение close выполняются в следующих этапах. Его close=false
означает лишь отсутствие безусловного требования закрытия на уровне codec;
например, ошибка params в hello всё равно закроет соединение по разделу 4.

Уточнения транспорта T04 (20 октября 2026 года):

- Java decodeEnvelope проверяет JSON/оболочку/ID, а validateRequestParameters
  выполняет проверку параметров. Существующий decodeRequest объединяет их
  и сохраняет поведение T03. Транспорт использует только decodeEnvelope:
  диспетчер T05 сначала проверит состояние/доступ, затем параметры команды.
- ID увеличиваются отдельно для каждого TCP-соединения, в том числе для
  запросов, отклонённых из-за полной входной очереди. UUID Session — контекст
  соединения, не личность ученика. Закрытие очищает ещё не начатые запросы.
- В выходном пределе 8 кадров учитывается частично передаваемый головной кадр.
  Его срок передачи начинается, когда он становится головным, и не продлевается
  при частичном прогрессе. Ожидание за предыдущим кадром не запускает этот срок.
- Listener принимает числовой IPv4/IPv6 в listenAddress. Это исключает
  неотменяемый DNS lookup, который мог бы задержать завершение сетевого потока.
  Синтаксис проверяется без DNS; bind/accept/read/write и закрытие каналов
  выполняются отдельным NIO reactor. onDisable только подаёт сигнал остановки.
- Python разрешает IP/hostname, включая localhost. Синхронное разрешение имени
  ОС выполняется до общего срока TCP-connect для всех полученных адресов.
  Время DNS не ограничено этим сроком; отдельные resolver-потоки не создаются.
  Передача запроса и ожидание полного ответа имеют отдельные абсолютные сроки.
- Тайм-аут подключения имеет TIMEOUT/not-applied: RPC ещё не существовал.
  Тайм-аут обмена — TIMEOUT/unknown; соединение закрывается, повторов нет.
  После возможной отправки мутации обрыв/повреждённый ответ имеет unknown;
  локальная ошибка до отправки — not-applied.

Архивная промежуточная сборка T04 ограниченно ставит запросы в очередь, но ещё не
исполняет их и не переводит соединение в READY. Незавершившее handshake
соединение закрывается через 5 секунд. Только отдельный тестовый consumer
может снимать запросы/отправлять ответы/вызывать markReady; он не входит в JAR.
Это граница этапа, а не окончательная реализация поведения разделов 4–7.

Уточнения handshake T05 (20 октября 2026 года):

- Диспетчер на потоке Paper проверяет состояние до параметров метода:
  blocks.set до hello получает NOT_READY даже с неверными params; повторный
  hello — INVALID_STATE. Оба отказа закрывают соединение после попытки ответа.
- Строковый неверный/пустой токен hello получает AUTH_FAILED до проверки
  остальных параметров и обращения к миру. Отсутствующий/нестроковый token —
  INVALID_PARAMS. Секрет сравнивается через SHA-256 и MessageDigest.isEqual;
  это не шифрование транспорта. Пробелы вокруг непустого токена сохраняются.
- Успешный ответ hello и переход READY ставятся атомарно в ограниченную
  выходную очередь только до истечения срока от accept. Контекст мира публикуется
  вместе с этим переходом; закрытие/просрочка не могут восстановить READY.
  ACK означает успешный handshake; фактическая доставка зависит от транспорта.
- Метаданные мира читаются только на потоке Paper и сохраняются неизменяемыми.
  Числа удалённых limits в Python остаются точными JsonNumber и не увеличивают
  локальные пределы codec. Отсутствие токена/неподдержанный локальный профиль
  проверяются до DNS/TCP; только token=None обращается к MINEBRIDGE_TOKEN.
- T05 — промежуточная сборка, не завершённый v0.1: форма hello сохраняет
  обязательный capabilities=["blocks.set"] из замороженного контракта/корпуса,
  но setter реализуется в T06. До T06 корректный blocks.set отвечает
  UNSUPPORTED_FEATURE/not-applied, не меняет мир и не выдаёт applied=true.
  Это временная граница этапа; публичный Minecraft.create появится после setter,
  в T07. Дополнительные capabilities не объявляются.

Начиная с T06 это ограничение промежуточного T05 снято: blocks.set реализован.
Сохранённое описание относится только к архивному артефакту T05.

4. Handshake и мир
-----------------

CONNECTED разрешает только system.hello. Успех переводит в READY;
неуспешный hello, запрос мутации до hello и повторный hello закрывают соединение
после отправки подходящей ошибки, если транспорт позволяет.
Доменная ошибка обычного blocks.set оставляет READY, кроме отказа транспорта.
Завершение/закрытие переводит в CLOSED; новых операций больше нет.

Минимальная авторизация — один серверный токен текущего урока. Пустой/неверный
токен не превращается в anonymous. token=None в Python использует
MINEBRIDGE_TOKEN; если значения нет, AuthenticationError до подключения.
Секрет не фиксируется в репозитории, fixture, trace, stacktrace или сообщении.
Токен не означает ник и не устанавливает SELF; одинаковый токен у A/B всё равно
даёт две независимые сессии. Это не постоянные профили компьютеров/учеников.
Анонимный режим и pairing здесь не реализуются. Транспорт v0.1 предназначен
для локального стенда/доверенной LAN; default bind=127.0.0.1, port=4711.
Адрес LAN задаётся явно оператором. Интернет-публикация не входит в срез.

Плагин имеет один configured defaultWorld; он должен существовать и быть
доступен при старте. world=None выбирает его, указанное имя должно совпадать
с доступным configured миром. Нельзя выбирать «первый» мир по порядку коллекции.
При неизвестном имени — WORLD_NOT_FOUND; при существующем, но недоступном —
PERMISSION_DENIED. Идентификатор выбранного мира фиксируется на сессию;
игроки, их ники, позиции и измерения на него не влияют.

Запрос-пример (значение token — демонстрационное):

```json
{"jsonrpc":"2.0","id":1,"method":"system.hello","params":{"protocol":{"major":1,"minor":0},"token":"EXAMPLE-NOT-A-SECRET","world":null,"coordinates":"absolute"}}
```

Все четыре параметра запроса обязательны; world может быть null/строкой.
major/minor — неотрицательные целые, major сервера=1; при другом major —
PROTOCOL_VERSION. Для major=1 выбирается min(clientMinor,serverMinor), сейчас 0.
Неизвестный профиль координат — UNSUPPORTED_FEATURE; v0.1 только absolute.

Пример ответа (высоты примерные, в реальности читаются из выбранного мира):

```json
{"jsonrpc":"2.0","id":1,"result":{"protocol":{"major":1,"minor":0},"sessionId":"31cadb96-7a40-4f45-a068-213352f6cb26","pluginVersion":"0.1.0-dev","serverVersion":"26.2","world":{"name":"world","uuid":"a1905647-deee-4732-a516-4bc34a1ed1d9","minY":-64,"maxYExclusive":320},"coordinates":"absolute","chunkPolicy":"loaded-only","applyPhysics":true,"capabilities":["blocks.set"],"limits":{"maxFrameBytes":65536,"maxJsonDepth":16,"maxSessions":8,"maxQueuedRequests":8,"maxOutputFrames":8,"handshakeTimeoutSeconds":5,"frameAssemblyTimeoutSeconds":5,"writeTimeoutSeconds":5,"maxOperationsPerTick":32,"maxOperationsPerSessionPerTick":4,"executorBudgetMillis":2}}}
```

Поля этого result обязательны. Клиент проверяет negotiated major, профиль,
capability blocks.set и корректность типов/границ до возврата create.
sessionId — новый непрозрачный UUID для TCP-соединения. Это не личность ученика.
Полная версия/build/SHA Paper дополнительно фиксируется в manifest стенда.
Лимиты ответа отражают действующую конфигурацию; клиент не увеличивает свои
локальные пределы автоматически из непроверенного ответа сервера.

5. blocks.set, подтверждение и порядок
------------------------------------

```json
{"jsonrpc":"2.0","id":2,"method":"blocks.set","params":{"world":"world","position":[0,80,0],"block":{"key":"minecraft:cobblestone","states":{}}}}
```

Все поля обязательны, world совпадает с миром сессии. states только пустой
объект. Иной существующий мир не разрешается отдельным полем raw-запроса.
Сервер повторно проверяет типы/числа, блок, границы и полномочия; raw-клиент
не может обойти правила Python. Загруженность проверяется через isChunkLoaded
до getBlockAt; незагруженный чанк даёт CHUNK_NOT_LOADED, не загружается/генерируется.

Уточнения реализации T06 (20 октября 2026 года; wire-версия не менялась):

- Неизвестное raw-имя мира даёт WORLD_NOT_FOUND; существующий другой мир —
  PERMISSION_DENIED. Для выбранного имени сервер каждый раз разрешает сохранённый
  UUID сессии. Исчезновение/замена мира с тем же именем не перепривязывает сессию:
  WORLD_NOT_FOUND. Высоты и границы повторно читаются во время операции.
- Материал разрешается точным Registry.MATERIAL.get по полному namespaced key;
  проверяются isBlock, отсутствие legacy и точное совпадение ключа. Permissive
  matchMaterial/Registry.match не используются. Setter получает default BlockData
  через Paper Block.setType(material,true), в том числе при повторе того же материала.
- Политика центра блока использует один снимок публичных WorldBorder.getCenter()
  и getSize() на потоке Paper, с ограничением server.getMaxWorldSize(). Нижние
  границы включены, верхние исключены. Закреплённый CraftWorldBorder.isInside(Location)
  округляет Location через BlockPos и не сохраняет дробный центр, поэтому адаптер
  явно сравнивает x+0.5/z+0.5 с вычисленными границами. Это политика данного API;
  побитовая эквивалентность внутренней интерполяции движущегося border не обещается.
- Успешный ответ кодируется до записи, но публикуется только после нормального
  возврата setter. Доменная ошибка сохраняет READY. При исключении setter —
  INTERNAL_ERROR/unknown, без обещания отката. Переполнение/закрытие выхода после
  setter не отменяет запись и не создаёт повторной попытки.
- Непосредственно перед setter короткий Session.tryBeginOperation атомарно
  определяет порядок начала операции и close. Закрытие до этой точки отменяет
  запись; после неё уже начатая операция может завершиться. Monitor Session
  не удерживается во время Paper API/физики; marker снимается в finally.
- Ограниченный диагностический trace включается только локальным JVM-параметром
  -Dminebridge.diagnostics=true; по умолчанию выключен. APPLY_BEGIN/APPLY_DONE
  отмечают сам setter, ACK_ENQUEUED записывается под lock публикации выходного
  кадра до его доступности writer. Sink/журнал вызывается вне Session lock.
  Буфер ограничен 256 событиями; пропуски учитываются и лишают trace полноты,
  но не меняют операцию. Trace T06 содержит sequence/sessionId/requestId/
  applySequence/threadId/primaryThread. World/position и gate добавлены в T08,
  как уточнено в разделе 7. Секреты и сырые параметры запроса в trace не попадают.

GameExecutor выполняет проверку и setter на главном потоке обычного Paper.
В этом срезе физика включена. После нормального завершения setter формируется:

```json
{"jsonrpc":"2.0","id":2,"result":{"applied":true}}
```

На Python оба setBlock возвращают None только после этого ответа. Установка
уже такого же блока также успешна. Состояние, изменившееся впоследствии от
физики/игрока/другого плагина, не делает исходный ACK ложным. Ответ не гарантирует
отрисовку клиентом, сохранение на диск, BlockPlaceEvent или согласование с каждым
сторонним protection-плагином. Последнее требует отдельной будущей интеграции.
Нельзя заменять операцию административной строкой setblock ради реализации API.

Мутации в пределах соединения выполняются FIFO. Из разных соединений порядка
прихода/завершения не обещаем; запись в одну позицию побеждает по последнему
реальному исполнению setter. В v0.1 нет длительных jobs, поэтому резервирование
областей не требуется. Trace фиксирует sessionId/requestId и порядковый номер
исполнения, но не становится публичным API.

6. Ошибки и неизвестный исход
----------------------------

Пример ошибки до записи:

```json
{"jsonrpc":"2.0","id":2,"error":{"code":-32023,"message":"Target chunk is not loaded","data":{"code":"CHUNK_NOT_LOADED","outcome":"not-applied"}}}
```

error.code — число, error.message — безопасный текст, data.code — стабильное
машинное имя, data.outcome — not-applied либо unknown для конкретного запроса.
Текст сообщения не используется для машинной классификации. Stacktrace остаётся
в серверном журнале с sessionId/requestId. Result и error одновременно запрещены.

| Число | data.code | Python exception | Соединение |
|---|---|---|---|
| -32700 | PARSE_ERROR | ProtocolError | Закрыть после попытки ответа |
| -32600 | INVALID_REQUEST | ProtocolError | Закрыть |
| -32601 | METHOD_NOT_FOUND | UnsupportedFeatureError | READY сохраняется |
| -32602 | INVALID_PARAMS | InvalidArgumentError | READY; при hello закрыть |
| -32603 | INTERNAL_ERROR | ServerOperationError | READY, outcome может быть unknown |
| -32001 | AUTH_FAILED | AuthenticationError | Закрыть |
| -32002 | PROTOCOL_VERSION | ProtocolVersionError | Закрыть |
| -32003 | NOT_READY | ProtocolError | Закрыть |
| -32004 | INVALID_STATE | ProtocolError | Закрыть |
| -32010 | LIMIT_EXCEEDED | LimitExceededError | READY, если транспорт способен ответить |
| -32020 | WORLD_NOT_FOUND | WorldNotFoundError | READY; при hello закрыть |
| -32021 | PERMISSION_DENIED | PermissionDeniedError | READY; при hello закрыть |
| -32022 | COORDINATE_OUT_OF_BOUNDS | CoordinateOutOfBoundsError | READY |
| -32023 | CHUNK_NOT_LOADED | ChunkNotLoadedError | READY |
| -32024 | INVALID_BLOCK | InvalidBlockError | READY |
| -32025 | UNSUPPORTED_FEATURE | UnsupportedFeatureError | READY; при hello закрыть |

Все перечисленные классы входят в MinecraftError; ProtocolVersionError —
частный ProtocolError. ConnectionError и OperationTimeoutError возникают
локально. UnsupportedLegacyBlockError — локальная ошибка входа блока.
Неизвестный code при корректной форме error оборачивается в MinecraftError;
повреждённая форма/чужой ID — ProtocolError с закрытием соединения.

У MinecraftError предусмотрены машинные .code и .outcome. Для server error
они берутся из data, для локального timeout code=TIMEOUT/outcome=unknown.
После обрыва при отправленной мутации ConnectionError использует
code=CONNECTION_LOST/outcome=unknown. Ошибки до отправки мутации имеют
outcome=not-applied. Неизвестный исход не определяется разбором текста сообщения.

Проверки до setter гарантируют not-applied для данного запроса. После начала
setter при исключении нельзя обещать откат: INTERNAL_ERROR/outcome=unknown.
Другие ранее принятые запросы не охватываются этим outcome.

При timeout или потере связи клиент не повторяет мутацию; исход может быть
неизвестен. OperationTimeoutError сообщает unknown, закрывает соединение,
поздний ответ не может стать ответом следующей операции. Reconnect создаёт новую
сессию; idempotency key и память результатов здесь не реализуются.
Wrong-ID/повреждённый ответ после отправки мутации также не доказывает её отмену.

7. Close, shutdown и тестовый контракт
------------------------------------

close/EOF/disable перестают принимать новые запросы и отменяют ещё не начатые
задачи сессии. Начавшийся setter может завершиться; уже сделанное не откатывается.
При физическом обрыве клиент не знает, началась ли задача. Очередь, socket и
потоки освобождаются; игровой поток не ждёт завершения socket writer.
При остановке плагина клиент получает ошибку/EOF в пределах своих deadline,
а не обещанный ответ SERVER_STOPPING, который сеть может не доставить.

Для тестов предусмотрен отдельный observer JAR, не входящий в поставку.
Он читает реальный мир через консоль, не вызывает BlockService и не принимает
сетевые команды Python. Отдельный диагностический trace у production setter
показывает поток самой записи. Тестовый gate может отложить dispatch без
блокирования тика; по умолчанию выключен и недоступен удалённым клиентам.
Ни observer, ни gate не добавляют production методов протокола.

Для доказательства порядка trace также регистрирует ACK_ENQUEUED в точке,
когда успешный ответ становится доступным socket writer. Локальный монотонный
eventSequence присваивается в самой точке события, не по порядку доставки логов.
Для успешного запроса обязательно APPLY_DONE.eventSequence <
ACK_ENQUEUED.eventSequence. Порядок по времени прихода stdout и TCP не доказывается.

Уточнения T08 (21 октября 2026 года; публичный API и wire 1.0 сохранены):

- Локальный JVM-флаг -Dminebridge.testControl=true регистрирует Java service
  TestControl и включает trace. Диагностика также включается прежним флагом
  -Dminebridge.diagnostics=true без регистрации service. По умолчанию service отсутствует;
  observer — отдельный JAR. Конфигурация, токен и RPC не включают test-control.
- Gate привязан к caseId/sessionId/requestId и проверяется до dequeue головы
  Session. Удержанный запрос остаётся в ограниченной очереди; тот же FIFO
  сохраняется, другие сессии и тики продолжаются. Отдельной очереди gate нет.
  Release разрешает обычный dispatch; close отменяет ещё не начатый запрос.
- Cleanup проверяет отсутствие активного gate и queued/active состояния
  отслеживаемых запросов case до восстановления мира. Иначе CASE_BUSY без очистки.
  В том числе RELEASED не разрешает очистку до завершения отслеживаемой записи.
  Прочие requestId и будущие запросы этим guard не охватываются: orchestrator
  завершает все свои вызовы либо закрывает клиентов перед восстановлением мира.
- QUEUED/CANCELLED фиксируются на фактическом потоке enqueue/close, который
  может быть NIO; Paper API там не вызывается. APPLY_BEGIN/APPLY_DONE и успешный
  ACK_ENQUEUED фиксируются на игровом потоке. ERROR содержит безопасные code/outcome.
- Добавлены caseId, worldName/worldUuid, x/y/z, errorCode/outcome. Мир копируется
  из авторизованного immutable контекста; сырое имя запроса не журналируется.
  До hello метаданные мира могут отсутствовать; невалидные координаты — null.
- Отдельные буферы публикации и истории ограничены 256 событиями каждый.
  Snapshot сообщает latestSequence/oldestSequence/droppedEvents/evictedEvents.
  Дренирование журнала не стирает историю; вытеснение или пропуск не скрывается
  и не позволяет считать trace полным доказательством.
- Observer самостоятельно читает Paper BlockData, явно удерживает свои чанки
  и публикует коррелированные неизменяемые JSON-снимки через локальную консоль.
  Его чтение не использует BlockService или ожидаемый результат RPC.

Уточнения испытательного seam T10 (22 октября 2026 года; wire 1.0 сохранён):

- Локальный Java TestControl позволяет observer приостановить writer одной
  READY-сессии. Он не останавливает чтение, dispatcher или тики. Пауза снимает
  OP_WRITE, но не меняет срок головного кадра: production deadline остаётся
  5 секунд. При обычном запуске service отсутствует, writerPaused=false.
  Нового RPC или поля production-конфигурации нет.
- Счётчики requestHighWater/outputHighWater, receivedFrames и partialFrameBytes
  не содержат payload. Они наблюдают существующие ограниченные очереди и
  фактическую сборку кадра. Closed Session может удерживаться ограниченным
  test-control до cleanup только ради доказательства отмены/предела очереди.
- Для точного заполнения output queue используется локальная пауза. Отдельная
  проверка настоящего нечитающего TCP-клиента выполняется без неё. Эти способы
  не подменяют друг друга и явно различаются в отчёте.
- При длинной матрице история 256 событий может вытеснять старые записи.
  Тест сохраняет начальный sequence своего проверяемого интервала и проверяет,
  что интервал целиком удержан. Суммарные evictedEvents не скрываются;
  droppedEvents должны оставаться нулевыми. Снимок последних 256 событий
  не объявляется полным журналом всего запуска.

Устройство независимого observer и порядок серверных проверок описаны в
[интеграционном руководстве](../../integration/README.md). Wire-копии полного
кадра, trace и фактическое состояние мира сопоставляются по сессии/запросу.
Это тестовое наблюдение, не новые методы или поля протокола. Этот документ
сохраняет историческую границу v0.1; текущий API описан отдельно.

- [Paper scheduler](https://docs.papermc.io/paper/dev/scheduler/): ограничения обращения к миру из асинхронного кода.
- [Block](https://jd.papermc.io/paper/26.2/org/bukkit/block/Block.html): setter и смысл applyPhysics.
- [World](https://jd.papermc.io/paper/26.2/org/bukkit/World.html): проверка загруженности чанка.
- [WorldBorder](https://jd.papermc.io/paper/26.2/org/bukkit/WorldBorder.html): доступная проверка границы; применение этой политики — наше предложение.
