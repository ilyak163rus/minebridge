Контракт Minebridge v0.2.0 — I01–I05
==================================

Документ фиксирует исторический технический контракт v0.2.0.
Действующий пользовательский интерфейс описан в [справочнике API](../API.md).
Исторический [контракт v0.1](V0_1_CONTRACT.ru.md) не переписывается задним числом.
Целевая среда: Paper 26.2 build 133, Java 25, Python 3.11+.

Дополнение 0.2.1 от 26 октября 2026 года:
`Minecraft.create(..., logging: bool = False)` включает серверные логи одной
сессии при true. Hello допускает необязательный boolean `logging`, capability
`session.logging` подтверждает поддержку. Без настройки старый hello сохранён.
При нормальном выходе Python открытые успешные подключения завершаются через
drain/close; отложенная ошибка печатается в stderr без изменения exit code.
Для обработки исключений внутри программы сохраняются явные flush/close.
Принудительное завершение не имеет такой гарантии.

Публичный API
------------

```python
Minecraft.create(ip="localhost", port=4711, *, writeMode="buffered",
                 token=None, world=None, timeout=5.0, coordinates=None, player=None,
                 logging=False)
mc.setBlock(x, y, z, block, data=0) -> None
mc.blocks.setBlock(x, y, z, block, data=0) -> None
mc.setBlocks(x1, y1, z1, x2, y2, z2, block, data=0) -> None
mc.blocks.setBlocks(x1, y1, z1, x2, y2, z2, block, data=0) -> None
mc.getBlock(x, y, z) -> int
mc.getBlocks(x1, y1, z1, x2, y2, z2) -> dict[tuple[int, int, int], int]
mc.blocks.getBlock(x, y, z) -> BlockSpec
mc.blocks.getBlocks(x1, y1, z1, x2, y2, z2) -> dict[tuple[int, int, int], BlockSpec]
mc.getPlayerEntityId(name) -> int
mc.players.get(target) -> PlayerRef
mc.players.list(targets=selector.ALL_PLAYERS) -> list[PlayerRef]
mc.players.getPos(target) -> Location
mc.players.teleport(targets, x, y, z, *, world=None) -> TargetResult
mc.players.giveItem(targets, item, amount=None, *, overflow="return") -> InventoryResult
mc.effects.add(targets, effect, *, duration, level=1, particles=True) -> TargetResult
mc.spawnEntity(x, y, z, entityType, *, world=None, item=None, block=None,
               face=None, owner=None) -> EntityRef
mc.entities.spawn(entityType, x, y, z, *, world=None, item=None, block=None,
                  face=None, owner=None) -> EntityRef
mc.withContext(*, player=None) -> Minecraft
mc.postToChat(message) -> None
mc.flush() -> None
mc.close() -> None
```

`writeMode` допускает только `"buffered"` и `"sync"`; неверное значение
отклоняется до подключения. Позиционные IP и порт сохранены. `create` возвращает
объект только после успешного hello и необязательной привязки `player`.
Публичных jobs/Future/async API нет. Задания и ожидание чанков — внутренние
детали плагина.

В `buffered` запись нормализуется локально и отправляется без ожидания своего
ответа. Окно неподтверждённых запросов ограничено: максимум 128, дополнительно
уменьшается до серверных `maxQueuedRequests` и `maxOutputFrames`, если они меньше.
При заполнении окна отправитель ждёт; команды не теряются. Единственный reader
принимает ACK независимо от вызовов `flush`. Сервер подтверждает каждый запрос.

В `sync` вызов ждёт подтверждения установки. `flush` в обоих режимах ждёт все
записи, принятые до его барьера. Синхронный запрос результата также сначала
дожидается предыдущих записей. Порядок исполнения и ответов внутри сессии
совпадает с порядком запросов; между сессиями общего порядка нет.

Обычный `close` дожидается записей, затем закрывает сокет и поток reader,
включая путь ошибки; повтор безопасен. Внутренний `TcpTransport.close` прерывает
соединение немедленно, но не является учебным публичным методом.

Мир и конфигурация
------------------

```yaml
listenAddress: '127.0.0.1'
port: 4711
authEnabled: false
token: ''
```

`listenAddress` — числовой IPv4/IPv6, `port` — целое 1..65535. `authEnabled`
необязателен и по умолчанию false; отсутствующий `token` означает пустую строку.
Неизвестные поля отклоняются. Старый `defaultWorld` — исключение: принимается,
игнорируется с сообщением при запуске и не влияет на выбор мира. Пользовательские
сетевые настройки не перезаписываются автоматически.

По умолчанию плагин выбирает основной загруженный мир по ключу
`minecraft:overworld`, независимо от имени папки и порядка списка миров.
Если основной мир не найден при запуске, плагин не включается. `world=None`
выбирает его для сессии; явная строка выбирает загруженный мир по имени или ключу.
Hello возвращает фактические имя, ключ, UUID и высоту. Сессия закреплена за UUID;
пересозданный мир с прежним именем требует нового подключения. Присутствие
или перемещение игрока мир сессии не переключает.

При `authEnabled: false` токен не нужен: доступ к TCP-порту даёт доступ к API,
без обещания личной идентификации ученика. Существующий токен сам по себе
авторизацию не включает. При `true` сервер требует непустой непробельный токен
в конфиге и точное совпадение токена клиента. Строка сохраняется без trim.
Клиент берёт необязательный `MINEBRIDGE_TOKEN`, только когда `token is None`;
отсутствие и пустая строка проходят локальную проверку и оцениваются сервером.

Блоки, состояния и области
--------------------------

Корневой и namespaced `setBlock` используют один нормализатор и соединение.
Сохраняются legacy-пары `(0,0)`, `(1,0)`, `(4,0)` и константы `AIR`, `STONE`,
`COBBLESTONE`; таблица расширяется проверенными соответствиями из
`legacy-blocks-v0.2.json`. Числа не назначаются новым блокам произвольно.
Статический каталог `block.*` генерируется из снимка закреплённого Paper26.2.
Допускаются `LegacyBlock`, `BlockSpec`, полные namespaced-ключи и состояния:
`"minecraft:oak_stairs[facing=east,half=bottom]"`,
`BlockSpec("minecraft:oak_log", {"axis": "x"})`,
`block.OAK_LOG.withStates(axis="x")`. Неизменяемое withStates создаёт новое значение.
Имена свойств — `[a-z0-9_]{1,64}`, значения — `[a-z0-9_-]{1,128}`, до64 свойств;
их применимость к данному блоку проверяется серверным BlockData API.
Координаты — конечные int/float, каждая округляется floor и должна помещаться
в int32; bool не принимается. Сервер проверяет материал, актуальные границы
высоты, WorldBorder и UUID мира перед изменением.

I02 объявляет `chunkPolicy="load-generate"`, `coordinates="absolute"`,
`applyPhysics=true`. Незагруженные чанки загружаются/генерируются асинхронно,
без присутствия игрока и без ожидания Future в игровом потоке. На время работы
чанк удерживается ticket с общим счётчиком пользователей; освобождение одной
сессии не снимает удержание другой. Большая область обрабатывается порциями,
не загружает все чанки одновременно. При сбое загрузки — `ChunkLoadError`.
Изменения выполняются в игровом потоке через Paper API. ACK после setter
не означает сохранение на диск, устойчивость к физике или транзакцию/откат.

Обе границы областей включены, переставленные углы допустимы. Максимум
setBlocks — 1000000 позиций, getBlocks — 262144. Проверка объёма не допускает
переполнения. Установка большой области выполняется по тикам; окончание
подтверждается после всей операции. Другие сессии получают время выполнения.
Конфликтующая мутация зарезервированной стройкой области через Minebridge
получает `RegionBusyError`. Игроки/физика/другие плагины этим резервом не блокируются.
Ошибки и отключение не откатывают уже изменённые блоки.

Корневые чтения возвращают старый ID по проверенному соответствию. Если его
нет или он неоднозначен — `UnsupportedLegacyBlockError`; словарь не выдаётся
как успешный неполный результат. Современные `mc.blocks.*` возвращают BlockSpec
со всеми фактическими состояниями и работают с полным современным каталогом.
Числовое чтение типа не сохраняет историческое data или современные свойства.

Ключи getBlocks — абсолютные координаты. Внутри используется постраничное чтение;
оно не обещает атомарный снимок при чужих изменениях. Порядок сериализации:
x меняется быстрее, затем z, затем y. Python проверяет полноту и порядок страниц.

Сетевой контракт 2.0
-------------------

Framing, UTF-8, ограничение 65536 байт на payload, глубина 16, числовые ID
1..9007199254740991, правила JSON и таблица ошибок унаследованы из v0.1.
Общий актуальный корпус: [protocol/v2](../../protocol/v2/README.md).
Плагин и клиент I01 работают с major=2; совместимость с wire 1.0 не заявляется.

```json
{"jsonrpc":"2.0","id":1,"method":"system.hello","params":{"protocol":{"major":2,"minor":0},"token":null,"world":null,"coordinates":"absolute"}}
```

Ключи hello params ровно `protocol`, `token`, `world`, `coordinates`;
protocol содержит `major` и `minor`. Токен — строка/null, мир — строка/null.
Результат содержит protocol 2.0, sessionId, pluginVersion, serverVersion,
world `{name,key,uuid,minY,maxYExclusive}`, coordinates, chunkPolicy,
applyPhysics, capabilities и limits. `world.key` — обязательный namespaced-ключ.
`blocks.set` обязательна для клиента; сервер I01 также рекламирует
`writes.buffered`. Неизвестные поля результата и дополнительные capabilities
допустимы. Числа limits остаются описательной метаинформацией и не увеличивают
локальные пределы кодека.

`blocks.set` содержит ровно `{world,position,block}`: world — фактическое имя
мира сессии, position — три int32, block — `{key,states}`. Успешный результат
`{applied:true}` публикуется после изменения. Notifications не исполняются.
Каждый запрос имеет отдельный ID и отдельный ACK либо ошибку. **Ответы FIFO:**
сервер отправляет их в том же порядке, в котором принял запросы сессии.
Клиент отклоняет ответ вне порядка, неправильный ID и незапрошенный ответ.

Дополнения I02 (каждый запрос по-прежнему имеет отдельный ID):

| Метод | params | result |
|---|---|---|
| blocks.get | world, position | block: {key,states} |
| blocks.setRegion | world, from, to, block | applied:true |
| blocks.getRegion | world, from, to, offset, limit | blocks:[{position,block}], nextOffset, total |

from/to — три int32; offset — 0..262143 и меньше объёма; limit — 1..64.
nextOffset — следующий offset либо null в конце; total — полный объём области.
Один ответ не превышает действующий лимит кадра. Итоговый словарь собирает Python.
Capabilities I02: blocks.set/get/setRegion/getRegion и writes.buffered.

Для живого длительного задания сервер отправляет уведомление
`{"jsonrpc":"2.0","method":"system.progress","params":{"requestId":N}}`.
Оно относится к текущему головному запросу, не является ACK, не завершает flush
и не меняет порядок финальных ответов. Уведомление продлевает срок неактивности
запросов, ожидающих за той же головой; heartbeat отправляется не реже раза в
секунду, пока живое задание ждёт загрузку или выполняет область.
Произвольные уведомления клиента по-прежнему не исполняются.

Лимиты сервера I01: до 8 подключений; 512 входящих запросов и 512 исходящих
кадров на сессию; до 128 операций сессии и 512 суммарно за тик при бюджете
executor 2 мс. Это верхние пределы, не гарантированное число операций за тик:
бюджет времени и длительность setter также ограничивают обработку. Переполнение
серверной очереди не разрешает неограниченное накопление данных.
Продвижение уже активных заданий I02 имеет отдельный общий бюджет 2 мс за тик
и максимум 256 блоков задания за один проход. Это не обещание общего потолка
всего плагина в 2 мс; одна операция Paper с физикой также может занять больше.

Ошибки и сроки
--------------

Локальные ошибки типов, координат, формата блока и handshake обнаруживаются
до отправки соответствующего запроса. Серверные ошибки типизированы по
числовому коду, текст объяснения фиксируется клиентом и не копирует удалённые
сообщения или секретные параметры. Диагностика содержит `.code`, `.request_id`,
`.method`, `.outcome`. Для ошибки до создания RPC ID/метод равны `None`.

В buffered-режиме ошибка уже отправленной записи может быть сообщена следующим
вызовом записи (до принятия новой команды), `flush` либо `close`. Это ограничивает
накопление непрочитанных ошибок. Барьер собирает все ошибки охваченных операций,
выбрасывает первую по порядку ID и помещает все в её `.failures` tuple. После
сообщения эти ошибки считаются прочитанными; доменная ошибка сама по себе
не делает соединение непригодным. Фатальная ошибка протокола/сети закрывает его.

Срок по умолчанию — 5 секунд на сетевую стадию подключения/записи/ожидания
ответа; системное DNS-разрешение синхронно и находится вне TCP deadline.
Ожидание подтверждения ограничено даже без явного `flush`. В I02 live progress
продлевает срок неактивности, поэтому пять секунд не являются общим пределом
строительства или генерации. При потере связи/остановке heartbeat ожидание
заканчивается ошибкой. Публичный универсальный менеджер заданий не вводится.

Для обрыва/таймаута мутации `outcome="unknown"` применяется только после попытки
передачи её байтов: операция могла выполниться. До попытки отправки, а также
для немутирующего hello исход `not-applied`. Явная ошибка сервера сохраняет
объявленный исход. Автоматического повтора, reconnect и rollback нет.

Новые коды: REGION_BUSY=-32026, CHUNK_LOAD_FAILED=-32027. При ошибке до
изменений outcome=not-applied; если часть области могла быть изменена — unknown.

Критерий скорости I01 проверяется отдельно на локальном Paper: 100 инертных
блоков в загруженных чанках вместе с `flush` должны занять не более 0,5 секунды
в медиане пяти запусков при нормальных TPS. Этот критерий не является обещанием
скорости любого LAN-сервера; измеренные результаты фиксируются после проверки.

Добавления I03: игроки, контекст, селекторы и чат
------------------------------------------------

`PlayerRef` — неизменяемая ссылка с `uuid: UUID`, `entityId: int`, `name: str`;
наследует `LivingEntityRef` и `EntityRef`. Runtime ID может устареть после выхода
и повторного входа; операции используют UUID. `players.get` принимает имя,
UUID-строку, объект `UUID` или `PlayerRef`; `getPlayerEntityId` — текущий ник.
Ни один из этих методов не назначает SELF.

`create(..., player="CurrentNick")` после обычного hello разрешает онлайн-игрока
через `players.get` и сохраняет UUID. Ошибка привязки закрывает новое соединение.
Имя проверяется до DNS: 1–16 ASCII-букв, цифр или `_`. `withContext(player=...)`
создаёт фасад поверх того же соединения с отдельно сохранённым UUID; исходный
фасад не меняется. Допустимы также UUID и PlayerRef; `None` или отсутствие player
снимает привязку только у нового фасада. Закрытие любого фасада закрывает общее
соединение; повторное закрытие безопасно. Буфер, порядок и барьеры общие.
При выключенной авторизации привязка не подтверждает личность ученика.

Цели `list/getPos/teleport`: имя, UUID-строка/объект UUID, EntityRef, Selector,
vanilla-строка `@...` или явный список ссылок. Список передаётся как UUID,
дубликаты удаляются сервером с сохранением порядка. Пустой список допустим.
До первой мутации проверяется весь разрешённый набор: операции игроков требуют
игроков, а не любых сущностей. Селектор разрешается один раз на операцию.
Грамматику и значения фильтров разбирает `Server.selectEntities` закреплённого
Paper. Python не строит собственную грамматику и не выполняет команды сервера.

Статические типизированные константы `selector.ALL_PLAYERS`, `RANDOM_PLAYER`,
`NEAREST_PLAYER`, `SELF`, `ALL_ENTITIES` содержат соответственно `@a`, `@r`,
`@p`, `@s`, `@e`. Строки и константы используют один механизм исполнения.
Общий/случайный выбор и имя не требуют привязки. `@s` требует онлайн-исполнителя;
ближайшие цели и пространственные фильтры требуют его текущей позиции в мире
сессии. Если игрок перешёл в другой мир, пространственный запрос возвращает
`CONTEXT_WORLD_MISMATCH`; мир сессии сам не меняется. Простой `@s` не является
пространственным фильтром и продолжает ссылаться на связанного игрока.
Если связанный UUID больше не онлайн, запрос, которому нужен исполнитель,
возвращает PLAYER_NOT_FOUND. Можно дождаться входа того же игрока либо создать
фасад с новой привязкой; автоматического выбора другого ника нет.

Проверка требуемого контекста предшествует вызову серверного resolver. Поэтому
для некорректного пространственного селектора без исполнителя первой ошибкой
может быть `MISSING_CONTEXT`; при наличии контекста синтаксис проверяет Paper.
Это позволяет не выбирать случайную цель повторно ради проверки синтаксиса.

Конкретный отсутствующий игрок — `PLAYER_NOT_FOUND`; пустой групповой выбор
возвращает `[]` или `TargetResult(0, 0, ())`. `getPos` требует ровно одну цель,
иначе `INVALID_TARGET`. `Location` содержит `world, x, y, z, yaw, pitch`.
Телепортация сохраняет дробные координаты и ориентацию игрока; по умолчанию
назначение находится в мире сессии, явный world выбирает загруженный мир по
имени/ключу. Чанк назначения автоматически загружается/генерируется; ожидание
удерживает очередь этой сессии, другие сессии продолжают работу.

`TargetResult` содержит `matched`, `applied` и tuple `targets` из
`TargetOutcome(uuid, applied, code)`. Для успеха code=None; для неуспеха —
машинная причина. UUID уникальны, matched совпадает с количеством результатов,
applied — с количеством успешных целей. Выход игрока, отмена телепортации и
другие изменения после проверки отражаются по цели; общего отката нет.
Отключение TCP отменяет ожидание/не начатые действия и освобождает удержания.
Уже запущенная Paper teleportAsync может завершиться после отключения;
закрытие соединения не является отменой совершённой игровой операции.

`postToChat` рассылает буквальный текст всем онлайн-игрокам и пишет его в консоль.
Разметка `<red>` и `@a` внутри сообщения не интерпретируются. В buffered-режиме
подтверждение ожидается через flush/чтение/close; в sync — внутри вызова.
ACK означает серверную отправку сообщения, а не подтверждение показа клиентом.

Wire I03 (точные поля params/result):

| Метод | params | result |
|---|---|---|
| players.get | world, executor, target | player: {uuid,name,entityId} |
| players.list | world, executor, targets | players: [{uuid,name,entityId}] |
| players.getPos | world, executor, targets | location: {world,x,y,z,yaw,pitch} |
| players.teleport | world, executor, targets, position, destinationWorld | matched, applied, targets: [{uuid,applied,code}] |
| chat.post | message | applied:true |

world — имя мира сессии; executor — UUID-строка либо null, передаётся на каждый
запрос, а не изменяет серверный контекст подключения. target — имя/UUID-строка;
targets — непустая строка до 2048 Unicode-символов либо массив из 0–1024 UUID.
position — три конечных JSON-числа в int32-диапазоне, без округления вниз;
destinationWorld — имя/ключ либо null. message — 1–4096 Unicode-символов.
Фактическую высоту/границу назначения проверяет сервер до телепортации.
Handshake и major/minor 2.0 не меняются; новые методы объявляются capabilities.

Новые ошибки: PLAYER_NOT_FOUND=-32028, INVALID_SELECTOR=-32029,
MISSING_CONTEXT=-32030, INVALID_TARGET=-32031,
CONTEXT_WORLD_MISMATCH=-32032. Доменная ошибка до изменений имеет
outcome=not-applied и не закрывает исправное соединение. Частичный результат
телепортации передаётся через TargetResult, а не скрывается общим ACK.

Добавления I04: предметы, эффекты и создание сущностей
----------------------------------------------------

Модули `items`, `effects`, `entity` — статические `Final`-константы типов
`ItemKey`, `EffectKey`, `EntityTypeKey`. Типы не наследуются от str и не
подменяют друг друга. Принимаются также полные строки `namespace:path`;
импорт и подсказки не обращаются к серверу. Снимок закреплённого Paper build 133
содержит 1537 предметов, 40 эффектов и 158 реальных типов сущностей.
AIR присутствует в реестре предметов, но выдать/создать его предметом нельзя.
UNKNOWN не является ключом реестра сущностей и в каталоге отсутствует.

`ItemStack(material, amount=1, name=None, lore=None)` — неизменяемое описание.
material принимает ItemKey или строку; name и строки lore являются буквальным
текстом. Максимум 256 Unicode-символов имени, 16 строк lore по 256 символов.
Входной список lore копируется в tuple. Зачарования, произвольные компоненты
и NBT не входят в I04 и не принимаются молча как неиспользуемые параметры.

`giveItem` использует количество из ItemStack, либо 1 у ключа/строки.
Явный amount заменяет количество описания. Диапазон — 1..2304 на получателя;
сервер делит количество на настоящие допустимые стеки данного предмета.
Цели разрешаются один раз, проверяется весь набор игроков до первой выдачи.
Метод ждёт результата независимо от writeMode и является барьером предыдущих
buffered-записей. Выдача не повторяется при неизвестном результате связи.

`InventoryResult(matched, applied, targets)` содержит tuple InventoryOutcome:
`uuid, applied, code, requested, given, leftovers, dropped`.
leftovers — tuple ItemStack. Для каждой цели выполняется равенство
`requested = given + sum(item.amount for item in leftovers) + dropped`.
applied=True означает обработанную операцию, даже если полный инвентарь
вернул всё количество в leftovers. Дубликаты UUID не приводят к повторной выдаче.
Нормальное переполнение не является ошибкой протокола и не уничтожает предметы.

`overflow="return"` возвращает остаток без выбрасывания. `overflow="drop"`
явно создаёт непоместившиеся предметы рядом с получателем; отменённый плагином
ItemSpawnEvent оставляет это количество в leftovers. Отрицательные количества
и скрытое удаление остатков не допускаются. Если игрок вышел во время выполнения,
его исход содержит PLAYER_NOT_FOUND и ещё не выданное количество в leftovers.
Ранее выданное/выброшенное не откатывается.

`effects.add` использует тот же TargetResolver и контекст, но требует живые
сущности: игрока/моба/LivingEntityRef, включая UUID и vanilla-селекторы.
Весь набор проверяется до первого изменения; предмет или другая неживая
сущность в смешанном списке вызывает INVALID_TARGET без частичного эффекта.
duration — положительные конечные игровые секунды; округляем вверх до целого
числа тиков `ceil(duration * 20)` в диапазоне 1..2147483647.
level — 1..256, серверный amplifier равен level-1; particles — строго bool.
Результат TargetResult отражает применение по UUID; отказ Paper, например
из-за уже имеющегося эффекта, может дать applied=False/code=EFFECT_REJECTED.
Гарантированного изменения здоровья/AI для каждого типа эффекта не обещаем:
обычную игровую семантику определяет Minecraft.

`spawnEntity` и `entities.spawn` — одна реализация с разным порядком аргументов.
Координаты конечные, дробные, без округления вниз; высоту/границу и мир проверяет
сервер. world=None выбирает мир сессии, явный world — загруженный мир по имени
или ключу. Чанк назначения автоматически загружается/генерируется с общим
ChunkService, сессия сохраняет FIFO и heartbeat. Метод всегда ждёт результата.
Возвращается EntityRef, для живой сущности — LivingEntityRef, с UUID, entityId
и ключом фактического типа. Самостоятельно созданный ранее EntityRef может
иметь key=None; ссылка из spawn всегда содержит ключ. Игровой движок может
переместить или удалить сущность сразу после создания.
Удержание чанка покрывает создание, а не бессрочную симуляцию сущности.
Последующие тики AI, физики и молнии требуют обычных условий симуляции мира;
присутствие игрока рядом может иметь значение. Автозагрузка для одного вызова
не равнозначна постоянному vanilla force-load.

Матрица типов закреплена в `catalogs/paper-26.2-build133-game.json`:

| Тип | Параметры | Создание |
|---|---|---|
| 150 обычных типов | без дополнительных параметров | World.spawnEntity |
| ITEM | item=ItemStack/ItemKey/строка | World.dropItem, количество не больше одного настоящего стека |
| FALLING_BLOCK | block=BlockInput | World.spawnFallingBlock, AIR не допускается |
| LIGHTNING_BOLT | без дополнительных параметров | настоящая World.strikeLightning |
| PAINTING | face | картина 1×1, горизонтальное направление и твёрдая опора |
| ITEM_FRAME, GLOW_ITEM_FRAME | face | рамка с указанным направлением и твёрдой опорой |
| FISHING_BOBBER | owner | Player.launchProjectile(FishHook), затем установка позиции |
| PLAYER | не создаётся этим API | UNSUPPORTED_ENTITY_TYPE |

face — одна из строк north/south/east/west/up/down; для картины up/down
не допускаются. Указанная позиция должна быть свободной, опора — соседний
блок со стороны, противоположной face; нужный соседний чанк также удерживается.
owner — имя онлайн-игрока, UUID либо PlayerRef. Он разрешается один раз в UUID
и проверяется перед созданием; владелец должен находиться в мире назначения.
Поплавок подчиняется обычным условиям игры (удочка, дистанция и состояние
владельца); ссылка не обещает бессрочное существование поплавка.
Неподходящие либо недостающие параметры special-типа дают INVALID_ENTITY_TYPE
до создания; неподдержанный тип не подменяется другим мобом.
Молния реальна и может наносить урон/менять мир; визуальная молния её не заменяет.

Wire I04 (точные поля):

| Метод | params | result |
|---|---|---|
| players.giveItem | world, executor, targets, item, overflow | matched, applied, targets:[{uuid,applied,code,requested,given,leftovers,dropped}] |
| effects.add | world, executor, targets, effect | matched, applied, targets:[{uuid,applied,code}] |
| entities.spawn | world, destinationWorld, position, entity, options | entity:{uuid,entityId,key,living} |

ItemDTO: `{key, amount, name, lore}`; nullable name/lore обязательны как поля.
EffectDTO: `{key, durationTicks, level, particles}`. entity в запросе: `{key}`.
options содержит все четыре nullable-поля `{item, block, face, owner}`;
block имеет прежнюю форму `{key,states}`, owner на проводе — имя/UUID-строка.
world — закреплённый мир сессии, destinationWorld — явный мир создания либо null.
Общие правила UUID, int32, targets и чисел сохраняются из I03.
Новые методы объявляются capabilities; версия протокола остаётся 2.0.

Для give/effects — не более 1024 выбранных целей. До мутаций проверяется,
что консервативная верхняя оценка ответа помещается в 65536 байт. Иначе
LIMIT_EXCEEDED/outcome=not-applied. Длинные операции выполняются частями
в рамках дополнительного общего бюджета gameplay jobs 2 мс за тик;
одиночный вызов Paper может занять больше. Общий бюджет всего плагина в 2 мс
не обещается. Завершённые части при отключении/ошибке не откатываются.

Новые ошибки: INVALID_ITEM=-32033, INVALID_EFFECT=-32034,
INVALID_ENTITY_TYPE=-32035, UNSUPPORTED_ENTITY_TYPE=-32036,
ENTITY_NOT_FOUND=-32037. Ошибка подготовки — not-applied; отказ/сбой после
входа в мутацию может иметь unknown. Никаких автоматических повторов нет.
