Реализованный API
-----------------

```python
from minebridge.minecraft import Minecraft
from minebridge import selector

mc = Minecraft.create("localhost", 4711, player="CurrentNick")
try:
    print(mc.getPlayerEntityId("CurrentNick"))
    print(mc.players.get("CurrentNick"))
    print(mc.players.list())
    position = mc.players.getPos(selector.SELF)
    result = mc.players.teleport(selector.SELF, position.x, position.y, position.z)
    mc.postToChat("Привет из Python!")
    mc.flush()
finally:
    mc.close()
```

Два позиционных аргумента create сохранены. player необязателен; для обычных
блоков, общего выбора и чата не нужен. Привязка разрешает текущий ник в UUID
после обычного hello; поиск ID не назначает SELF. `withContext(player=...)`
создаёт новый фасад того же соединения, оставляя исходный без изменений.
`withContext()` снимает привязку у нового фасада. Закрытие любого фасада
дожидается записей и закрывает общее соединение для всех фасадов.

Константы selector: ALL_PLAYERS, RANDOM_PLAYER, NEAREST_PLAYER, SELF,
ALL_ENTITIES. Допустимы также vanilla-строки, например `@a[distance=..10]`,
имя, UUID, ссылка и список ссылок. Paper разбирает селектор один раз;
плагин проверяет весь выбранный набор перед первым изменением.
Игровые команды setblock/tp/say через dispatchCommand не вызываются.

PlayerRef содержит UUID, временный entityId и имя; свойства не делают запросов.
Location возвращает мир, дробные x/y/z и yaw/pitch. Телепортация сохраняет
дробные координаты/ориентацию и возвращает TargetResult с исходом по UUID.
Пустая группа допустима; getPos требует ровно одного игрока.
Чат передаёт буквальный текст всем онлайн-игрокам и консоли; его buffered-записи
подчиняются тем же flush/чтение/close, что и блоки.

Устройство и найденные исправления
---------------------------------

PlayerService и PaperPlayerBackend используют публичный API Paper.
PlayerJobManager удерживает FIFO-голову сессии при загрузке чанка и асинхронной
телепортации. Завершение проверяется на игровом потоке, heartbeat поддерживает
ожидание. Блоки и телепортация используют общий ChunkService с учётом удержаний;
завершение одного задания не освобождает ticket, нужный другому.

При проверке исправлены три дефекта: конкурентный close общих фасадов теперь
дожидается одного завершения, UUID существующего моба даёт INVALID_TARGET,
а допустимые vanilla-ключи в кавычках, например `@a["distance"=..5]`, корректно
требуют позиционный контекст. Значения и синтаксис по-прежнему проверяет Paper.

Селекторы работают для обычных игроков без выдачи OP. Это проверено игровыми
подключениями и bytecode закреплённого CraftServer.selectEntities: публичный
API отключает командную проверку прав на селектор. Он не превращает ученика
в оператора. Дополнительные роли/ограничения учебных действий в I03 не вводились.
Свидетельство исследования: .work/i03-selector-permissions-bytecode.txt.

Фактические проверки
-------------------

- 147 Python-тестов на каждой из версий 3.11 и 3.14; включая новые DTO,
  UUID-привязку, независимость фасадов, барьеры, частичный результат и close.
- 437 Java cases без ошибок; общий корпус протокола содержит 266 сценариев.
  После исправления текста Unicode-fixture отдельно повторены 266 Java cases
  и 29 Python-тестов протокола. Замороженный JAR не менялся.
- Девять компактных сценариев на Paper прошли целиком. Два настоящих игровых
  TCP-клиента вошли на локальный offline-стенд; observer независимо подтвердил
  их UUID/runtime ID. Они не являются искусственными Bukkit-игроками.
- Два независимых Python TCP-подключения: раздельный SELF, новая/снятая привязка,
  поиск ID без неявной привязки. Параллельные вызовы выполнялись в двух потоках
  одного Python-процесса; два отдельных процесса входят в общую приёмку I05.
- Проверены @a/@r/@p/@s, имя/UUID/ссылки, фильтр имени и расстояния относительно
  каждого игрока, ключ distance в кавычках, пустая группа и типизированные ошибки.
- Дробная телепортация подтверждена независимым observer. @e с мобом,
  UUID моба и смешанный список отклонены без перемещения любого игрока.
- Buffered setBlock → postToChat → синхронный поиск игрока: observer увидел блок,
  оба игровых клиента действительно получили пакет с уникальным сообщением.
  Проверялось получение пакета, а не визуальная отрисовка окна Minecraft.
- Два контекста одновременно телепортировали собственных игроков и отправили
  чат. Телепортация в ранее незагруженный чанк (1250,1250) привела игрока в
  (20000.25,220.5,20000.75), что независимо подтвердил observer. В этом сценарии
  также завершились действия второй сессии; runner не фиксировал условие
  «второй ответ строго раньше завершения телепортации». Продвижение другой
  сессии при гарантированно ожидающей teleport future проверено Java-тестом.
- После перехода исполнителя в Nether пространственный селектор вернул
  CONTEXT_WORLD_MISMATCH; общий выбор сохранился. Выход другого игрока дал
  PLAYER_NOT_FOUND для его SELF, не повредив оставшееся подключение.
- Paper остановился штатно с exitCode=0; собственные подключения/потоки закрыты,
  исходники и артефакты совпали с хешами прогона. Пользовательский сервер
  не изменялся; ранее принятое EULA скопировано без повторного принятия.

Границы
-------

Связанный игрок — контекст исполнения, а не подтверждение личности ученика.
UUID-ссылки пока не несут отдельного постоянного идентификатора сервера;
проверка переноса ссылок между разными серверами не обещается.
Пространственные селекторы требуют связанного онлайн-игрока в мире сессии.
Поддержка произвольного origin, локальных координат и pairing остаётся будущей.
Уже начатая teleportAsync может завершиться после отключения TCP; отката нет.
ACK чата означает серверную отправку, а не подтверждение показа сообщения.
