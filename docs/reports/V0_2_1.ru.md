Minebridge 0.2.1 — выход короткого скрипта и серверный журнал
==========================================================

26 октября 2026 года. Исправлен сценарий пользователя: `create(ip, port)`,
`setBlock`, `postToChat` и немедленный конец Python-программы.

Причина
-------

В 0.2.0 buffered-вызов возвращался после отправки запроса, до выполнения на
Paper. Поток приёма daemon не удерживал Python-процесс. При завершении скрипта
соединение закрывалось; сервер мог отменить ещё не начатые команды, а ответы
с ошибками некому было прочитать. Поэтому отсутствие исключения в таком коде
не доказывало выполнение. `flush()`/`close()` явно ожидали ответы и ранее,
но простой привычный учебный скрипт без них имел гонку с завершением процесса.

Регрессионная проверка сначала воспроизвела ранний сброс сокета на 0.2.0.
На Paper отдельно воспроизведено завершение старого установленного wheel с
exitCode=0 и неизменённым блоком при намеренно удержанном первом запросе.
Этот контроль делает гонку воспроизводимой, а не утверждает, что любой
быстрый запуск 0.2.0 всегда теряет каждую команду.

Изменения
---------

- После успешного hello транспорт регистрируется в слабом реестре нормального
  выхода Python. `atexit` дожидается записей через существующий `finish()` и
  закрывает соединение; явный `close()` удаляет его из реестра. Буферизация,
  окно, FIFO, таймауты, барьеры и отсутствие автоматического повтора сохранены.
- Ошибка во время неявного завершения выводится в stderr с типом, методом и
  request ID. Такой обработчик не меняет exit code; для исключения, которое
  можно обработать в программе, нужно явно вызвать `flush()`/`close()`.
  Принудительное завершение процесса не запускает этот обработчик.
- `Minecraft.create(..., logging: bool = False)` включает журнал одной сессии
  при true. Фасады `withContext` разделяют её настройку. Значения иных типов
  отклоняются до подключения. В hello добавлен необязательный boolean `logging`,
  в capabilities — `session.logging`. При False сохраняется старый запрос
  без нового поля. Для True требуется обновить серверный плагин.
- Сервер пишет `ACTION` в обычную консоль/`logs/latest.log`: session/request ID,
  метод, мир, сокращённые параметры, received/completed/error, результат или
  код ошибки. Лог успешного завершения создаётся после фактического исполнения;
  `ackQueued` описывает очередь ответа, а не его получение клиентом.
- Вывод в лог выполняется асинхронным заданием, отдельно от игрового потока
  и блокировок Session. Очередь ограничена 4096 строками, каждая строка — примерно
  2 КиБ. Переполнение имеет явный счётчик пропусков. Токен/hello-параметры
  не выводятся, управляющие символы экранируются, длинные значения сокращаются.
  Обычные сессии без флага не создают строки журнала действий.

Проверки
--------

- 470 Java-тестов без failures/errors/skips; включая общий корпус с тремя
  новыми hello-сценариями, изоляцию логирования сессий, результаты/ошибки,
  отсутствие токена, экранирование, ограничение буфера. `test shadowJar --offline`.
- По 170 тестов из установленного wheel на Python 3.11.17 и 3.14.7, без пропусков.
  Два новых subprocess-теста подтверждают ожидание ACK после конца тела скрипта
  и stderr при отложенной ошибке; проверены сигнатура/типы/согласование logging.
- Проверка упаковки 0.2.1: RECORD, sdist/wheel, версии JAR/Python, JSON-каталоги,
  py.typed, генераторы и изолированный офлайн-импорт обеих версий Python прошли.
- Настоящий Paper 26.2 build 133, JDK 25, отдельный мир и игровой TCP-клиент:
  шесть точечных сценариев прошли. Старый wheel воспроизводит потерю записи;
  новый ждёт отложенный запрос и завершает блок/чат без close, в том числе
  по координатам пользователя `(0,0,0)`. Состояние блока подтверждено независимым
  observer, чат — реальным игровым пакетом. Отдельно проверены logging off/on,
  серверная ошибка и её stderr при выходе, логи чтения/контекста/выдачи/эффекта/spawn.
  Сервер завершился штатно, exitCode=0, без ERROR, свои порты освобождены.

Обновление
----------

Заменить JAR при остановленном сервере и установить wheel 0.2.1 тем же
интерпретатором, которым запускается скрипт. Существующий конфиг сохраняется.
Пример:

```python
from minebridge import Minecraft, block

mc = Minecraft.create("192.168.0.200", 4712, logging=True)
try:
    mc.setBlock(0, 0, 0, block.COBBLESTONE)
    mc.postToChat("привет")
finally:
    mc.close()
```

Без `logging=True` серверный журнал действий выключен. Блок на y=0 обычно
находится под землёй; координаты отображения и выполнение команды — разные вещи.
