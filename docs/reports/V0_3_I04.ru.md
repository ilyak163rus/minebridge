## Результат

Реализованы mc.inventories.ofBlock/ofPlayer, InventoryRef.getItem/getContents/
setItem/clear и массовый players.setItem. Все операции синхронны и являются
барьером buffered writes. Старый giveItem сохраняет распределение/остатки;
setItem заменяет весь указанный стек и проверяет фактический результат.

Ссылка на игрока закреплена за UUID и содержит 41 публичный слот:0..35 и
slots.HEAD/CHEST/LEGS/FEET/OFF_HAND. BODY/SADDLE не открываются через этот API.
Сундук по умолчанию адресует физическую половину27; combined=True — Paper
left/right общий54 или27 для одиночного. Layout/UUID проверяются при каждом RPC,
чанки загружаются через общий ChunkService с временными leases.

InventoryRef/InventoryInfo/InventoryPart, ItemView и результаты записи неизменяемы.
ItemView не является lossless ItemStack и не принимается setter. Чтение
представляет известные поля и явно отмечает дополнительные данные/сокращение.
getContents собирает ограниченные страницы, сохраняя пустые слоты и их номера;
при layout error частичный словарь не возвращается.

## Настоящий сервер

Изолированный offline Paper с прежним принятым EULA, два игровых TCP-клиента
I04Alice/I04Bob и два отдельных source-Python OS-процесса. Независимый
test-only InventoryObserver читает native инвентари и SHA serializeAsBytes;
production capture/internal inventory service для oracle не вызывается.

1. Разные PID/sessionId, UUID refs, 41 публичный слот, withContext и ошибка
   ofPlayer для нескольких выбранных игроков.
2. Точная замена diamond16→emerald3 с previous/current, пустые слоты None,
   независимые native инвентари двух игроков.
3. 64 меча, amount0, hidden numeric slot и bool не изменяют содержимое;
   HEAD/OFF_HAND работают. Public clear очищает только41 слотов, сохраняя
   BODY и SADDLE и инвентарь другого игрока.
4. Plain name/lore остаются hasAdditionalData=False; ItemView setter отвергается
   до изменения целевого слота.
5. Два отдельных сундука, buffered setBlock→ofBlock barrier, одиночный combined,
   explicit другой загруженный мир без изменения config.
6. Double chest через границу chunks511/512: физические половины27 и общий54,
   metadata совпадает с native left/right, запись в общий слот53 подтверждена.
7. Split/merge инвалидируют старые combined refs; physical half остаётся своей
   половиной; trapped chest работает.
8. Plain/enchanted/rich-text/shulker/long предметы читаются повторно без изменения
   native SHA; additionalData/truncated выставлены; previous длинного предмета
   остаётся bounded при последующей замене.
9. 54 длинных предмета прочитаны **54 сетевыми страницами** в порядке0..53.
   После первой реальной страницы test-only hook разделяет сундук: SDK получает
   InventoryChangedError вместо частичного dict. Очистка physical half не
   затрагивает соседнюю, combined clear подтверждает все54 слота.
10. Дальний persisted сундук выгружен; ofBlock и последующий getItem снова
    загружают чанк, сохраняя записанный стек.
11. Bulk prevalidation ошибочного количества не меняет ни одного игрока;
    валидный селектор даёт TargetResult двух UUID, targeted clear не трогает Bob.
12. Offline UUID ref даёт PlayerNotFoundError; offline участник explicit bulk
    не приводит к частичной записи в ещё online игрока во время prevalidation.
13. После close метаданные остаются локальными, SDK-потоков не осталось.

На API133 оба скрытых слота реально доступны native observer: BODY с
LEATHER_HORSE_ARMOR и SADDLE с SADDLE после public clear сохранили прежние SHA.
Это положительная проверка, не пропущенный unsupported случай.

## Среда и границы

Windows x64, Temurin JDK25.0.4.1+1, Gradle9.1.0, прежний pinned Paper/API133
и bootstrap cache. Новых runtime-зависимостей нет.

| Вход | SHA-256 |
|---|---|
| Paper26.2-133 | bf1dcf627364f8a631ab15250d240eb5a8e89faaac523b391e1c61367fce9ff1 |
| Временный production dev4 JAR | 8105393d6d6a6b20f6727331867e02364b2db6600adfebe2ab69b3289b0b582d |
| Test-only observer JAR | 1cd21314f4819bda5dbc15c041ae6f9dca8c3cb179be24f5eade03401298672d |

Прямые inventory операции выполняются на game thread, без сетевого ожидания;
чанки ожидаются jobs асинхронно. Bulk prevalidation/изменения имеют ограниченные
порции128 и мягкий бюджет2ms, progress и round-robin. InventoryRef не создаёт
бессрочный реестр server handles. Страница ограничена32KiB, frame64KiB;
name/lore ограничены256codepoints/16×256 с явными flags.

getContents не является атомарным снимком против игрока/воронки/чужого плагина
между страницами. Частичные изменения после старта bulk не обещают rollback.
Офлайн-инвентари, другие типы контейнеров, opaque NBT и lossless copy/move в I04
не добавлены. LAN, пользовательский Paper99, полный класс и установленный wheel
не проверялись. Следующая I05 — совместная приёмка, VS Code и одна поставка0.3.
