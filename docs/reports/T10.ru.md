Приёмка T10
===========

Дата: 22 октября 2026 года. Статус: выполнено. Минимальный технический срез v0.1 принят.

На настоящем Paper проверены V01–V07, D01–D04, N01–N10 и F01–F05 по
[контракту v0.1-r1 / protocol 1.0](../contracts/V0_1_CONTRACT.ru.md) и
[плану приёмки](../PAPER_INTEGRATION_TEST_PLAN.ru.md). Основной прогон содержит
32 успешных unittest cases, без failures, errors и skipped. Это технический
прототип с четырьмя публичными вызовами: `Minecraft.create`, `mc.setBlock`,
`mc.blocks.setBlock` и `mc.close`. Полная совместимость с mcpi не заявляется.

Объём изменений
---------------

Python runtime не изменён относительно T09: все 15 файлов package payload
в wheel совпадают побайтно. Обновлены описание пакета/README и архивы поставки.
Wire 1.0, публичные сигнатуры, конфигурационные ключи и зависимости сохранены.
Новых RPC, публичного чтения блока, async/batch API или автоматических повторов нет.

В Java добавлены локальные диагностические счётчики очередей/кадров и управление
остановкой writer только через существующий Java-only TestControl. Управление
не является сетевой командой и публикуется только при явном локальном test flag.
Production write deadline остаётся 5 секунд. Observer отдельно читает Paper,
показывает счётчики и восстанавливает принадлежащие стенду позиции при shutdown;
он не использует ACK как источник истины о блоке.

Новые проверки находятся в [test_validation.py](../../integration/tests/test_validation.py),
[test_protocol_edges.py](../../integration/tests/test_protocol_edges.py),
[test_slow_reader.py](../../integration/tests/test_slow_reader.py),
[test_failures.py](../../integration/tests/test_failures.py) и
[test_shutdown.py](../../integration/tests/test_shutdown.py).
[Raw peer](../../integration/tests/raw_peer.py) обходит валидацию публичного Python,
а [fault proxy / controlled peer](../../integration/tests/fault_proxy.py) задают
точный момент удержания, потери или повреждения ответа. Существующая V/D-матрица
T09 повторно выполняется новым [orchestrator T10](../../tools/smoke_t10.py).

Стенд и границы доказательств
---------------------------

Windows x64, Paper 26.2 build 133, Temurin JDK 25.0.4.1+1 и Gradle 9.1.0
соответствуют [ENVIRONMENT_LOCK](../ENVIRONMENT_LOCK.ru.md). Paper SHA-256:
`bf1dcf627364f8a631ab15250d240eb5a8e89faaac523b391e1c61367fce9ff1`.
Основные клиенты — отдельные процессы CPython 3.14.7 с `-I`, импортирующие
установленный wheel из `.venv-t10-314/Lib/site-packages`. Перед стартом payload
установленного пакета сравнивается с выбранным wheel.

Основной запуск использует новый мир `t10-world`, seed `20261021`, UUID
`d335c1f6-b0d7-4342-9fdb-9351e3149446`, высоты `-64 <= y < 320`.
Bridge слушает `127.0.0.1:4711`; игровой порт и порты relay выбираются отдельно.
RCON/query выключены. Копируются bootstrap caches и ранее принятое оператором
согласие EULA; скрипт не принимает EULA автоматически и не копирует прежний мир.
F04 намеренно перезапускает тот же сохранённый мир, чтобы проверить восстановление
fixture и новый create после остановки.

Начальные состояния, реальные UUID/координаты, loaded-состояние чанков и материалы
подтверждает отдельный console-only Java observer. Oracle self-test проверяет
самого observer до V/D. Gate, полученный ответ, состояние очереди, фактический
Paper tick, server-close и proxy capture служат барьерами; заранее выбранная
пауза не считается доказательством исполнения или отмены.

Для успешной записи проверяется последовательность
`QUEUED → APPLY_BEGIN → APPLY_DONE → ACK_ENQUEUED` с корреляцией sessionId/requestId,
caseId, мира и координат. Setter и публикация ACK идут на главном потоке Paper;
`QUEUED` может принадлежать NIO-потоку. Диагностическая история ограничена
256 событиями. Полнота проверяется по checkpoint конкретной операции/случая;
старые события всей матрицы могут быть вытеснены. Это отличается от потери новых
событий: во всех проверенных интервалах `droppedEvents=0`. После группы
slow-reader сохранено 256 событий при `latestSequence=260, evictedEvents=4`,
после faults — при `latestSequence=278, evictedEvents=22`. Нулевая эвикция
истории всего прогона не заявляется.

Реальный slow reader N10
-----------------------

Числа очередей, tick и времени в этом разделе относятся к сохранённому
[финальному измерению a7095efcf83d441c90bee0858b443e02](../../integration/artifacts/t10-a7095efcf83d441c90bee0858b443e02/manifest.json).
Оба итоговых запуска приёмки перечислены отдельно ниже.

В [kernel-slow-reader](../../integration/tests/test_slow_reader.py) `SO_RCVBUF=1024`
установлен до connect; ОС вернула фактическое значение 1024. После hello клиент
не читает сокет до независимого подтверждения server-close. Отправлены 492
обычных запроса unknown method, по четыре за раунд; каждый следующий раунд
ожидает счётчик принятых полных кадров и завершение dispatch предыдущего.
Это 123 раунда и 216 наблюдений sessionStats, с конечными пределами нагрузки,
числа наблюдений, памяти и времени.

Реальная выходная очередь удерживает четыре кадра между tick 1047 и 1050,
без новых запросов и без чтения сокета. В этот период B успешно выполняет
setBlock, пока A всё ещё open и имеет четыре выходных кадра. `writerPaused=false`
на всём интервале; максимумы входной и выходной очереди равны четырём, ниже
лимита восемь. После write deadline A закрыта: `receivedFrames=493` с учётом
hello, обе очереди пусты. Только затем клиент читает 488 полных ответов,
67726 байт, и EOF; незавершённого хвоста в этом прогоне нет. Новый клиент
успешно проходит hello и применяет blocks.set. Полный case занял около
12,64 секунды; это наблюдение стенда, не SLA.

Отдельный `stalled-writer` честно отмечен как симуляция локальной остановки
writer, использующая неизменённый production deadline 5 секунд. Он проверяет
таймер и независимость B; реальный kernel case выше отдельно проверяет
нечитающего TCP-клиента. Переполнение выходной очереди создаётся локальным
pause для воспроизводимого точного предела, без предположений о размере OS buffers.

После подготовки закреплённого toolchain, установки wheel и наличия ранее
принятой EULA полный цикл запускается из корня проекта:

```powershell
.\.venv-tools\Scripts\python.exe tools/smoke_t10.py
```

Скрипт использует готовые артефакты: не скачивает сервер, не собирает проект,
не принимает EULA и не удаляет прежние evidence. Основной запуск проверяет

команды сборки и установки описаны в [DEVELOPMENT.ru.md](../DEVELOPMENT.ru.md),
команды стенда — в [integration/README.md](../../integration/README.md),
пользовательский старт — в [QUICKSTART.ru.md](../QUICKSTART.ru.md).

В run directory сохраняются manifest, логи Paper по режимам, unittest logs,
observer snapshots, sanitized wire/proxy captures и stdout/stderr клиентов.
Cleanup восстанавливает сохранённые fixture BlockData и снимает собственные
chunk tickets после завершения/отмены ожидающих операций. Это не обещание
отката побочной физики произвольного блока или долговечности ACK на диске.

LAN/сеть учебного класса не проверены: все реальные соединения выполнены на
loopback одного Windows-хоста. Нагрузка класса, другие ОС, SELF/игроки,
полная legacy-таблица, чтение/массовые операции, jobs и совместимость со
сторонними protection-плагинами остаются за границами минимального прототипа.
