Приёмка T04
===========

Дата: 20 октября 2026 года. Статус: выполнено.

Добавлен ограниченный TCP-транспорт Python/Java с независимыми соединениями
и корректным освобождением ресурсов. Успешный handshake, авторизация, выбор
мира и запись блоков относятся к T05/T06 и в этом этапе не реализованы.
Публичного Minecraft.create пока нет.

Реализация и границы
-------------------

- Java TcpServer использует один отдельный NIO reactor для bind/accept/read/write
  и закрытия каналов. Нет потоков на каждого клиента и неограниченного executor.
- Session хранит UUID соединения, входную очередь 8 запросов и выходную очередь
  8 кадров, включая частично передаваемый головной кадр. Максимум 8 соединений;
  девятое закрывается. Переполнение, EOF, notifications и неверные ID не оставляют
  ещё не начатые запросы в закрытой сессии.
- Размер/глубина остались 65536 байт/16 уровней. Абсолютные сроки handshake,
  сборки неполного кадра и передачи головного кадра — по 5 секунд. Частичный
  прогресс их не продлевает; idle READY разрешён через внутренний seam T05.
- BridgePlugin запускает транспорт асинхронно. Подтверждение bind/ошибка
  передаются обратно на поток Paper с проверкой актуальности экземпляра.
  onDisable только сигнализирует остановку, не выполняет socket IO и не ждёт join.
- Python TcpTransport устанавливает TCP и выполняет последовательные exchange
  с собственными возрастающими ID, одним владельцем чтения и одним ожидаемым
  ответом. close не ждёт RPC-lock и прерывает ожидание чтения/записи.
  Автоматических повторов, reconnect и фонового reader нет.
- Добавлены ConnectionError/OperationTimeoutError с машинными кодами и outcome.
  Повреждённый ответ после возможной отправки мутации не означает её отмену.

Production T04 проверяет оболочки и ограниченно ставит запросы в очередь,
но ещё не снимает их для исполнения и не переводит соединение в READY.
Полный корректный hello сейчас также завершится закрытием по сроку 5 секунд.
Обмен ответами в тестовом consumer не является работающим Minecraft API.

Выявленная техническая причина уточнения: проверка параметров в сетевом слое
мешала бы правильному запрету команд до handshake. Поэтому Java codec разделён
на decodeEnvelope и validateRequestParameters; строгий decodeRequest по-прежнему
объединяет их и проходит тот же общий корпус. Будущий router проверит состояние
сессии перед параметрами; wire-формат не менялся.

listenAddress теперь принимает числовой IPv4/IPv6. DNS при bind мог бы зависнуть
в неотменяемом вызове ОС и задержать shutdown; InetAddress.ofLiteral устраняет
эту зависимость. Имена вроде localhost в конфигурации listener отвергаются с
безопасной диагностикой. Python endpoint сохраняет поддержку IP/hostname,
включая localhost, однако время синхронного DNS не входит в общий TCP-connect
deadline. Отдельных resolver-потоков нет. Эти уточнения записаны в разделе 3
[контракта](../contracts/V0_1_CONTRACT.ru.md).

Транспортные тесты используют реальные loopback-сокеты: одновременные
соединения, дробление/склейка, EOF, неверные ID, границы очередей/соединений,
медленная передача и клиент, не читающий ответы, закрытие во время I/O,
занятый порт, повторные start/close и освобождение потоков/портов.
В тесте медленного читателя сначала наблюдается реально ожидающий головной
кадр; B отвечает, пока A ещё открыт. Это не проверка только после закрытия A.

В Windows отказ неблокирующего localhost-подключения на этом стенде наблюдался
примерно через 2 секунды. Для тестов отказа/hostname предусмотрены достаточные
сроки. Общий deadline разных адресов дополнительно проверен детерминированным
тестом с управляемым сетевым окружением/часами; он не заменяет loopback-проверки.

Реальный Paper подтвердил:

1. Bind и ответы на повреждённые оболочки; B отвечает, пока A держит неполный кадр.
2. Неверный UTF-8 A не останавливает B; повторный ID закрывает только своё соединение.
3. Девятый запрос переполняет очередь и получает LIMIT_EXCEEDED; его ID уже считается использованным.
4. Корректный hello не получает поддельного успеха и закрывается по сроку T04.
5. Stop закрывает два активных соединения; новый процесс успешно слушает тот же порт.
6. Занятый порт, пустой token, отсутствующий мир и некорректный YAML дают ожидаемые отказы.

Шесть запусков Paper: transport, restart, occupied-port, blank-token,
missing-world, invalid-yaml. Сценарий transport содержит несколько сетевых
проверок выше. В захваченном stdout токен отсутствует, неожиданных серверных
ошибок в успешных сценариях нет. Тестовые процессы после прогона остановлены.
Согласие на EULA использовано из ранее принятого оператором локального стенда.
LAN, настоящий успешный handshake и изменение мира пока не проверялись.
