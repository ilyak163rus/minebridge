## Результат

Реализован вертикальный срез: реальный чат игрока → AsyncChatEvent →
подписка Python → функция в явно вызванном run() → синхронная команда → ответ.
В I02 работает только events.CHAT_MESSAGE, с фильтрами игроков/мира.
Другие игровые события относятся к I03; работа со слотами инвентарей — к I04.

Есть subscribe/unsubscribe, run/poll/stop, независимые pollEvents/pollChatPosts,
getRecent и clearPending/clearAll. Снимки и результаты неизменяемы и типизированы.
SELF остаётся явно указанным исполнителем подключения; автор события — event.player.
Два withContext одного соединения разделяют dispatcher и курсор истории.

Живая доставка отделена от очереди RPC и журнала. Переполнение отмечает подписку
BROKEN и выдаёт EventOverflowError; потеря непрочитанной истории выдаёт отдельный
EventHistoryLostError без молчаливого изменения курсора. Записи начинаются после
hello, даже если до первого poll не было подписок. Сервер фиксирует внутреннюю
границу захвата до hello ACK и при регистрации подписки, чтобы ожидающий
нормализации старый чат не попадал к новому подписчику.

## Настоящий сервер

Стенд — отдельный локальный offline Paper с прежним принятым EULA, двумя настоящими
игровыми TCP-клиентами I02Alice/I02Bob и двумя отдельными source-Python процессами.
Тестовые игроки имеют OP, чтобы ограничение частоты чата не мешало короткому набору
сценариев. GameClient отправляет настоящий пакет чата закреплённого протокола;
независимый observer фиксирует AsyncChatEvent, включая отменённый чат, и читает
фактический инвентарь. Production event API для имитации события не вызывается.

1. Два игровых подключения и два разных Python PID/sessionId; старый чат до hello
   отсутствует в истории новой сессии.
2. i02-gift → callback в i02-explicit-callback-consumer → getBlock (ID 4), getRecent,
   giveItem. Observer подтверждает ровно один алмаз, оба игровых клиента видят ACK.
   Второй живой потребитель получает RuntimeError.
3. Первый poll обеих программ возвращает общий eventId; generic/alias/withContext
   делят курсор, getRecent повторяет чтение без его изменения.
4. clearAll одной сессии не очищает историю/подписки другой; SELF фильтрует live,
   а обычная история содержит чат обоих игроков.
5. Ручной live poll получает Unicode-сообщение и не потребляет pull-историю.
6. Отменённый native chat отсутствует в Minebridge; postToChat не создаёт
   обратное событие.
7. После unsubscribe новых callbacks нет; исключение функции выходит из run,
   последующий RPC продолжает работать.
8. stop из callback, stop в ожидании и close будят цикл, Python-потоки не остаются.
9. Переподключение получает новую базу истории; clearAll до первого pull учитывает
   ещё не читавшийся тип, другая программа продолжает работу.

Сервер штатно остановлен с exitCode=0, Lifecycle stopped; ошибок уровня
ERROR/SEVERE/FATAL нет, оба порта освобождены. У игровых клиентов errors=[].
После прогона проверены хеши 41 Python source-файла, скриптов и входных JAR.

## Входы и границы результата

Среда: Windows x64, Java 25.0.4.1+1, Gradle 9.1.0, закреплённые Paper/API build133
и прежние Gradle verification/lock файлы. Новые runtime-зависимости не добавлены.

| Вход | SHA-256 |
|---|---|
| Paper 26.2-133 | bf1dcf627364f8a631ab15250d240eb5a8e89faaac523b391e1c61367fce9ff1 |
| Временный minebridge-paper-0.3.0.dev2.jar | 02fe1755e29364696b1af09622546ee447947f188e319dea313987b56272ba51 |
| Test-only observer JAR | bca04ccc193f96c5f6d5a5cfdff6e62d8f6893612cbe074bdc0afa5493414c32 |

Журнал ограничен 4096 записями, 4 MiB закодированных данных и 2400 тиками на мир,
до 8 удерживаемых миров. Это бюджет данных, не точная верхняя граница heap JVM.
Очередь async ingress — 1024 сообщения плюс до восьми coalesced loss markers;
нормализация — до 128 единиц за тик. Бюджет 2 ms мягкий, проверяется между
единицами; одна нормализация с ограниченной рассылкой выполняется целиком.
serverTick считает тики Minebridge с начала serverEpoch, не fullTime мира.
Живые очереди — до 512 кадров, подписки — до 32 на соединение.

Граничные переполнения и потеря истории проверялись детерминированными unit/TCP
проверками; на Paper проверялся реальный положительный путь и lifecycle, без
массового flood. LAN, пользовательский build99, полный класс учеников и другие
версии Paper в этой итерации не проверялись. Повтор/постоянный replay, отмена
игрового события Python-функцией и гарантии exactly-once не входят в API.
