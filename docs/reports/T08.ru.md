Приёмка T08
===========

Дата: 21 октября 2026 года. Статус: выполнено.

Независимый observer и воспроизводимый стенд работают на настоящем Paper.
Gate удерживает запрос перед dispatch, не останавливая тики и другую сессию.
После release проверены реальный блок и порядок APPLY_DONE → ACK_ENQUEUED.
Один production JAR проверен с локальным test-control и без него.
Полная матрица V/D/N/F остаётся T09–T10; весь v0.1 ещё не объявляется завершённым.

Реализация
----------

- [Observer](../../integration/observer-plugin/README.md) — отдельный Gradle
  subproject :observer. Он принимает только локальные консольные команды,
  не открывает порт и не добавляет production RPC. Чтение BlockData вызывает
  Paper напрямую, без BlockService, Python-нормализатора или ожидаемого ACK.
- setup сохраняет исходные BlockData, явно загружает/удерживает чанки и очищает
  позиции. read проверяет loaded до чтения. unload восстанавливает позиции,
  снимает собственный ticket и ожидает фактического isChunkLoaded=false через
  задачи по тикам с deadline. cleanup восстанавливает блоки/border и свои tickets.
- JSON-снимки содержат caseId, отдельный requestId консольной команды, sequence,
  tick, threadId/primaryThread, фактические UUID/координаты/key/properties/BlockData.
  Для каждого ответа создаётся новый неизменяемый файл через временный файл;
  повторное использование correlation ID не исполняет команду снова.
- [TestControl](../../plugin/src/main/java/dev/minebridge/testing/TestControl.java)
  регистрируется как Java service только при -Dminebridge.testControl=true.
  По умолчанию service отсутствует. Gate проверяется перед dequeue головы
  ограниченной очереди Session, без дополнительной очереди, sleep или ожидания
  Python на игровом потоке. Case/request metadata ограничены 128 записями.
- Release возвращает запрос обычному executor. Close отменяет ожидающую запись;
  release отменённого запроса не оживляет её. Перед очисткой fixture TestControl
  проверяет gate и queued/active состояние явно отслеживаемых requestId case;
  при наличии работы возвращает CASE_BUSY до восстановления мира.
- Trace дополнен QUEUED/ERROR/CANCELLED, caseId, авторизованным контекстом мира,
  координатами и безопасными code/outcome. QUEUED/отмена могут выполняться на NIO;
  Paper API там не вызывается. Setter и успешная публикация ACK отмечаются на
  игровом потоке. Sequence присваивается в самих точках событий.
- Буфер публикации и независимая история содержат максимум по 256 событий.
  Drain журнала не уничтожает историю; droppedEvents/evictedEvents сообщаются
  явно. Сырые токены, строки мира из запроса и параметры ошибок не записываются.
- [Harness](../../tools/smoke_t08.py) использует стандартную библиотеку Python,
  установленный wheel и два отдельных процесса с -I. Внутренний session context
  читается только для test correlation; рабочие вызовы — публичные create/setBlock/close.
  Переменные окружения передают тестовый секрет; argv/manifest не содержат его.

Публичный Python API, wire 1.0, четыре production config-поля и зависимости
runtime сохранены. Observer не включён в production JAR. Новая зависимость
observer на bridge — compileOnly; отдельно закреплён его compile classpath.
Python-код совпадает с T07; пересобранный пакет обновляет описание этапа.
Parser исторического smoke T06 адаптирован к расширенным фазам trace, чтобы
сохранить совместимость T06/T07 harness с текущей диагностикой.

Настоящий Paper
---------------

Стенд Windows x64/loopback, Paper 26.2 build 133, JDK25. Каждый запуск harness
создаёт новую .work/t08-<runId>/server и мир t08-world с seed=20261021.
Копируются только bootstrap cache/libraries/versions, собственные два JAR и
ранее принятый оператором eula.txt; мир/плагины прошлого стенда не копируются.
Manifest содержит SHA исходного согласия от 20 октября; автоматического
принятия EULA нет. TCP bridge — 127.0.0.1:4711, игровой порт выбирается отдельно,
RCON/query выключены. Между двумя режимами одного прогона сервер перезапускается
в том же изолированном мире после восстановления fixture.

1. Observer проверяет себя на двух разных позициях, включая исходно непустую
   позицию minY. После очистки независимо читает AIR, затем разные STONE и
   COBBLESTONE. Неизвестный UUID даёт WORLD_NOT_FOUND. После cleanup новая
   подготовка подтверждает восстановленные исходные BlockData и снятые tickets.
2. Отдельный чанк явно загружается и удерживается, затем фактически выгружается.
   Повторный checkChunk подтверждает loaded=false/ticketHeld=false; spawn не
   используется как предположение о загрузке.
3. Два отдельных Python-процесса имеют разные PID/sessionId и одинаковый rpcId=2.
   После GATED запрос A остаётся queued: блок AIR, вызов не завершён, APPLY_BEGIN
   отсутствует. Пока A удержан, B успешно ставит STONE, observer читает его,
   а фактический tick увеличивается. После release A возвращает None, observer
   читает COBBLESTONE. Для обоих setter trace совпадает с UUID/координатами case
   и главным потоком observer; APPLY_DONE.sequence < ACK_ENQUEUED.sequence.
4. Во втором прогоне дополнительно вызван cleanup при GATED: CASE_BUSY,
   сохранённые gate/AIR/ticket и всё ещё ожидающий вызов подтверждены заново.
5. Close удержанной сессии даёт клиенту unknown; сервер отдельно подтверждает
   CANCELLED/закрытую сессию до setter. Release не возобновляет запись, позиция
   остаётся AIR, B продолжает работу. Противоречия нет: клиентская потеря связи
   сама по себе не доказывает отмену, её доказывает серверное наблюдение теста.
6. После рестарта без opt-in status показывает controlEnabled=false,
   gateArm отвечает CONTROL_DISABLED. Обычный публичный setBlock работает;
   независимое чтение подтверждает блок. Production SHA одинаков в обоих режимах.

В успешных trace-снимках droppedEvents=0 и evictedEvents=0. Барьеры опираются
на состояние gate/очереди/блока/тика и завершение вызовов, а не длительность sleep.
Оба Paper-процесса каждого прогона штатно остановлены; клиентские процессы
завершены, TCP/игровые порты освобождены. Токен не появился в журналах сервера
и клиентов; неожиданных серверных ERROR/SEVERE/FATAL нет.

Обычный cleanup защищает от ожидающих/начатых отслеживаемых requestId case,
но не от остальных requestId или будущих запросов RELEASED-сессии. Harness сначала дожидается
завершения RPC либо закрывает клиента и наблюдает отмену; cancelCase закрывает
связанные сессии перед аварийным восстановлением. Полнота последних trace-событий
при асинхронной остановке reactor здесь не обещается. Observer предназначен для
одноразового мира и инертных блоков, не для отката block entities/физики/диска.
LAN, другие ОС, нагрузка класса и полная fault-матрица пока не проверялись.

oracle, двумя процессами, FIFO и повторным чистым прогоном.
