Приёмка T06
===========

Дата: 20 октября 2026 года. Статус: выполнено.

Raw blocks.set проверяет и устанавливает один блок на основном потоке Paper,
затем публикует applied=true. Действительные блоки и порядок setter/ACK проверены
на Paper 26.2 build 133. Публичный Minecraft.create/setBlock — следующая T07;
полный observer/gate и сквозные испытания пользовательского API остаются T08–T10.

Реализация
----------

- BlockService отделяет правила записи от Paper через узкий Backend. В одном
  вызове проверяются мир и UUID сессии, фактические высоты, центр блока относительно
  border, точный материал и loaded-состояние. isChunkLoaded(floorDiv(x,16),
  floorDiv(z,16)) вызывается до getBlockAt.
- PaperBlockBackend использует точный Registry.MATERIAL.get, проверяет ключ,
  isBlock и отсутствие legacy. Неизвестный ключ, предмет вместо блока и посторонний
  namespace не заменяются AIR и не проходят permissive matchMaterial.
- Разрешение выбранного мира повторяется по UUID; замена мира с прежним именем
  не перепривязывает сессию. Неизвестное raw-имя получает WORLD_NOT_FOUND,
  существующий другой мир — PERMISSION_DENIED.
- Block.setType(material,true) устанавливает default BlockData с физикой.
  Повтор того же материала тоже вызывает setter и успешно подтверждается.
  Фактическое поведение setType проверено по закреплённому CraftBlock bytecode:
  он вызывает material.createBlockData(), затем setBlockData(data,applyPhysics).
- До setter ошибка имеет outcome=not-applied; после начала setter исключение
  имеет INTERNAL_ERROR/unknown. Откат и автоматические повторы не обещаются.
  Доменная ошибка сохраняет READY; отказ выходного транспорта после записи
  не отменяет уже выполненную операцию.
- RequestRouter заранее кодирует успешный кадр, вызывает BlockService и только
  после нормального завершения ставит ответ в ограниченную очередь Session.
  Существующие FIFO, round-robin и бюджеты GameExecutor сохранены.
- Session.tryBeginOperation атомарно определяет начало операции относительно
  close. Закрытие до него отменяет setter; после него начатая операция может
  завершиться без доставки ответа. Marker снимается в finally; во время Paper
  API/физики monitor Session свободен.

Выявленная техническая причина уточнения border: закреплённый
CraftWorldBorder.isInside(Location) преобразует Location через BlockPos и теряет
дробную часть. Поэтому для согласованного центра x+0.5/z+0.5 адаптер сравнивает
точные границы из публичных getCenter/getSize, ограниченные getMaxWorldSize.
Нижние края включены, верхние исключены. Unit-тесты проверяют дробные края и
нестандартный абсолютный предел; реальный Paper — border размера 1 с дробным
центром. Для движущегося border политика определена публичным снимком getSize,
а не внутренней интерполяцией Minecraft. Уточнение записано в
[контракте](../contracts/V0_1_CONTRACT.ru.md), wire 1.0 сохранён.

Временное исключение T05 закрыто: capability blocks.set теперь реально реализована.
Других production RPC, блоковых состояний, legacy-пар, игроков/SELF или selector API
T06 не добавляет. Python runtime-код прежний; обновлён README пакета.

Диагностика
-----------

OperationTrace выключен по умолчанию. Локальный JVM-параметр
-Dminebridge.diagnostics=true включает ограниченный буфер 256 событий.
APPLY_BEGIN/APPLY_DONE расположены непосредственно у setter. ACK_ENQUEUED
фиксируется внутри публикации кадра Session, пока writer ещё не может его получить.
Под lock выполняется только короткая запись метаданных; sink/журнал вызывается
при drain вне Session lock. Ошибка диагностического hook не меняет опубликованный ACK.

Событие содержит sequence, phase, sessionId, requestId, applySequence, threadId,
primaryThread. Нет токена или произвольных параметров запроса. При переполнении
учитываются пропуски: такой trace неполон и не служит полным доказательством.
Диагностика не управляется через сеть. World/position и gate полного observer
запланированы в T08. Вывод журнала находится вне бюджета операций; результаты
не являются измерением производительности класса.

границы памяти, drop count, последовательности и отказ диагностического sink.

Настоящий Paper
----------------

tools/smoke_t06.py использует ранее принятый EULA локального .work/t02-server.
Отдельная console-only fixture integration/fixtures/block_smoke_probe не зависит
от bridge и не открывает порт. Она готовит/удерживает тестовые чанки, независимо
читает BlockData, проверяет loaded-состояние и временно меняет border. При нормальной
остановке восстанавливает затронутые блоки/border и снимает свои tickets. Её JAR
собирается отдельно и после прогона удаляется со стенда.

Проверены:

1. STONE, COBBLESTONE, AIR, современный oak_planks и повтор того же блока.
   После каждого ACK независимый консольный read совпал с ожидаемым BlockData.
2. Запись в загруженной отрицательной позиции и отказ для фактически незагруженного
   отрицательного чанка (-4097,4096); состояние проверено до/после, чанк не загрузился.
3. Неизвестный/запрещённый мир, отсутствующий блок, предмет, другой namespace,
   неправильный ключ, непустой states, высоты вне диапазона, дробный/bool/overflow
   raw-ввод и неизвестные поля. Отказы not-applied сохраняли контрольный блок и READY.
4. Текущий WorldBorder, верхние X/Z края при размере 1, принятие центра внутри.
5. Две одновременно открытые raw TCP-сессии с разными UUID и совпадающими ID.
   По три запроса в каждой получили FIFO ACK; два итоговых блока независимо проверены.
   Это два соединения/потока одного harness, не два пользовательских Python-процесса T09.
6. Stop с двумя READY, повторное занятие того же порта и запись после restart;
   занятый порт, пустой token конфигурации, отсутствующий мир и неверный YAML.

В итоговом прогоне 14 успешных мутаций/42 события в blocks и 1/3 в restart.
Порядок сравнивался по sequence, присвоенному в точках событий; время доставки
stdout/TCP для этого не использовалось. Полный управляемый gate T08 не реализован.
Токен отсутствовал в серверном выводе, неожиданных ERROR/SEVERE/FATAL в итоговых
сценариях нет; тестовые процессы и listener завершены.

Во время подготовки стенда обнаружены и исправлены две ошибочные предпосылки:
Windows reader мог мешать замене result.tsv, а Paper оставлял соседний с ticket
чанк загруженным. Теперь результат публикуется в уникальный immutable файл,
а loaded-only использует независимо проверенный дальний чанк. Точное различие
floorDiv/усечения доказывается unit-тестами. Первые неуспешные попытки сохранены
в .work/t06-paper-first-attempt* и second-attempt*; итоговые шесть сценариев
полностью повторены после исправлений. Production-код из-за этих проблем не менялся.
