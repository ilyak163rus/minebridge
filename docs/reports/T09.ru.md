Приёмка T09
===========

Дата: 21 октября 2026 года. Статус: выполнено.

Проверена полная успешная матрица V01–V07 и совместная работа D01–D04 на
настоящем Paper. Установленный Python-пакет проходит цепочку create → hello →
setBlock → Paper setter → ACK → None. Независимый observer читает фактические
блоки, а trace доказывает исполнение setter на главном потоке и публикацию ACK
после APPLY_DONE. Полная матрица N01–N10/F01–F05 остаётся задачей T10.

Объём изменений
---------------

Runtime Python, Java-плагин и observer JAR сохранены из T08 без изменений.
Публичный API, wire 1.0, конфигурация и зависимости не расширялись. Чтение блока
для проверки выполняет отдельный observer; публичный getBlock не добавлен.
Архив dist/t09 содержит точные копии четырёх проверенных артефактов T08.

Добавлены [матрица V](../../integration/tests/test_vertical_slice.py),
[матрица D](../../integration/tests/test_two_sessions.py),
[общие проверки](../../integration/tests/t09_support.py),
[пассивный relay](../../integration/tests/wire_tap.py) и
[orchestrator](../../tools/smoke_t09.py). Существующие fixtures и worker
расширены только тестовыми командами выбора формы блока, повторного create и
наблюдения незавершённого вызова. Все изменения находятся в стенде.

Relay работает на loopback между установленным клиентом и настоящим bridge.
Он принимает полный JSON/LF-кадр и передаёт его исходные байты, включая
терминатор, без изменения. Это меняет TCP segmentation/время передачи; relay
не является прозрачным средством проверки partial-frame, malformed-input или
сетевых сбоев T10. Порядок, число кадров и корреляция подтверждаются фактически
захваченными запросами/ответами. Поле token удаляется до сохранения hello,
остаточные вхождения секрета редактируются. Секрет не записывается в evidence.

Для relay действуют отдельные конечные ограничения: кадр 65536 байт, максимум
256 кадров, 16777472 байт и 32 соединения. Эти ограничения стенда не заменяют
проверку production-лимитов. Локальные smoke с двумя соединениями проверяют
сохранение байтов LF/CRLF, корреляцию, копии снимков, редактирование токена и
завершение ресурсов. Отдельные случаи oversized/невалидного JSON/неполного EOF
проверяют отказ самого relay без сохранения сырых данных. Это не проверки
обработки такого ввода Paper-плагином.

Стенд и доказательства
---------------------

Закреплённые Windows x64, Paper 26.2 build 133, Temurin JDK 25.0.4.1+1,
Gradle 9.1.0 и SHA Paper сохранены из [ENVIRONMENT_LOCK](../ENVIRONMENT_LOCK.ru.md).
Клиенты запускаются CPython 3.14.7 с -I; import выполняется из установленного
wheel в site-packages. Перед стартом все файлы package payload сравниваются
с выбранным wheel. Исходный каталог python/src не используется для импорта.

Каждый прогон создаёт новую директорию .work/t09-<runId>/server и новый мир
t09-world с seed=20261021. UUID мира получается из hello и независимого
observer; между чистыми прогонами он различается. Копируются только bootstrap
cache/libraries/versions, два собственных JAR и ранее принятое оператором
согласие EULA от 20 октября. Автоматического принятия EULA и копирования мира
предыдущего прогона нет. Bridge слушает 127.0.0.1:4711, relay и игровой порт
получают отдельные локальные порты; RCON/query выключены.

Перед V/D каждый раз выполняется oracle self-test T08: начальные AIR,
независимые STONE/COBBLESTONE, UUID/координаты, ошибка неизвестного мира,
восстановление исходных BlockData и снятие собственных chunk tickets.
Observer явно загружает/удерживает чанки. Факт их загрузки не выводится из
близости к spawn. V01 отдельно получает из консоли Paper фактический ответ
«There are 0 of a max of 1 players online».

A и B — разные процессы установленного Python, с разными PID/sessionId и
одним тестовым токеном из окружения. Они одновременно присутствуют READY в
одном Paper-процессе. Одинаковые hello id=1 и blocks.set id=2 допустимы в
разных соединениях. Один общий токен не доказывает персональные квоты учеников.

Проверки по сценариям
--------------------

| ID | Фактическое доказательство |
|---|---|
| V01 | Возврат create после успешного hello; wire и session context совпадают: protocol 1.0, действующий мир/UUID/высоты, absolute, loaded-only, applyPhysics=true, capabilities=[blocks.set] и все закреплённые limits. Token получен из env. Paper подтверждает отсутствие игроков. |
| V02 | Четыре отдельные позиции AIR и root setBlock через 4, LegacyBlock(4,0), block.COBBLESTONE и modern key. Каждый вызов возвращает None; observer читает cobblestone, trace содержит завершённый setter и ACK. |
| V03 | Те же четыре формы через mc.blocks.setBlock; реальные wire params совпадают с root. Дополнительная повторная запись того же блока успешна. Учтены ровно шесть blocks.set: один root reference, четыре namespace-вызова и повтор; скрытых запросов/getBlock нет. |
| V04 | -0.2 нормализован в -1, соседний x=0 остался AIR; положительные дроби проходят floor. minY и maxYExclusive-1 записываются. maxYExclusive даёт CoordinateOutOfBoundsError/COORDINATE_OUT_OF_BOUNDS/not-applied: только QUEUED/ERROR, без setter; соседние позиции и прежние записи подтверждены observer. |
| V05 | После GATED запрос queued, позиция AIR, клиент не завершён, ACK/APPLY_BEGIN отсутствуют. Фактический tick увеличивается до release. Затем None, новый блок и APPLY_DONE.sequence < ACK_ENQUEUED.sequence. |
| V06 | STONE, затем COBBLESTONE одной сессии в одной позиции. ACK и публичный возврат первой предшествуют отправке второй; requestId и applySequence возрастают; итог cobblestone. Это последовательный публичный API, проверка уже принятой FIFO очереди остаётся N07/T10. |
| V07 | Два close одного объекта, попытка записи через закрытый объект даёт ConnectionError/CONNECTION_LOST/not-applied без нового кадра. Новый create в том же Python-процессе получает новый sessionId; старое соединение удалено, завершённый блок сохранён, новая запись работает. |
| D01 | Два разных PID и sessionId удерживаются одновременно READY в одном Paper-процессе. У обоих hello id=1, ответы принадлежат своим connectionId/sessionId. |
| D02 | До ожидания ответа отправлены два публичных id=2: A удержан gate, B действительно завершает запись другой позиции. Тики продолжаются, A остаётся AIR/queued. После release A тоже успешен; материалы и ответы не смешались. |
| D03 | Два разных материала в одной позиции, обе сессии живы. Итог сравнивается с материалом последнего фактического applySequence, определённого trace; победитель не назначается по имени клиента или порядку TCP send. |
| D04 | Выбран предусмотренный планом вариант: разрыв A через публичный close при GATED. Клиент A получает unknown, отдельно сервер доказывает CANCELLED/not-applied до setter и пустую очередь. Release не возобновляет A, его позиция AIR; та же READY-сессия B выполняет записи до и после разрыва. Повреждённый raw-кадр остаётся T10. |

Каждое успешное применение сопоставлено по caseId, sessionId, requestId, миру
и координатам. В trace ровно QUEUED → APPLY_BEGIN → APPLY_DONE → ACK_ENQUEUED;
setter и ACK имеют тот же главный threadId, что независимый observer.
QUEUED может быть на NIO и не считается доказательством потока setter.
Доказательства не опираются на заранее выбранное число миллисекунд ожидания:
используются завершение команд, состояние очереди/gate, trace и фактический tick.

Результаты
----------

Финальная ревизия прошла дважды в новых мирах, без failures/errors/skipped:

| Прогон | Oracle | V/D | Всего unittest cases | Paper exitCode |
|---|---|---|---|---|
| [7299b619f8cd432dbbdb86d8b7fdabe7](../../integration/artifacts/t09-7299b619f8cd432dbbdb86d8b7fdabe7/manifest.json) | 1 | 11 | 12 | 0 |
| [fe1c5c7f86aa41b5ae0cc762454e35e0](../../integration/artifacts/t09-fe1c5c7f86aa41b5ae0cc762454e35e0/manifest.json) | 1 | 11 | 12 | 0 |

В каждом из этих прогонов wire.json содержит 85 кадров: 43 запроса и 42 ответа,
16 hello, 27 blocks.set. Из операций с блоками 25 успешно вернули None, одна
отклонена по maxYExclusive, одна отменена при закрытии A без ACK. Никаких
повторов/reconnect для незавершённой операции не выполнялось. Все 16 захваченных
соединений закрыты; relay не зарегистрировал ошибок.

Сводка .work/t09-paper-results.json имеет allPassed=true. SHA артефактов и
исходников тестов совпали между прогонами и сохранились во время испытаний;
runId/UUID мира различаются. В конце каждого прогона подтверждены пустой список
production-сессий, все закрытые relay-соединения и 104 события trace с
droppedEvents=0/evictedEvents=0: 27 QUEUED, по 25 APPLY_BEGIN/APPLY_DONE/ACK_ENQUEUED,
один ERROR и один CANCELLED. Неожиданных ERROR/SEVERE/FATAL в Paper нет.
Процессы worker/Paper завершились, игровые/bridge/capture порты освобождены;
токены отсутствуют в сохраняемых журналах и JSON.

Незавершённость вызова подтверждается упорядоченной командой worker, а не
только пустой очередью reader orchestrator. Ограниченный join перед следующим
вызовом устраняет гонку между публикацией результата и выходом worker-thread.
Предварительные два успешных прогона до усиления этих барьеров сохранены в
.work/t09-preliminary-paper-results.json и собственных директориях evidence;
итоговая приёмка относится к двум финальным runId из таблицы.
Сводки проверки архивов и evidence: .work/t09-artifacts.json и
.work/t09-final-checks.json; отдельная проверка процессов — .work/t09-process-check.json.

Локальный relay smoke выполнен на CPython 3.11.17 и 3.14.7; evidence сохранены
в .work/t09-wire-tap-smoke-*.json, отказы лимитов/парсинга — в
.work/t09-wire-tap-bound-*.json. Fixture-free discovery не запускает Java,
реальные server cases пропускаются без явно переданного стенда. Unit suites
runtime в T09 заново не запускались: приложения не менялись. Подтверждённые
381 Java cases и по 122 Python-теста на 3.11/3.14 относятся к [T08](T08.ru.md).

В каждой директории integration/artifacts/t09-<runId> находятся manifest,
журнал Paper, unittest log, независимые observer-снимки, wire.json и результаты
отдельных worker-процессов. Cleanup восстанавливает сохранённые BlockData и
собственные tickets после завершения RPC/закрытия клиентов; это восстановление
подготовленных инертных позиций в текущем мире, а не откат диска, block entities
или побочных эффектов произвольной физики. Не обещается долговечность записи
на диске только на основании ACK.

Сеть учебного класса/LAN, другие ОС, нагрузка класса, N01–N10 и F01–F05 этим
этапом не закрываются. Следующая самостоятельная задача — T10: валидация,
ограниченные ресурсы и управляемые сбои по оставшейся матрице, включая FIFO
двух уже queued raw-запросов N07 и семантику unknown без автоматического retry.
