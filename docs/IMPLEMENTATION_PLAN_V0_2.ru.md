План разработки Minebridge v0.2 — пять итераций
==============================================

Обновлено: 25 октября 2026 года. Все пять итераций завершены;
[I01](reports/I01.ru.md), [I02](reports/I02.ru.md), [I03](reports/I03.ru.md),
[I04](reports/I04.ru.md), [I05](reports/I05.ru.md),
[активный контракт](contracts/V0_2_CONTRACT.ru.md).
Итоговые JAR/wheel 0.2.0 находятся в [dist/v0.2](../dist/v0.2/README.ru.md).
Совместная приёмка выполнена на этих файлах: два отдельных Python-процесса,
два игровых подключения, два новых основных мира при неизменном конфиге.
Поставку I01 сохраняем как историю; она содержит лишь часть нынешних функций.

Основание — требования пользователя от 22 октября и
[целевая архитектура](../ARCHITECTURE.ru.md). Работающий v0.1 и его отчёты
сохраняются как история. Ниже явно заменяются четыре ограничения v0.1:
обязательные имя мира и токен, синхронная запись по умолчанию и loaded-only.
Это изменения по запросу пользователя, а не незаметная смена старого контракта.

Пять итераций означают пять законченных пакетов работ. Подготовка контрактов
и необходимые проверки входят в эти итерации; отдельных T00–T10 для v0.2
не будет. По уточнению пользователя после I01, промежуточные поставки JAR/wheel
больше не собираются: единая поставка — в конце v0.2, на I05. Для проверки
исходников на Paper в I02–I04 использовалась временная сборка в build/,
Python проверялся из исходников. На I05 проверены установленные итоговые wheel
и JAR. Итерация завершается примером и перечнем
реально работающих методов. Уже выданные артефакты I01 сохраняются как история.

1. Результат версии
-------------------

```python
from minebridge.minecraft import Minecraft
from minebridge import block, entity, items, effects, selector

mc = Minecraft.create("192.168.0.200", 4712)
try:
    for x in range(100):
        mc.setBlock(x, 80, 0, block.COBBLESTONE)
    mc.flush()

    mc.setBlocks(0, 80, 2, 10, 85, 10, block.STONE)
    block_id = mc.getBlock(0, 80, 2)
    region = mc.getBlocks(0, 80, 2, 2, 80, 2)
    # Например: {(0, 80, 2): 1, (1, 80, 2): 1, (2, 80, 2): 1}

    players = mc.players.list()
    player_id = mc.getPlayerEntityId("CurrentNick")
    position = mc.players.getPos("CurrentNick")
    mc.players.teleport("CurrentNick", 0, 85, 0)
    mc.players.giveItem(selector.ALL_PLAYERS, items.IRON_SWORD, 1)
    mc.effects.add(selector.ALL_PLAYERS, effects.SPEED, duration=30, level=2)
    zombie = mc.spawnEntity(5, 85, 5, entity.ZOMBIE)
    lightning = mc.spawnEntity(8, 85, 5, entity.LIGHTNING_BOLT)
    mc.postToChat("Постройка готова!")
finally:
    mc.close()
```

Это пример для итоговой v0.2.0, не для исторической v0.1. Ник и IP примерные;
4712 удобен, если RaspberryJuice продолжает занимать 4711. В плане используем
правильное написание `spawnEntity` для упомянутого пользователем `spawnEnitiy`.

В v0.2 входят все перечисленные пользователем области. Не входят scoreboard,
титры/action bar, события Python, серверные правила, undo, сохранение проектов,
pairing, обязательные аккаунты учеников, клиентские моды и новые версии Paper.
Сущности и состояния блоков не означают произвольное редактирование NBT,
содержимого контейнеров или создание нового типа блока/моба на клиенте.

2. Решения, которые определяют реализацию
-----------------------------------------

Мир и конфигурация
~~~~~~~~~~~~~~~~~~

- В `config.yml` больше не требуется `defaultWorld`. По умолчанию выбираем
  основной Overworld по ключу измерения `minecraft:overworld`, независимо от
  имени папки. Конкретный публичный вызов проверяем на закреплённом build 133
  в первой итерации. Порядок списка миров не используется как контракт.
- Handshake возвращает фактически выбранные имя, ключ и UUID мира. Сессия
  закрепляется за UUID: пересозданный мир с прежним именем не становится
  незаметно целью уже работающего подключения. После пересоздания — новое
  подключение; после перезапуска сервера новый основной мир выбирается сам.
- Если основной мир недоступен, плагин выдаёт понятную диагностику. Он не
  создаёт произвольный мир и не выбирает текущего случайного игрока.
- Необязательный явный `world` сохраняется для адресного выбора другого мира;
  для обычного `create(ip, port)` никакие имена не нужны.
- Мир контекста не переключается вслед за телепортацией игрока неявно.

Авторизация
~~~~~~~~~~~

Обычная конфигурация учебного сервера:

```yaml
listenAddress: '127.0.0.1'
port: 4711
authEnabled: false
token: ''
```

Для LAN преподаватель один раз меняет адрес прослушивания. `authEnabled`
по умолчанию `false`: отсутствие токена в коде и переменной окружения допустимо,
пустой токен не мешает запуску, токен не требуется ни для одной обычной операции.
В этом режиме доступ к слушающему порту даёт доступ к учебному API без личной
авторизации; не обещаем изоляцию по личности ученика.

При явном `authEnabled: true` непустой токен снова обязателен. Сохраняются
необязательный Python-параметр `token` и `MINEBRIDGE_TOKEN` для этого режима.
Выбор игрока через `player` остаётся контекстом исполнения, а не авторизацией.

Миграция существующего конфига входит в I01: старый `defaultWorld` принимается
как устаревшее, игнорируемое поле с однократным сообщением; старый `token`
без `authEnabled: true` не включает авторизацию. Значение секрета не журналируется.
Без необходимости не перезаписываем пользовательские сетевые настройки.

Запись, ответы и производительность
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

```python
Minecraft.create(ip="localhost", port=4711, *, writeMode="buffered",
                 token=None, player=None, world=None, timeout=5.0,
                 coordinates=None)

mc.flush() -> None
mc.close() -> None
```

- Два привычных позиционных аргумента сохраняются. Допустимы `writeMode="buffered"`
  и `writeMode="sync"`; любое другое значение сразу вызывает ошибку аргумента.
- По умолчанию `setBlock`, `setBlocks`, `postToChat` возвращаются после принятия
  операции в ограниченный поток отправки. Нормализация аргументов выполняется
  до постановки; серверные ошибки могут обнаружиться позднее.
- Клиент передаёт несколько запросов без ожидания ответа на каждый; ответы
  сопоставляются по ID и принимаются независимо от вызовов `flush()`. Нужен
  единственный владелец чтения сокета, а не конкурирующие читатели.
- `flush()` ждёт завершения всех операций, принятых до его вызова, и сообщает
  отложенные ошибки с методом, ID и исходом. Буфер и окно запросов ограничены;
  при заполнении применяется ожидание освобождения места, а не потеря команд.
- `getBlock/getBlocks`, поиск ID, список/позиция игроков, spawn и методы с
  `TargetResult/InventoryResult` ждут реального результата. Они также являются
  барьером предшествующих операций; публичные Future и `async/await` не нужны.
- В режиме `sync` методы записи ждут исполнения, как в v0.1. Режим не меняет
  проверки, систему координат или физику операции.
- Обычный `close()` дожидается ожидающих операций, затем закрывает ресурсы.
  При ошибке всё равно закрывает соединение. Обрыв сети и истечение сроков
  не должны создавать вечное ожидание. Повторный `close()` безопасен.
- Короткий сетевой timeout не считается максимальной длительностью всей
  стройки/генерации: для длинной операции нужны ответы о живом задании и
  отдельное ожидание завершения. Мёртвое соединение обнаруживается ограниченно.
- Внутри сессии сохраняется порядок фактического исполнения. Загрузка чанка
  или длительный `setBlocks` удерживает голову этой сессии. Другие сессии при
  этом продолжают работать. Завершённая запись видна последующему чтению,
  если её не изменил другой участник мира.
- Нет автоматического повтора при неизвестном результате: это относится и к
  выдаче предметов, созданию мобов, молнии. Общей транзакции и отката нет.

Цель скорости для I01: на контрольном локальном Paper при нормальных 20 TPS,
в заранее загруженной области и с инертными блоками, 100 последовательных
`setBlock` в buffered-режиме вместе с `flush()` должны укладываться в 0,5 секунды
в медиане пяти запусков. Это критерий выбранного стенда, не обещание для любого
компьютера или генерации новых чанков. Фиксируем также 1000 блоков, режим sync
и два подключения, без выдуманного заранее результата.

Нынешние dev-лимиты 4 операции/сессию/тик, 32 суммарно и 2 мс не становятся
неизменяемым требованием v0.2. Настраиваем их по фактическому завершению записей
и состоянию Paper. Поднятие лимита само по себе не заменяет оконную отправку.

Чтение ID и современные блоки
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

Сохраняем уже согласованное разделение совместимого и современного API:

```python
mc.getBlock(x, y, z) -> int
mc.getBlocks(x1, y1, z1, x2, y2, z2) -> dict[tuple[int, int, int], int]

mc.blocks.getBlock(x, y, z) -> BlockSpec
mc.blocks.getBlocks(x1, y1, z1, x2, y2, z2) -> dict[tuple[int, int, int], BlockSpec]
```

- У современных блоков нет исторических числовых ID. Не выдаём номер Java enum,
  временный registry ID или выдуманное число за совместимый ID mcpi.
- Корневые чтения используют проверенную обратную legacy-таблицу. Если
  соответствия нет, возвращается `UnsupportedLegacyBlockError`; групповой
  вызов не возвращает частичный словарь как успешный полный результат.
- Для полного современного мира предназначены `mc.blocks.*`: например,
  `BlockSpec("minecraft:oak_stairs", {"facing": "east", "half": "bottom"})`.
  Корневое числовое чтение не является способом сохранения состояний.
- `getBlocks` возвращает абсолютные координаты, включает обе границы,
  принимает переставленные углы; координаты округляются вниз. Внутренняя
  передача идёт страницами с ограничением объёма, не одним гигантским JSON.
- Большое чтение не обещает атомарный снимок мира при чужих изменениях.
- Каталог `block.*` покрывает блоки закреплённой 26.2: старые совместимые имена
  остаются `LegacyBlock`, современные — `BlockSpec`. Таблица чисел расширяется
  по проверенным соответствиям, отдельно от полноты современного каталога.
- Строковая форма `minecraft:oak_stairs[facing=east,half=bottom]` и `BlockSpec`
  поддерживают свойства. Сервер валидирует свойства через свой BlockData API.
  Произвольные состояния не означают автоматической установки второй половины
  многоблочной конструкции или изменения block entity/NBT.

Чанки и области
~~~~~~~~~~~~~~~

- По умолчанию обращение к незагруженному чанку запускает загрузку; если чанк
  ещё не существует — генерацию. Это относится к чтению, записи, spawn и
  точке назначения телепортации. Предварительно подходить к месту не нужно.
- Загрузка не блокирует игровой поток ожиданием Future. На время операции
  чанки удерживаются и затем освобождаются; повторные загрузки объединяются.
- Удержание общее для плагина: нужен счётчик пользователей каждого чанка,
  чтобы завершение одной сессии не снимало удержание другой.
- Большие области обрабатываются порциями с ограничением одновременно
  загружаемых/удерживаемых чанков. Высота, граница мира и объём всё равно
  валидируются. Ошибка границ не является ошибкой незагруженного чанка.
- Сохраняется ранее предусмотренное резервирование области длительного
  строительства внутри нашего API: конфликтующая мутация получает
  `RegionBusyError`. Это не блокировка действий игроков, физики или других
  плагинов. Освобождение резерва/чанков обязательно и при ошибке/закрытии.
- После окончательного закрытия сессии незавершённая стройка отменяется,
  уже применённая часть остаётся. В v0.2 не делаем публичный универсальный
  менеджер заданий: необходимое исполнение и ожидание остаются внутренними.

Игроки, селекторы и результаты
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

- `mc.getPlayerEntityId(name) -> int` возвращает текущий runtime ID онлайн-игрока
  и не меняет контекст. `mc.players.list() -> list[PlayerRef]`; ссылка содержит
  UUID, имя и текущий ID. Отсутствующее имя — понятная ошибка.
- `mc.players.getPos(target) -> Location` требует ровно одного игрока.
  `Location` содержит мир, x/y/z и ориентацию. Перемещение:
  `mc.players.teleport(targets, x, y, z, *, world=None) -> TargetResult`.
- Выбор целей: текущий ник, UUID, `PlayerRef`, константа `Selector` и стандартная
  строка `@...`. Цель разрешается сервером один раз непосредственно перед
  операцией. Не пишем собственную неполную грамматику Minecraft-селекторов.
- Константы: `ALL_PLAYERS`, `RANDOM_PLAYER`, `NEAREST_PLAYER`, `SELF`,
  `ALL_ENTITIES`. Для операций игроков допустимы только игроки; для эффектов
  — живые сущности. Ошибки типа не превращаются в молчаливый пропуск.
- Весь разрешённый список целей проверяется до первого изменения. Если цель
  исчезла или изменилась уже во время исполнения, это отражается в результате
  по цели; откат ранее выполненных действий не обещается.
- `create(ip, port)` не угадывает SELF по IP. Для SELF ученик указывает
  `player="CurrentNick"` в create либо использует
  `mc.withContext(player="CurrentNick")` поверх той же сессии. Между занятиями
  ник и компьютер могут меняться. В рамках привязки сохраняется UUID.
  withContext возвращает новый фасад, не изменяя исходный контекст.
- SELF без привязки вызывает `MissingContextError`. Ближайшая цель и фильтры
  расстояния требуют определённой точки отсчёта — в v0.2 это выбранный игрок
  в согласованном мире. Произвольный конструктор origin не является условием
  выпуска. Общие/случайные игроки и выбор по имени не требуют SELF.
  Если выбранный игрок перешёл в другой мир, пространственный селектор
  возвращает ошибку контекста до изменений; мир сессии не переключается.
- `@a` сохраняет значение всех игроков, а не неявно «только я». При выключенной
  авторизации преподаватель разрешает общий учебный доступ без токена.
- Неверный селектор — ошибка, корректный пустой групповой выбор даёт matched=0.
  `TargetResult` отражает matched/applied и результаты по UUID. Ошибка одного
  этапа не обещает отката уже выполненных действий.
- `mc.players.giveItem(targets, item, amount=None, *, overflow="return")`
  возвращает `InventoryResult` с остатками. Полный инвентарь не уничтожает
  непоместившиеся предметы; `overflow="drop"` явно выбрасывает остатки.
- `mc.effects.add(targets, effect, *, duration, level=1, particles=True)`:
  duration — игровые секунды, level=1 — первый уровень. Результат TargetResult.
- `mc.postToChat(message)` отправляет обычное сообщение всем онлайн-игрокам;
  в buffered-режиме завершение можно ожидать через flush/close.

Каталоги и создание сущностей
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

- `block`, `entity`, `items`, `effects`, `selector` — статические типизированные
  Python-модули с подсказками без сервера. Не нужны отдельные классы на каждый
  материал или динамическое создание имён только после подключения.
- Для полных каталогов блоков/предметов/эффектов/сущностей используем снимок
  закреплённого Paper 26.2 build 133 с воспроизводимым генератором и версией
  данных. Экспорт/генератор — инструмент разработки, не лишний production RPC.
- В `entity.*` представлены все реальные типы из реестра целевой версии,
  в том числе `LIGHTNING_BOLT`. Служебное UNKNOWN не считается типом Minecraft.
  В метаданных различаем обычное создание, специальный адаптер/обязательные
  параметры и тип, не создаваемый таким способом.
- Канонический метод `mc.spawnEntity(x, y, z, entityType, ...) -> EntityRef`
  ждёт результата и возвращает UUID/тип/runtime ID созданной сущности.
  Точные дополнительные параметры специальных типов фиксируются по снимку
  перед реализацией I04, с аннотациями и подсказками.
- Полный каталог не означает, что игрока или любой технический тип можно
  создать только по координатам. Для выброшенного предмета нужен предмет,
  для падающего блока — описание блока; для прочих специальных типов
  составляется явная матрица. Не подменяем неподдержанный тип свиньёй.
- `LIGHTNING_BOLT` входит в обязательную поставку и создаёт настоящую молнию,
  с её игровыми последствиями. Визуальная молния без урона не является
  неявной заменой этой операции.

3. Пять итераций и зависимости
-------------------------------

Порядок: I01 → I02 → I03 → I04 → I05. Внутренние подзадачи выполняются в
рамках соответствующей итерации; каждая не требует отдельного согласования.
Точные wire-схемы фиксируются вместе с реализуемым методом, а не проектируются
сразу на весь будущий Minecraft API.

I01. Простое подключение и быстрый поток записей
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

Цель: привычный create(ip, port), отсутствие токена и имени мира, быстрый
цикл setBlock с подтверждённым завершением. Доступен writeMode="sync".

Работы и компоненты:

- Зафиксировать короткий `docs/contracts/V0_2_CONTRACT.ru.md`: настройки,
  hello, версии, очередь, flush/close, FIFO, результаты/ошибки. Полные схемы
  следующих методов добавляются по ходу следующих итераций.
- Из-за несовместимой семантики вводим wire-протокол 2.0, отдельные
  `protocol/v2/` fixtures. v0.1 архивен; автоматическую совместимость старого
  клиента с новым плагином не реализуем. Несовпадение версий — понятная ошибка.
- Изменить `BridgeConfig`, `config.yml`, `BridgePlugin`, `WorldContext`,
  `SessionManager`, `RequestRouter`, codec и session/transport.
- Изменить Python `_handshake.py`, `_protocol.py`, `_transport.py`,
  `minecraft.py`, `api/blocks.py`, `errors.py`: окно запросов, один независимый
  получатель ответов, буфер, flush, оба режима, ограниченное завершение.
- Изменить `GameExecutor`/`ExecutionLimits`: обработка готового потока без
  искусственного ожидания тика после каждой команды и подбор бюджетов.
  Вызовы мира остаются на разрешённом игровом потоке.
- В начале итерации проверить доступность необходимых публичных API на нашем
  JAR: автоматический Overworld, async chunks, сущности/спецтипы, селекторы с
  выбранным игроком. Это короткая проверка технических оснований, не новая фаза.

Результат: пакет I01; старый пример цикла работает в buffered-режиме,
в этой итерации ещё в загруженных чанках. Ограничение снимается в I02.

Приёмка и необходимые проверки:

- Без мира/токена create(ip, port) успешен. После пересоздания основного мира
  и перезапуска сервера конфиг не меняется; проверяется фактический новый мир.
- Явно включённая авторизация работает; старый конфиг мигрирует определённо.
- 100 блоков + flush: цель ≤0,5 с в медиане пяти замеров на описанном стенде;
  измеряется подтверждённое исполнение, а не только скорость постановки.
- Buffered и sync дают одинаковый итог, все подтверждения разобраны;
  отложенная ошибка видна в flush/close, соединение и поток приёма завершаются.
- Два подключения одновременно продвигаются; заполнение ограниченной очереди
  не вызывает взаимной блокировки. Тайм-аут не приводит к скрытому повтору.

Риски: взаимная блокировка читателя/писателя, потеря ошибок при close,
слишком большой игровой бюджет, сравнение времени отправки с временем мира.

I02. Блоки, состояния, области и автоматические чанки
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

Зависимость: I01. Цель: все четыре root-метода блоков, современное чтение,
каталог block.*, состояния и работа вдали от игроков без подготовки чанков.

Работы и компоненты:

- Дополнить контракт и протокол операциями чтения, областей, страниц и
  внутреннего длительного задания; описать лимит объёма и частичное выполнение.
- Python: `models/blocks.py`, `block.py`, `_data/`, `api/blocks.py`,
  `minecraft.py`, модели результатов и ошибки; `compat/`, новый `catalogs/`
  со снимком/генератором и проверенной обратной таблицей старых ID.
- Java: расширить `BlockService`/`PaperBlockBackend` для BlockData и чтения;
  добавить ChunkService, внутренний JobManager и резервирование областей;
  интегрировать их с GameExecutor, сессиями и очисткой ресурсов.
- setBlocks передаёт область один раз, затем выполняется частями. Последующие
  команды сессии не обгоняют стройку. getBlocks передаётся страницами.
- Автозагрузка/генерация с дедупликацией, общим подсчётом удержаний и
  освобождением при любом завершении; долгую генерацию не выдаём за сетевую тишину.

Результат: пакет I02 и примеры лестницы, бревна, чтения словаря координат/ID,
постройки области в незагруженном/ещё не сгенерированном месте.

Приёмка и необходимые проверки:

- Одиночная установка/чтение, все границы области, переставленные углы,
  отрицательные координаты и словарь с ожидаемым числом элементов.
- Чтение после buffered setBlocks видит завершённую запись своей сессии.
- Состояния лестницы и ось бревна сохраняются после установки/чтения;
  неверное свойство даёт понятную ошибку.
- Каталог покрывает серверный снимок; legacy-ошибка нового блока объяснена,
  тот же блок читается современным методом без потери состояний.
- Запись и чтение в удалённом чанке работают без игрока; две сессии не снимают
  удержания друг друга. Ошибка/закрытие освобождает ресурсы.
- Область не замораживает остальные сессии; конфликтующий резерв даёт
  RegionBusyError, окончание/отмена освобождает резерв.

Риски: стоимость генерации, память большого словаря, физика и многоблочные
конструкции, потеря порядка во время async loading, утечка chunk tickets.

- Ожидание/чтение/close обнаруживают отложенные ошибки, остановка сервера

- Повторный замер 100/1000 блоков и загрузки нового чанка отдельно; показатели

- Установка итогового wheel в чистый venv, загрузка итогового JAR, один проход
  VS Code/Pylance по публичным методам и каталогам, короткая пользовательская

отчёт с фактическими результатами и оставшимися ограничениями.

различия build 133 и пользовательского build 99, неверное сравнение скорости.
Если нет двух игровых клиентов, это явно незавершённая ручная проверка, а не
повод подменять её двумя TCP-соединениями и объявлять всё проверенным.

4. Как ограничиваем объём проверок
----------------------------------

- Не создаём отдельную тестовую итерацию для каждого внутреннего класса.
  Новые тесты защищают пользовательское поведение и существенные границы.
- На I01–I04 — проверки изменённой логики и короткий Paper-сценарий этой
  возможности. Сохраняем полезные существующие тесты, актуализируем ожидания
  намеренно изменённого контракта; исторический протокол v1 не выдаём за v2.
- На I05 — один объединённый прогон, упаковка и одна IDE-проверка. Повторы
  нужны при исправлении обнаруженной ошибки, а не ради количества запусков.
- Обязательны только значимые риски новой функциональности: порядок/барьеры,
  быстрый поток без deadlock, чанки, числовые соответствия/состояния, контекст
  целей, специальные сущности, две сессии и освобождение ресурсов.
- Результаты компактны: что изменено, как пользоваться, что проверено,
  какой JAR/wheel устанавливать. Не требуется большой отчёт на каждый метод.

5. Проверенные основания и оставшиеся технические вопросы
---------------------------------------------------------

Работающий код v0.1 и его ограничения прочитаны локально. Текущая библиотека
выполняет только один ожидаемый RPC за раз; GameExecutor вызывается раз в тик,
действуют dev-лимиты 4/32/2 мс. Именно этот обмен меняется в I01.

Публичная документация Paper 26.2 подтверждает поиск мира по ключу,
асинхронную загрузку/генерацию, plugin tickets, селекторы и создание молнии.
Онлайн-документация на момент просмотра уже обозначает build 134, поэтому
компиляция и фактическое поведение на нашем build 133 проверяются в I01.
Ни новая скорость, ни v0.2 в целом пока не измерены и не реализованы.

Источники технических оснований:

- [Server: мир по ключу](https://jd.papermc.io/paper/26.2/org/bukkit/Server.html#getWorld(org.bukkit.NamespacedKey)).
- [World: чанки, tickets и молния](https://jd.papermc.io/paper/26.2/org/bukkit/World.html).
- [EntityType: каталог и isSpawnable](https://jd.papermc.io/paper/26.2/org/bukkit/entity/EntityType.html).
- [Server.selectEntities](https://jd.papermc.io/paper/26.2/org/bukkit/Server.html#selectEntities(org.bukkit.command.CommandSender,java.lang.String)).
- [Game ticks и планировщик](https://docs.papermc.io/paper/dev/scheduler/).

В начале I01 нужно закрыть только технические основания, которые влияют на
реализацию: выбор основного мира на закреплённом build, контекст стандартных
селекторов и перечень специальных spawn-случаев. Полная классификация реестра
и параметры её адаптеров доводятся в I04. Это работа исполнителя, а не запрос
пользователю повторно выбрать уже указанные им требования.

Первая самостоятельная реализация — I01 целиком. Она завершена, когда
установленные JAR+wheel подключаются двумя аргументами без токена/имени мира,
режим по умолчанию действительно buffered, sync доступен явно, цикл 100 блоков
вместе с flush проходит целевой замер, ошибки не теряются и два подключения
работают одновременно. Только после этого переходим к I02.
