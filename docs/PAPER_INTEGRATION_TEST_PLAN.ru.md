Интеграционные проверки минимального среза на Paper
=================================================

План подготовлен 15 октября 2026 года. Состояние на 21 октября: матрица V/D
пройдена в T09, N/F остаётся T10; сборка и жизненный цикл стенда
проверены в [T02](reports/T02.ru.md), транспорт на Paper и отдельном
межъязыковом стенде — в [T04](reports/T04.ru.md). Авторизация, выбор мира и две
одновременные Python-сессии на Paper проверены в [T05](reports/T05.ru.md);
операции с блоками этим прогоном не проверялись. Raw blocks.set, два TCP-соединения,
независимое консольное чтение и диагностический порядок setter/ACK проверены в
[T06](reports/T06.ru.md). Публичная цепочка create→setBlock→None проверена в
[T07](reports/T07.ru.md) двумя отдельными Python-процессами. В
[T08](reports/T08.ru.md) проверены независимый observer, реальная выгрузка чанка,
gate с продвижением тиков/сессии B, release/отмена и обычный режим того же JAR.
[T09](reports/T09.ru.md) дважды выполнил все V01–V07/D01–D04 на свежих мирах,
с сопоставлением реальных RPC, trace и чтения Paper. N01–N10/F01–F05 остаются T10. Связан с
[планом задач](IMPLEMENTATION_PLAN.ru.md) и
[контрактом r1](contracts/V0_1_CONTRACT.ru.md).

1. Что требуется доказать
------------------------

Реальная цепочка: установленный Python-пакет → TCP → hello → blocks.set →
выполнение Paper setter на главном потоке → ACK → возврат None. Два отдельных
Python-процесса держат соединения одновременно, не смешивают ответы/контексты
и не мешают друг другу при ошибке одного клиента.

Mock/поддельный TCP peer полезен для модульных проверок, но не заменяет эти
сценарии. Снимок экрана и applied=true также не являются достаточным oracle.
getBlock не добавляется в публичный API только ради тестов.

2. Стенд и воспроизводимость
---------------------------

Используется отдельный чистый временный экземпляр настоящего Paper 26.2,
не учебный мир. Сборка выбирается и фиксируется T02: серверный JAR URL/SHA-256,
Paper API dependency, JDK/vendor/patch, Gradle wrapper/checksum, Python,
версии и SHA production JAR, observer JAR и wheel. Не подменять build на latest
между прогонами. Сборка 133-stable, её доступность и запуск проверены в T02;
точные значения — в [ENVIRONMENT_LOCK.ru.md](ENVIRONMENT_LOCK.ru.md).

Согласие оператора на EULA получено в чате 20 октября 2026 года для локального
стенда проекта. Инструменты и Paper загружены в T02, автоматического принятия
EULA в скриптах нет. Firewall и рабочая сеть не менялись.

Начальные условия:

- Один настроенный defaultWorld; из hello/observer известны его имя, UUID,
  minY/maxYExclusive. Его UUID сравнивается между источниками, не хардкодится.
- Временная директория и фиксированная конфигурация мира; сторонних плагинов,
  кроме production bridge и observer, нет. Игроки для этого среза не нужны.
- Два тестовых чанка с положительными/отрицательными координатами и отдельный
  кандидат для проверки unload. Observer явно загружает и удерживает нужные
  чанки; факт проверяется через API. Не считать spawn гарантией загрузки.
- Рабочая высота выбирается из фактических границ. Позиции observer очищает
  и читает до запуска случая. Используются AIR, STONE, COBBLESTONE без опоры
  на случайные тики, жидкости, редстоун и многоблочные конструкции.
- Сервер слушает loopback:4711; токен урока передаётся двум процессам через
  окружение стенда. Совпадение токена намеренно: sessionId всё равно различны.
- A и B — отдельные процессы Python из установленного wheel, не две переменные
  в одном процессе. Orchestrator управляет барьерами и собирает результаты.

Для реального применения в классе дополнительно проводится smoke через LAN
с двух компьютеров. Это проверяет маршрут/порт/настройку слушателя; без такой
проверки не заявляем, что сеть класса уже настроена. Устройство LAN пока неизвестно.

3. Независимое наблюдение и внутренний trace
------------------------------------------

В integration/observer-plugin создаётся отдельный test-only Java-плагин.
Он получает команды от orchestrator через stdin/консоль процесса Paper,
а не через новый сетевой порт. Асинхронный вывод сопоставляется по caseId.

Минимальный контракт observer:

| Действие | Результат |
|---|---|
| setup(caseId, world, positions) | Явная загрузка/удержание чанков, подготовка и снимок начального состояния |
| read(caseId, world, position) | Самостоятельный вызов Paper API и canonical BlockData, world UUID, координаты, server sequence/tick |
| unload/checkChunk(caseId, chunk) | Снятие своих удержаний, ожидание подтверждённого unloaded-состояния либо конечная ошибка setup |
| cleanup(caseId) | Снятие удержаний и очистка своего временного состояния |

Это названия тестовых действий, не команды production-протокола. Snapshot
читается на main thread напрямую из World/Block; observer не вызывает
BlockService/normalizer и не берёт наблюдаемый материал из ожидаемого ACK.
Сравниваем canonical key и свойства, а не ненадёжный порядок текста свойств.

Флаг mainThread в snapshot доказывает поток observer, а не поток записи.
Поэтому в GameExecutor/адаптере непосредственно перед setter нужен guard и
внутренний trace: connection/sessionId, requestId, applySequence, world/position,
признак главного потока, стадии QUEUED/APPLY_BEGIN/APPLY_DONE/ERROR/CANCELLED.
ACK_ENQUEUED фиксируется в точке публикации успешного ответа socket writer.
Для всех этих стадий eventSequence назначается атомарно в точке события;
в частности, запись ACK_ENQUEUED не откладывается до последующего чтения логов.
Проверяется APPLY_DONE.eventSequence < ACK_ENQUEUED.eventSequence того же запроса.
Секреты в trace исключены. Один глобальный applySequence отражает реальный
порядок записей на main thread, а не порядок прихода TCP-пакетов.

Для проверки ACK-after-apply нужен внутренний gate до APPLY_BEGIN. Он удерживает
задание в очереди и сразу возвращает управление игровому циклу, не выполняет
sleep/ожидание Python на main thread. Освобождать gate может только локальный
тестовый observer через внутренний Java test-control seam. Этот seam не
добавляет сетевого метода, не читает ожидаемый результат за observer и по
умолчанию отключён. Один и тот же production JAR тестируется с gate и без него;
в обычной конфигурации доступного удалённо test-control нет.

Удержание чанков, независимое чтение/восстановление, фактическая выгрузка и
test-control проверены на закреплённом Paper в T08. Команды воспроизведения —
[integration/README.md](../integration/README.md). Gate удерживает голову очереди;
cleanup возвращает CASE_BUSY до изменения fixture, если запрос ещё ожидает.

Проверка oracle до основных тестов: observer сам подготавливает две разные
позиции и читает их; проверяет UUID и координаты; ошибается на неизвестном мире;
cleanup освобождает свои chunk tickets. Нельзя принимать все тесты, если
наблюдатель не смог подтвердить исходное состояние.

4. Успешный путь и семантика V01–V07
----------------------------------

| ID | Действия | Доказательство / критерий приёмки |
|---|---|---|
| V01 | create(ip,port) с токеном из env | Hello завершён до возврата; protocol=1.0, действующий world/limits/capabilities; нет зависимости от присутствия игрока |
| V02 | setBlock в исходный AIR поочерёдно через 4, LegacyBlock(4,0), block.COBBLESTONE и modern key | None после успешного ответа; observer на четырёх отдельных позициях читает cobblestone; trace содержит завершённый setter |
| V03 | Повтор V02 через mc.blocks.setBlock; запись того же блока ещё раз | Те же wire-параметры и результат; повтор успешен, лишних сетевых запросов/скрытого getBlock нет |
| V04 | Координаты -0.2, положительная дробь и граничные значения допустимой высоты | Изменена позиция после floor, x=0 не задет при x=-0.2; minY допустим, maxYExclusive отклоняется до изменения |
| V05 | Arm gate, отправить запись, дождаться GATED/QUEUED, прочитать исходный AIR, отпустить gate | До release нет ACK/записи; eventSequence доказывает APPLY_DONE < ACK_ENQUEUED; после клиентского ACK независимый observer видит новый блок; tick не блокировался |
| V06 | Две последовательные записи одной сессии в одну позицию: STONE затем COBBLESTONE | Возврат/ACK первой до отправки второй; applySequence возрастает; итог COBBLESTONE; никакого вывода о межсессионном порядке |
| V07 | Идемпотентный close, затем новый create | Сокет/очереди освобождены, новый sessionId; завершённый блок сохранён в текущем мире; закрытый объект больше не пишет |

V04 сначала проверяет конечные значения локальными тестами T01: bool, NaN и
Infinity не должны достигать сервера через официальный клиент. Raw-ввод
проверяется отдельно, чтобы не принять клиентскую валидацию за серверную.

5. Две одновременные сессии D01–D04
----------------------------------

| ID | Действия | Доказательство / критерий приёмки |
|---|---|---|
| D01 | Запустить A/B, пройти hello и удержать оба соединения барьером | Один и тот же Paper process, интервалы соединений перекрываются; sessionId различны; hello id=1 допустим у обоих |
| D02 | Одновременно отпустить A/B для id=2, разные позиции, разный материал | Корреляция (sessionId,2) не смешивается; оба вернули None; observer видит оба материала в правильных позициях; готовность B не ждёт закрытия A |
| D03 | Запись A и B в одну позицию с gate/barrier и разными материалами | Обе успешно применённые записи отмечены своим applySequence; итог соответствует последней реально исполненной записи; заранее победителя по имени процесса не назначаем |
| D04 | A посылает повреждённый/слишком большой кадр либо разрывает соединение; B пишет повторно | A закрыт по контракту; B остаётся READY и действительно меняет другой блок; очередь/ошибка A не использует id B |

Для D02 допускается дополнительно загейтить A и проверить завершение B:
gate должен быть per-session/per-request и не останавливать весь dispatcher.
Один завершившийся A, затем B — не доказательство одновременной работы.
Общий токен в этих тестах не доказывает персональные квоты учеников; их нет в v0.1.

6. Валидация и транспорт N01–N10
------------------------------

| ID | Ввод/ситуация | Ожидаемый исход |
|---|---|---|
| N01 | Неверный токен; отсутствующий env на клиенте | AUTH_FAILED и закрытие либо локальный AuthenticationError; мир неизменён; токен не попал в отчёт |
| N02 | Другой major, невалидные поля hello, repeated hello, blocks.set до hello | Точная ошибка/закрытие из контракта; READY не получен либо повтор запрещён; мутации нет |
| N03 | Неизвестный или недоступный мир | WORLD_NOT_FOUND либо PERMISSION_DENIED; UUID исходного мира и соседние блоки неизменны |
| N04 | Неизвестный материал, предмет вместо блока, nonempty states, неподдержанный legacy/data | INVALID_BLOCK/UNSUPPORTED_FEATURE либо локальный UnsupportedLegacyBlockError; без подмены воздухом и без setter |
| N05 | Неправильный raw position, дробь/bool/переполнение, высота вне мира/позиция вне WorldBorder | INVALID_PARAMS либо COORDINATE_OUT_OF_BOUNDS; observer подтверждает отсутствие записи |
| N06 | Чанк заранее подтверждён unloaded; raw blocks.set | CHUNK_NOT_LOADED; повторное checkChunk показывает, что запрос его не загрузил; затем при явном setup тот же запрос успешен |
| N07 | Один кадр разбит на TCP-порции; затем raw id=2/id=3 с разными блоками в одну позицию отправлены вместе и оба queued под gate | Неполный кадр не исполняется; после LF ровно одна операция; после release applySequence(id=2)<applySequence(id=3), итог второй блок — это проверка FIFO очереди |
| N08 | Invalid JSON/UTF-8, duplicate keys, oversized/deep frame, незавершённый EOF | Ошибка/закрытие строго по таблице; повреждённая операция не выполняется; B из D04 остаётся работоспособным |
| N09 | Batch, notification без id, null/string/fraction/repeated ID, unknown method, positional/extra params | Запрещённые формы не мутируют мир; notification без ответа; для прочих точные code/closure; unknown method не ломает READY |
| N10 | Лимит активных соединений, входной/выходной очереди; медленный читатель | Ограниченное число ресурсов; отказ excess; socket IO не ждёт на main thread; после освобождения ресурса новый клиент принимается |

N07/N10 используют raw-клиент, поскольку официальный Python-клиент держит
один RPC в работе. Это не основание расширять публичный API batch/async-методами.
Для двух подслучаев N07 используются свежие READY-сессии с заново начинающимися
ID, чтобы проверка partial frame не создавала нарушения возрастающего ID.
V06 проверяет порядок последовательного API, N07 — отдельно FIFO уже принятой очереди.
Для N10 переполнение создаётся контролируемо при удержанном gate; размеры очередей
и close проверяются наблюдаемыми счётчиками, а не только отсутствием OOM.

7. Сбои F01–F05
---------------

| ID | Управляемый сбой | Ожидаемый исход |
|---|---|---|
| F01 | TCP-прокси после hello удерживает только ответ blocks.set; observer подтверждает фактическую запись | У клиента OperationTimeoutError/unknown, соединение закрыто; одна передача запроса и один APPLY_BEGIN, автоматического повтора нет |
| F02 | A закрывается, пока его запрос в gate, сервер подтверждает SESSION_CLOSED/CANCELLED, gate освобождается | Не начатая запись не выполняется; B продолжает работу. Само закрытие сокета без подтверждения server-close ещё не является барьером |
| F03 | Закрыть соединение после APPLY_DONE, но до доставки ACK | Мир изменён; клиент сообщает потерю связи/unknown, а не «точно отменено»; новый create не повторяет запись |
| F04 | Stop/disable сервера при A/B и ожидающем запросе | Нет бесконечного ожидания/утечки; клиенты получают EOF/ошибку/deadline; после нового старта новое соединение работает. Не требовать недоставляемый ACK shutdown |
| F05 | Wrong-ID, malformed result или поздний ответ от controlled TCP peer | Клиент закрывает соединение, не отдаёт ответ чужому запросу и не повторяет запись; это клиентский контрактный тест, не доказательство состояния Paper |

Fault proxy ведёт счёт запросов/доставок и редактирует журнал с удалением token.
Ожидания задаются deadline и событиями/барьерами. Общий watchdog стенда,
например 120 секунд на обычный case и 300 на startup, лишь ограничивает зависание;
это предлагаемые тестовые пределы, не SLA производительности сервера.
Для F01 клиентский deadline можно уменьшить конфигурацией теста, сохраняя
серверный запас, чтобы проверялось именно потерянное подтверждение.

8. Артефакты, порядок и выпуск
-----------------------------

Порядок: preflight/toolchain → чистый запуск → проверка observer → V01–V07 →
D01–D04 → N01–N10 → F01–F05 → чистый повтор основного пути → stop/cleanup.
Каждый случай подготавливает свои позиции/сессии и подтверждает baseline.
Окончание case учитывает уже принятые задачи; мир нельзя удалить, пока они
ещё могут исполниться. Cleanup освобождает только ресурсы стенда.

Для каждого прогона сохраняются:

- Manifest версий, URL/SHA артефактов, contract revision, конфигурация без секретов.
- Лог Paper, observer snapshots и trace с session/request/case IDs.
- Wire trace без токена, stdout/stderr и exit codes обоих Python-процессов.
- Машинный результат/JUnit и перечень pass/fail/skip с причинами.
- Отдельная отметка LAN smoke и ручной проверки IDE; отсутствие такой отметки
  нельзя заменять предположением о прохождении.

Минимальный срез завершён только после обязательных V/D/N/F сценариев и
совпадения SHA тестировавшихся wheel/JAR с выдаваемыми артефактами. Пропуск
обязательного сценария означает незавершённую приёмку. Полные V/D/N/F сценарии
T10 пока запланирован: полных N/F pass-результатов нет. Полные V/D проверки T09,
проверки стенда T08 и частичные проверки T02/T04/T05/T06/T07 описаны в отчётах; измеренная производительность
класса не заявляется.

Позже отдельно проверяются игроки/SELF и меняющиеся ники, полная таблица блоков,
setBlocks/jobs, физически сложные блоки, другие плагины, сохранение на диск,
полный класс и устойчивость длительных занятий. Это не скрытые требования v0.1.

Фактические основания: [Paper scheduler](https://docs.papermc.io/paper/dev/scheduler/),
[World API](https://jd.papermc.io/paper/26.2/org/bukkit/World.html),
[Block API](https://jd.papermc.io/paper/26.2/org/bukkit/block/Block.html).
World API отдельно отмечает отсутствие прежней гарантии spawn chunks;
поэтому стенд явно удерживает свою область. Реализация observer проверена в T08.
