Общие данные протокола 2.0 — I01–I04
==================================

Дополнение 0.3/I01 от 27 октября 2026 года сохраняет protocol 2.0/minor=0.
Добавлены отдельные capabilities и схемы управления игроками/мирами, снятия
эффектов; старый effects.add и players.teleport не меняют wire-форму.
В общий корпус добавлены 57 request/result/error-shape сценариев; новый режим
`method-response` позволяет обоим кодекам проверять результат указанного RPC.
Точный API и шесть новых доменных кодов описаны в
[контракте I01](../../docs/contracts/V0_3_CONTRACT.ru.md).
События/история ещё не отправляются и остаются следующими итерациями.

Дополнение 0.2.1: `system.hello.params.logging` — необязательный boolean.
При отсутствии/false журнал действий соединения выключен. При true он включается
после успешного handshake; токен не логируется. Capability `session.logging`
позволяет клиенту проверить поддержку. Старый hello без нового поля сохранён.
В общий корпус добавлены true/false и отклонение числового значения.

Корпус [fixtures/corpus.json](fixtures/corpus.json) используется кодеками Python
и Java. Формат и правила framing сохранены из [v1](../v1/README.md);
исторический корпус v1 не изменён. Изменённые строки преобразованы без
повторного разбора JSON payload, чтобы сохранить повторные ключи, неверные
числа и другие намеренно некорректные входы.

Изменения I01:

- `system.hello.params.protocol` запрашивает major=2, minor=0. Другой major
  может пройти проверку формы запроса, но отклоняется при согласовании сессии.
- `system.hello.params.token` допускает строку или null. Проверка токена —
  политика конфигурации сервера; кодек не вводит обязательную авторизацию.
- Ответ hello содержит обязательный namespaced `world.key` вместе с именем,
  UUID и границами высоты. Клиент сохраняет ключ в неизменяемом контексте.
- Capability `blocks.set` обязательна; `writes.buffered` описывает новый
  режим отправки. Дополнительные capability не нарушают форму ответа.
- I01 сохраняет `chunkPolicy="loaded-only"`, `coordinates="absolute"`,
  `applyPhysics=true` и прежние поля limits. Загрузка чанков входит в I02.
- Идентификаторы запросов, ответы и порядок исполнения продолжают действовать
  при нескольких запросах в полёте. Буферизация не использует notifications.

Классификация ошибок использует числовой код. Python показывает фиксированное
локальное объяснение, не копируя текст ошибки сервера или секретные параметры.
Буферизованный транспорт дополнительно связывает ошибку с методом и ID.

Дополнения I02:

- Непустые states проходят структурную проверку; применимость свойств к блоку
  проверяет Paper. Прежний fixture states-unsupported заменён проверкой формы
  states-shape-valid-registry-check-later; архивный корпус v1 не изменён.
- `blocks.get`, `blocks.setRegion`, `blocks.getRegion` описаны в
  [активном контракте](../../docs/contracts/V0_2_CONTRACT.ru.md).
- Сервер объявляет `chunkPolicy="load-generate"`. Клиент распознаёт и историческое
  loaded-only из I01, и новый режим.
- Серверные `system.progress` с requestId поддерживают живое ожидание долгого
  головного задания и его очереди. Это уведомления о ходе работы, не ACK.
- Добавлены REGION_BUSY (-32026) и CHUNK_LOAD_FAILED (-32027).

Дополнения I03:

- players.get/list/getPos/teleport и chat.post имеют отдельные строгие DTO;
  [контракт](../../docs/contracts/V0_2_CONTRACT.ru.md) фиксирует точные поля.
- hello не меняется: необязательная привязка игрока выполняется отдельным
  players.get. UUID исполнителя передаётся на каждый запрос, поэтому фасады
  withContext не меняют контекст друг друга.
- Телепортация принимает конечные дробные координаты. TargetResult содержит
  согласованные matched/applied и уникальные результаты по UUID; общий ACK
  не скрывает частичный результат. Чат передаёт буквальный текст.
- Добавлены PLAYER_NOT_FOUND (-32028), INVALID_SELECTOR (-32029),
  MISSING_CONTEXT (-32030), INVALID_TARGET (-32031),
  CONTEXT_WORLD_MISMATCH (-32032).
- Общий корпус содержит 266 сценариев, включая 15 новых проверок формы I03.
  Проверки результатов и реального исполнения находятся в тестах Python/Java
  и Paper-runner; форма запроса не подтверждает его игровую семантику.

Дополнения I04:

- players.giveItem, effects.add и entities.spawn имеют отдельные строгие DTO;
  формы, единицы и специальные параметры закреплены в активном контракте.
- InventoryResult проверяет уникальность UUID, matched/applied, типы метаданных
  и сохранность количества: requested=given+leftovers+dropped. Клиент дополнительно
  сверяет остатки с запрошенным предметом и режимом overflow.
- Ссылка созданной сущности содержит UUID, runtime ID, key и признак living;
  фактический key должен совпадать с запрошенным. Частичный успех не повторяется.
- Новые ошибки: INVALID_ITEM (-32033), INVALID_EFFECT (-32034),
  INVALID_ENTITY_TYPE (-32035), UNSUPPORTED_ENTITY_TYPE (-32036),
  ENTITY_NOT_FOUND (-32037).
- Общий корпус расширен до 283 сценариев (+17 I04); отдельно проверяются
  ответы и игровые действия на сервере. Протокол остаётся 2.0.

Дополнение 0.3.1:

- `PEACEFUL_SPAWN_BLOCKED` (-32053) сообщает, что сложность мира назначения
  запрещает создание выбранного типа сущности. Проверка происходит перед
  мутацией после загрузки чанка; outcome — `not-applied`.
- Python представляет его как `PeacefulSpawnError` с фиксированным понятным
  сообщением. [Точный контракт и критерий](../../docs/contracts/V0_3_1_SPAWN_CONTRACT.ru.md).
- Новый общий frame проверяется обеими реализациями codec; протокол остаётся 2.0.
